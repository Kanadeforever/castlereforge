## refactor30 历史因果增量

### 炼化 LB/RB 为什么会在 refactor29 反向

refactor29 已经正确把 LB 映射成 `INPUT_CATEGORY_PREV`、RB 映射成 `INPUT_CATEGORY_NEXT`，错误发生在炼化 Adapter 的最后一步：它把视觉 `delta` 直接做了 `current + delta`。实机证明炼化原版 `owner+category` 的 native index 增长方向与画面六类别从左到右相反，所以这种写法把最终视觉结果翻转了。refactor30 改成 `target = current - delta`；这不是改变通用输入，而是由 Adapter 修正原版内部编号。

### 存档点为什么当时没有新增模块（已判错）

refactor30 因页面外观与标准 SaveSlot 一致，误把地图存档点推断为主菜单天书 state7，并据此禁止 `save_point.c`。用户随后实机证明该路径完全收不到手柄输入；refactor31 枚举 `0x4245B0` 的全部直接调用后确认，二者只共享**子 SaveSlot 类**，不共享 owner。这个旧结论保留为反例，不再具有现行效力。

## 主 Interface 历史路线

### dev22：worker 手工构造——永久失败

worker 自己准备、分配 `0x660`、调用 ctor 并试图建立 Interface。复杂 UI 构造依赖游戏线程时序/上下文，风险高且实机失败。此路线永久禁止。

### dev24：`0x413933` 特殊地图事件——研究有价值，但对象归类错误

找到 `0x413850` 一组地图三项动作对象，以及 `0x413933 -> 0x431380` 的第0项 ButtonEvent，后面确实能进入 Interface ctor。后来重新与固化资料/反汇编对照，确认这组对象属于**休整/特殊地图三项动作菜单**（第0项“調態”），不是普通探索通用菜单入口。

因此“`0x413933` 能进 Interface”是真事实；“它就是普通探索按菜单键的入口”是假结论。

### refactor17：补 mode/active 请求——实机仍 FAIL

r17 认为 dev24 只是缺少“先把对象切到 active/mode=1”，于是把 Y 接到该对象生命周期。用户实测普通地图 Y 完全无法打开菜单；日志甚至没有出现 Y 请求。这次实机结果促使重新检查对象归属，并最终否决这条普通入口解释。

### refactor17 Shell 迟钝——跨模块 pending 生命周期 BUG

手工打开主 Interface 后，LB/RB、左右角色、根层 B 都能工作，说明根 Shell 的 Button/Event 地址和业务语义基本成立；但一次按键经常不生效，需要连续按很多次。

日志表现为大量“请求原版切换”后才偶尔出现一次“已由原版按钮消费”。源码复核发现 Battle 在**非战斗**时仍每 8ms 全局 `UiBridge_ClearEvent()`，会把 Interface 刚排入的 pending 删除。只有碰巧在 8ms 窗口内被游戏线程消费的请求才成功。

### refactor18：owner 隔离成功，但 Y 第二路线仍失败

r18 把 Y 改到 `0x40CC73 -> 0x406F20`，实机普通地图仍完全打不开主菜单，因此这条门控不能继续称为“普通地图已确认入口”。

同一版本的 UiBridge owner 隔离却被日志验证有效：Shell 的每一条 LB/RB/角色/B 请求都能紧跟一次原版 Event 消费，不再出现 r17 那种 pending 被 Battle 随机删除的问题。

### refactor19：复用原版 Space 的业务事件

用户提出“不发送 Space，只执行 Space 后面的原版事件”。重新反汇编得到：

```text
0x44A4DF  cmp eax,0x20
0x44A4E8  cmp [0x89F808],0
0x44A4F4  cmp [0x468BF0],0
0x44A500  push 1
0x44A57B  call 0x40B230
```

因此 r19 的 Y 只在 Exploration 游戏线程调用 `0x40B230(1)`，不再 patch 0x40CC73，也不生成任何 Space 键盘输入。

同时确认 `0x436330` 要求 `Interface+0x590>8` 才扫描根导航。r18 会在动画门关闭时丢掉新按键；r19 改成最多 8 项的语义动作队列，在安全帧顺序提交。

### refactor20a：主 Interface 预检由“函数体指纹”改成“业务链特征”

用户在 r19/r20 代码线上遇到：`[主界面预检失败] 原版 0x40B230 地图动作事件入口不一致`，长度 `0x23`，导致整个 Hook 安装停止。该检查验证了我们根本不会改写的函数体，属于过度严格。

新规则：保留 `0x44A4DF` 的 Space/busy/mode/action=1 业务语义，条件跳转位移使用 mask；`0x44A57B` 只要求仍是有效 `E8 rel32`，运行时解析它当前真正调用的目标。若其它兼容补丁把目标改到 wrapper，Y 跟随原版 Space 当前链路，不因为 `0x40B230` 函数体变化拒绝启动。Shell 真正 Hook 的 10 个 ButtonEvent CALL 仍精确 fail-closed。

### refactor21：法宝确认安全与绝学页

用户实机确认 refactor20a 的法宝页主体可用，但发现两个必须修正的事实：

1. LT/RT 的视觉方向反了。根因是不能把内部 subtype index 的递增/递减当成屏幕左右；r21 改为读取真实按钮 X 坐标。
2. X 弃置后，画面默认高亮“取消”，直接 A 却执行“确定”并丢弃物品。原版 type1 双按钮构造时会先把 `+0x58C=1`，随后 Update/HitTest 才形成真实视觉焦点；worker 若过早相信构造初值就会产生危险错选。

r21 的安全规则是：新 popup 默认逻辑取消；未由手柄主动导航时，被动观察原版真实 HitTest；A 选择当前焦点对应真实按钮；B 永远原版取消。state3 绝学使用确认框从第一版开始采用同一**安全原则**，但业务 Adapter 仍独立实现。
