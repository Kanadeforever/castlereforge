# 宽屏技术设计与协议

> 当前候选：v0.12.0 RuntimeSDK 适配候选（宽屏业务仍以 v0.11-poc11 实机基线为准）
> 对照基线：Godot兼容引擎研究固化49

> RuntimeSDK 联动已实现：Widescreen 注册 Display/Render 权威后端，逐帧发布最终 CameraPlan、
> `WorldToScreen/ScreenToWorld`、RenderQueue 与 Present。普通世界允许全输出投影；对白、Battle、
> 硬4:3和过渡阶段明确不可投影。当前结论已通过编译和假 Provider 合同验证，尚待目标游戏联合实机。
> Quest/Marker 只能查询 Runtime Display，不读取 INI、私有全局或固定添加 107/240。FPSUnlock 仍延期。

## 1. 原版 renderer 契约

原版 software backing 必须继续保持：

```text
768×576
= (64 + 640 + 64) × (48 + 480 + 48)
```

POC1 已经实机证明，把 renderer backing 直接扩大到 982×576 会破坏原版绘制契约。

因此当前所有版本都坚持：

```text
原版 renderer 永远只看到 768×576
```

## 2. 普通世界真宽屏

### 16:9

```text
107 + 640 + 107 = 854
```

### 21:9

```text
240 + 640 + 240 = 1120
```

中央完整队列只执行一次；左右只重放 `0x40B050` Scene world manager，并在侧画后恢复原 Camera 和完整 768×576 backing。

## 3. Camera 安全边界

地图足够宽时，中央 Camera 按当前侧区宽度向内收紧：

```text
wideMin = minX + SideWidth
wideMax = maxX - viewportW - SideWidth
```

避免地图边缘跑进完整宽屏相机范围。

地图不足当前输出宽度时使用对称居中安全策略，不让 Camera 强行越界。

## 4. 消息 UI 隔离

静态证据：

```text
0x40B050
  -> 0x403E30
  -> 0x404800
```

world manager 本身会再次进入消息更新 / 绘制路径。

所以左右 Camera 重放期间临时保存并清零：

```text
0x46F678
0x46F679
```

侧画结束立即恢复。

v0.7 已实机证明该方案可以消除第二套立绘、对话框和选择 UI。

## 5. 所有消息统一中央 640

只要原版消息 Event 槽：

```text
0x46F670 & 0xFF != 0
```

就进入统一侧面板模式。

不再区分：

- 玩家主动；
- NPC；
- 自动脚本；
- 剧情；
- 提示；
- 选择框。

同一 active Event 中两句对白之间短暂没有消息框时仍保持，直到 Event 和消息 UI 都结束，或者 scene identity 真正切换。

## 6. Battle

检测：

```text
BattleManager draw = 0x4429F0
```

Battle 不做多 Camera 真宽屏，而是：

```text
中央原版640
+ 左右统一侧面板
```

## 7. 左右推入 / 退出动画

动画量：

```text
0..256
```

经过整数 smoothstep：

```text
3t² - 2t³
```

再映射成：

```text
0..SideWidth
```

左面板从左侧屏幕外进入；右面板镜像进入。

退出完全反向。

移动内边缘保留 10 像素柔化带。

中央 640 不缩放、不移动。

## 8. v0.11 侧区样式分支

v0.11 不复制第二套状态机，而只在同一个 `apply_cinematic_slide_to_staging()` 最终像素处选择：

```text
BlurredSides=1
    -> 采样当前模糊背景并压暗

BlurredSides=0
    -> 直接使用纯黑 0x0000
```

之后两种模式都进入同一个：

```text
blend_rgb565(original, panel_pixel, edge_alpha)
```

所以运动、柔化和时间完全一致。

## 9. 模糊模式

工作图宽度随输出模式变化：

```text
16:9 -> 214×120
21:9 -> 280×120
```

流程：

```text
中央640按当前宽高比裁切
-> 缩图
-> 7×7 blur
-> 7×7 blur
-> 双线性采样
-> 压暗到160/256
```

## 10. 黑边模式

`BlurredSides=0` 时不调用：

```text
build_cinematic_low_source()
blur_low_pass()
```

因此没有无意义的模糊计算。

## 11. 硬 4:3 区域

标题、Bink、主 Interface 仍使用原有纯黑硬 4:3 逻辑。

`BlurredSides` 主要改变消息和 Battle 的统一侧面板；这些硬 4:3 区域本来就是黑色，因此没有视觉差异。

### 12.2 当前改写的四个 E8 CALL

| 地址 | 原目标 | 用途 |
|---|---:|---|

| `0x44A9E6` | `0x405A10` | 动态 staging -> Present |

### 12.3 Display / backing

| 地址/字段 | 语义 |
|---|---|
| `0x405960` | backing 分配 |
| `0x405A10` | Present |
| `0x405BD0` | 显示重建 |
| Display `+0x28` | DisplayMode* |
| 原 backing | 768×576 |
| logical | 640×480 |

### 12.4 Camera

| 地址 | 语义 |

## 13. 与固化49的对照

### 13.1 与本轮改动的关系

v0.11 只新增插件内部侧区像素样式：

```text
模糊
或
纯黑
```

没有新增任何游戏地址、Hook 或原版行为解释。

因此固化49中与宽屏有关的静态 Oracle 仍全部沿用：

- Display / DDDES；
- Camera；
- Scene world；
- Event；
- 消息生命周期；
- BattleManager。

固化49新增的 Battle 状态/抵消字段研究与本轮侧区样式无直接关系。

### 13.2 继续冻结的核心结论

- 原 renderer backing = 768×576；
- 982 / 1248 只可作为插件最终 staging；
- 不能把研究版扩 backing 路线重新作为 renderer 方案；
- Battle 识别继续使用 `0x4429F0`；
- 消息 UI 继续使用 `0x46F670/678/679` 的已闭合生命周期证据。
