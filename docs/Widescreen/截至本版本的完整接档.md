## 三、最重要的 renderer 结论

原版内部：

```text
768×576
= (64 + 640 + 64) × (48 + 480 + 48)
```

POC1 把 backing 扩成982×576后实机花屏/残留，因此永久放弃“扩大原 renderer backing”。

当前无论16:9还是21:9，原 renderer **始终只看到768×576**。

## 四、当前两种显示模式

INI：

```ini
[Display]
Ultrawide=0
```

### 默认 16:9

```text
854×480
107 + 640 + 107
staging 982×576
```

这是 v0.9 已实机验收的稳定行为。

### 可选 21:9

```text
1120×480
240 + 640 + 240
staging 1248×576
```

严格数学21:9：`1120/480 = 21/9`。

## 五、普通地图真宽屏

每帧：

1. 保存完整绘制队列；
2. 用安全中央 Camera 执行原完整队列一次；
3. 把中央640复制到宽屏帧中央；
4. 备份整张768×576 backing；
5. 只恢复 Scene world manager；
6. Camera 向左偏 SideWidth，重画，取新增左侧；
7. Camera 向右偏 SideWidth，重画，取新增右侧；
8. 恢复 Camera；
9. 恢复整张原 backing；
10. 最后 Present 插件自己的 staging。

左右重放只允许：

```text
0x40B050 Scene world manager
```

不恢复整队列。

## 六、地图边界

原版 Camera 只保证640宽。

当前地图足够宽时：

```text
centerMin = minX + SideWidth
centerMax = maxX - 640 - SideWidth
```

16:9 `SideWidth=107`；21:9 `SideWidth=240`。

所以超宽模式会更早停止 Camera，避免地图边缘进入相机范围。

如果地图比当前输出还小，不越界伪造内容；v0.10 会把地图在640之外实际拥有的额外宽度左右平分，让整张小地图尽量居中，避免21:9下出现明显偏向一边的大空区。

## 七、切图瞬态

最多保留上一张有效左右世界4个 Present，避免切图/Camera bounds中间态造成整条黑边闪烁。

超过宽限后安全收黑，不能无限显示旧地图。

## 八、GUI总原则

**GUI本身始终保持原版640×480坐标和比例。**

只有世界层真扩展。

这就是 v0.9 实机中头像、对话框、Battle HUD 和其它GUI比例保持自然的根本原因。

## 九、所有消息统一电影式方案

v0.9 用户已明确验收通过。

不再区分：

- 玩家主动；
- NPC；
- 自动脚本；
- 剧情；
- 提示；
- 选择框。

只要消息 UI 活跃：

```text
中央原版640
+ 左右强模糊面板推入
```

结束后左右向屏幕外退出。

v0.10 只把侧区宽从107同步扩到240；中央规则不改。

## 十、消息重复根因与冻结修复

实机曾出现左右第二套头像/对话框。

静态确认 `0x40B050` 内部仍会：

```text
0x40B087 -> 0x403E30
0x40B08C -> 0x404800
```

所以左右 Camera 重放期间：

```text
保存 0x46F678/679
临时置0
侧画
恢复
```

v0.7 用户已确认“手动触发没有重叠”，该方案必须冻结。

## 十一、消息锁存

进入电影式后：

- 同一 active Event 仍在时，中间短暂无对话框也保持；
- Event和消息都结束后退出；
- scene identity真正变化时也退出。

解决剧情中间反复进出侧区的问题。

## 十二、电影式模糊

v0.8 用户明确认为左右推入/退出方案“非常好”，随后决定推广到所有对话框。

当前低分辨率源：

```text
16:9：214×120
21:9：280×120
```

源画面按目标比例从中央640×480做中心 crop：

```text
16:9 高约360
21:9 高约274
```

然后两遍7×7 blur、双线性放大、压暗160/256。

## 十三、Battle

当前稳定策略：

```text
+ 左右电影式模糊
```

不做Battle真宽屏。此前world-only Battle尝试仍存在对象层风险。

## 十四、标题 / Bink / 主 Interface

继续：

```text
中央640
+ 左右黑边
```

16:9 各107；21:9 各240。

Bink直接把640内容写到物理surface，所以独立包装 `_BinkCopyToBuffer@28`，destX加当前 SideWidth。

## 十五、Present staging

0x406330按：

```text
modeWidth + extraX*2
```

读取每行，extraX=64。

所以：

```text
854 -> 982
1120 -> 1248
```

这只是最终读源，不是 renderer backing。
