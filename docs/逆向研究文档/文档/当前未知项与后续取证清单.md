- 因此8-bit PCM按标准WAVE PCM语义为unsigned byte，16-bit为signed little-endian。

旧文档把前两个字节合看成`u16 format_code`得到的`0x1001/0x1002/0x0801`，现在只保留为历史兼容显示值：`channels | (bits_per_sample << 8)`。

**路线状态：CLOSED_AT_SOLID37。**

### F. 【固化38已解决】`duration_legacy_ticks` 的Legacy Clock单位尺度

固化38已经把DDDES/WinMM/WM_TIMER/主循环/注册对象管理器/EVE/SF2链闭合。当前真实`DDDES.SCI +0x11=20`，固定基数为100，divider为5；在原版预期`wPeriodMin=1ms`下，一个Legacy Tick名义为50ms，也就是20Hz。

标准场景SF2 `0x407400`每个Legacy逻辑步只把Section0 `+0x22`装入的countdown减1，因此一个countdown单位就是一个Legacy Tick。实现仍须保留原离散状态机与切换fencepost，不能只把记录粗暴改写成浮点秒数。

**路线状态：CLOSED_AT_SOLID38。**

## v0.7D阶段中-固化9：Event ID槽映射、saved Event输入失效与code12 fallback复核

本固化继续使用同 SHA256 Oracle `RPG.exe`。`0x40B230` 对传入 Event ID `n` 执行 `n*16` 寻址：读取 `base+n*16-8` 与 `base+n*16-4`。与已冻结 EVE 布局 `8-byte header + 130×16-byte descriptor` 交叉，可严格换算为 descriptor `slot(n-1)` 的 `+0/+4`。因此 **Event ID n（n>0）= 当前已加载 EVE 的 0-based slot(n-1)**；code12 fallback 的 `0x40B230(3)` 即当前 EVE `slot2`，不能再解释为全游戏固定“Event 3”。slot2 在具体地图中的业务内容仍需真实 EVE 语料。

## v0.7D阶段中-固化18：D8 Battle 初始化与胜利结算随机顺序静态闭合

### 1. RNG核心保持不变

当前 Oracle 的全局随机数实现继续冻结：

```text
state @ 0x46E29C
seed(value): 0x45155B -> state=value
next(): 0x451565
    state = state * 0x343FD + 0x269EC3 (mod 2^32)
    return (signed(state) >> 16) & 0x7FFF
```

全 EXE 当前扫描到对 `0x451565` 的 **56 个 E8 rel32 直接 CALL**。该数字只覆盖直接 `E8`，不包含函数指针/虚调用/表驱动间接调用；因此不能把“56”解释成游戏全部随机消费点总数。

### 2. 伏龍A随机倒计数属于 pre-reseed RNG

直接调用链已经闭合：

```text
EVE opcode0x37 / LayoutGR index 0x82「伏龍A」
0x40D41B -> RNG next
    r = RNG % 400 + 800
    DataCenter+0xF4 = r

随后：
0x40D4D8 -> 0x4322C0
0x4324EC -> 0x442040 Battle核心初始化
0x442076 -> 0x451583 取得系统时间派生seed
0x44207C -> 0x45155B 重写全局RNG state
```

所以 `0x40D41B` 的伏龍A倒计数 draw **发生在 Battle reseed 之前**；它不会把重新播种后的 Battle RNG 序列向前推进一位。兼容引擎如果把伏龍A计数器放到 Battle reseed 之后生成，会改变整场战斗后续随机流。

### 3. reseed 后的 Battle 初始化显式 draw 协议

`0x442040` 在重新播种后按内部初始化 mode 分流；该 mode 的作者业务名仍未证明，保持结构名：

- mode `2`：`0x4423CB -> 0x424430`；
- mode `1`：先强制 `DataCenter+0xD8=1`，再 `0x4424AC -> 0x424430`；
- 其他/default：若外部 helper 未提供值且 `DataCenter+0xD8==0`，`0x442503` 消耗一次 RNG，执行 `RNG%6+1` 写回 `+0xD8`，随后 `0x442536 -> 0x424430`。

`0x424430` 的随机消费规则：

```text
count1 = LayoutGR+0x18
合法成功路径要求 count1 > 0
r1 = RNG % count1
LayoutTeamID = LayoutGR+0x1C[r1]

count2 = LayoutGR+0x6C
if count2 > 0:
    r2 = RNG % count2
    second_value = LayoutGR+0x70[r2]
```

因此每次**成功**的 `0x424430` 调用显式消耗 `1 + (count2>0 ? 1 : 0)` 次 RNG。这里闭合的是 `0x442040/0x424430` 中已经逐指令证明的显式 draw；尚不能据此声称 Battle 初始化所有间接 callee 的随机消费已全部穷尽。

## 固化55新增：Battle动作类四同参双调用与战场结界语义边界

### 55.1 本轮直接纠错

固化54及更早活动规格曾把`0x422AB0`中class4第二次`0x42A7A0`概括为“角色参数反向”。固化55逐指令重算两次调用栈后确认这是错误表述：两次调用的performer RoleDefinition、target RoleDefinition、DamageInfo、FIRTTECH、flag五个逻辑实参全部相同，this也同为`0x8A0194`。旧“反向”结论撤销。

### 55.2 类四底层为确定性固定输出

`0x42C680`读取`FIRTTECH+0x18`；等于4时`0x42C7A9 -> 0x42CC70`。该专用分支不进入公式selector、`0x42B0D0`五槽或`0x451565` RNG，固定把同一0x50-byte DamageInfo写成success=1、主要value/status DWORD为0、`DamageInfo+0x44=FIRTTECH+0x1E8`后返回。第一次调用返回后上层尚未消费DamageInfo，class4立刻用同一五参数再算一次。

因此当前已证状态等价规则为：**原EXE有两次纯计算调用，但第二次对最终DamageInfo没有新增效果；Godot兼容实现可以折叠成一次。** 该结论只适用于class4当前代码，不推广到其他class。

### 55.3 canonical class4语料

500条Firttech的`+0x18`分布为`0:330, 1:94, 2:67, 4:7, 5:1, 6:1`。class4七条是：`0x1C2反咒禁制、0x1C9閾迦封界、0x1CA鬼唳天幕、0x1CD幽魄厲界、0x1CE六甲神儀、0x1CF時輪返陣、0x1D1鬼縛之陣`。7/7作者说明均描述对己方或敌方持续存在的结界、护界、阵法、场域规则，因此`+0x18==4`可冻结为**战场结界/阵法类动作业务族**；作者源码枚举正式名仍UNKNOWN。七条当前共同raw值：`+0x30=0,+0x3C=11,+0x44=3,+0x1E8=0`，不据此强命名这些字段。

### 1. DamageInfo 真基址与固化3坐标修正

- `0x422B27: lea ebx,[esi+0x170]`：每目标 `DamageInfo` 基址是攻击者 `FightRole+0x170`；`0x422C8D add ebx,0x50` 证明 stride=`0x50`。

### 2. 五槽 residual 的第一阶段 application：DamageInfo → pending

`0x422C3D..0x422C6E` 固定循环 5 槽：读取 `DamageInfo+0x24+slot*4` residual/value，并从 `DamageInfo+0x10+slot*4` 取得 raw effect-like ID。在 residual>0、raw ID signed compare `<=27`、目标对应 runtime raw-ID 槽 `FightRole+0xA34+id*4 <=0` 时，直接执行：

```text
FightRole(target)+0xCC+raw_id*4 = residual_value
```

`FightRole+0xCC..+0x164` 是 **39 DWORD pending array**；`0x41F284..0x41F29A` 在 FightRole reset 时明确清零全部 39 槽。

注意：代码只观察到 signed `>27` 排除；不能仅凭此指令宣称负 ID 永不出现。当前已解析源样本为非负，但业务约束仍需保持证据边界。

### 3. 第二阶段 commit：pending → runtime

`0x42160D..0x421647` 扫描 pending `+0xCC..<+0x168` 共 39 DWORD。若 pending>0 且 `FightRole+0xA6C<=0`，则：

```text
runtime[offset + 0x968] = pending[offset]
pending[offset] = 0
```

因为 `0xCC+0x968=0xA34`，因此形成精确一对一映射：

```text
pending  FightRole+0xCC..+0x164   (39 DWORD)
              ↓ +0x968
runtime  FightRole+0xA34..+0xACC  (39 DWORD)
```

`FightRole+0xA6C`位于runtime数组index14；固化48已由「无方变幻/时幻沙」作者文本以及结果归零、pending提交阻断机器行为闭合为**化幻／无形**状态。

### 4. runtime 递减与清零

`0x420440` 中 `0x420662..0x420697` 从 `FightRole+0xA34` 开始扫描 **39 DWORD**；正值一般每次函数调用减 `10`，减后 `<=0` 夹为 0。`0x420440` 当前只找到一个 E8 直接 caller：`0x442CDB`，位于 Battle manager 的 per-role update 路径。
