当 125% DPI、Segoe UI 实际字宽或正文内容让某一句多折一行时，正文所需高度会超过预留矩形，DrawText 直接裁掉末尾；链接区仍按固定位置绘制，因此产生实机截图中的覆盖。

- 使用 `DrawTextW(... DT_WORDBREAK | DT_CALCRECT)` 按当前客户区宽度测量正文真实折行高度；

- DPI 变化后同样重新计算所需高度。

自动换行会让 RichEdit 的视觉行数随窗口宽度变化，因此不能再依赖视觉行号 API 判断 INI 行边界。

about3 改为：

- 用 `EM_FINDTEXTEXW` 在 RichEdit cp 坐标里寻找真实 `\r` / `\n`；
- 用 `EM_GETTEXTRANGE` 读取真实逻辑行；
- 用 `EM_EXSETSEL + EM_SETCHARFORMAT` 语法分色；
- 保存错误定位通过 `get_ini_logical_line_range_()` 按真实换行重新定位。

这样很长的 `;` 注释即使视觉折成多行，仍属于一个逻辑行并保持整行绿色。

### 0.5 未保存 / 保存失败提示增强

about3 使用醒目亮红色：

```text
● 未保存修改
● 保存失败：...
```

保存失败仍保留详细弹窗、具体行号和原因。修正并保存成功后恢复正常状态。

## 2. dev9 封存运行时架构

### 2.1 Launcher / Pre-Loader

```text
CastleModLoader.exe
  ↓ GUI / mods.ini / Loader INI
用户点击“启动游戏”
  ↓ 打开/清空本轮 modloader.log
SetCurrentDirectoryW(游戏根目录)
  ↓
Launcher 在 CreateProcessW 前临时 SetDllDirectoryW(mods)
  ↓
CreateProcessW(RPG.exe, CREATE_SUSPENDED)
  ↓
Launcher 恢复自己的 SetDllDirectoryW(NULL)
  ↓
内存注入两个 Early Import（顺序固定）
  1. CastleLocaleBootstrap.dll!CastleLocaleBootstrap_Bootstrap
  2. CastleModCore.dll!CastleModCore_Bootstrap
  ↓
ResumeThread
```

Early Import 在 dev9 恢复使用纯 DLL 文件名，由创建子进程时继承的 `mods` DLL 搜索环境定位两个内部 DLL。

### 2.2 LocaleBootstrap

`mods\CastleLocaleBootstrap.dll`：

- PE32/i386；
- 静态依赖严格只有 `ntdll.dll`；
- 在 KERNEL32 普通初始化之前尽早处理 CP950 NLS；
- 读取/使用 `c_950.nls`、`l_intl.nls`；
- 导出：
  - `CastleLocaleBootstrap_Bootstrap`
  - `CastleLocaleBootstrap_GetStatus`
  - `CastleLocaleBootstrap_GetObservedAnsiCodePage`
  - `CastleLocaleBootstrap_GetObservedOemCodePage`

### 2.3 ModCore

`mods\CastleModCore.dll`：

- PE32/i386；
- 静态依赖严格只有 `KERNEL32.dll`；
- dev9 保留 Core 早期 `SetDllDirectoryW(g_mods_root)`；
- 建立 Entry Gate；
- 建立 CP950/zh-TW Locale、USER32、GDI 兼容层；
- 建立 Overrides / ASI / GameAudit；
- ASI 自身使用绝对路径 + `LoadLibraryExW(..., LOAD_WITH_ALTERED_SEARCH_PATH)`，确保依赖 DLL 与 ASI 同目录可解析。

### 2.4 ddraw 裁决

当前最终裁决不是“Loader 完全不碰 ddraw”，而是 **保持 dev9 已实机成立的兼容边界**：

- Loader 不替用户分发/选择/卸载 `ddraw.dll`；

- dev9 继续让已加载 `ddraw.dll` 进入既有 Locale/USER32/GDI/文件 API Win32 IAT 兼容桥；

- cnc-ddraw 是当前稳定方案；
- 非 cnc-ddraw wrapper 的 `SetDisplayMode Error!(DDWCreate)` 不再继续研究。

# 《幽城幻剑录》Mod Loader v0.3.0-dev7 完整接档说明

> 本文件是 **v0.3.0-dev7 的独立完整接档**。任何人只拿到本包，都应优先阅读本页 dev7 当前裁决；下方完整保留 dev6、dev5 及更早研究作为历史证据。历史章节里的“当前”“推荐”“正式布局”只代表当时版本，凡与本节冲突，一律以 dev7 为准。

## 零、v0.3.0-dev7 当前状态

### 0.1 本轮直接来自用户实测的两个修正

本轮不是新增大范围业务功能，而是对 dev6 两个已被 Windows 实机直接指出的问题做收敛：

1. **Loader 两个内部 DLL 的发布位置恢复到 `mods\` 根目录。** dev6 为了避免 `SetDllDirectoryW(mods)` 污染曾把 `CastleLocaleBootstrap.dll` / `CastleModCore.dll` 移到游戏根目录；用户明确否决这个布局，因为卸载时理想语义应是“只删除 `CastleModLoader.exe` + 整个 `mods\`”。dev7 因而把两个 DLL 放回 `mods\`，但**没有**把 `SetDllDirectoryW(mods)` 加回来。
2. **INI 编辑器的语法颜色坐标修复。** dev6 实机截图显示同一条 `;` 注释会被错误切成绿/紫/蓝/橙多段，而且偏移会逐行累积。根因是旧着色器把 `WM_GETTEXT` 缓冲区数组下标直接当 RichEdit `EM_EXSETSEL` 的字符位置。dev7 改为完全使用 RichEdit 自身的 `EM_LINEINDEX / EM_LINELENGTH / EM_GETTEXTRANGE` 坐标进行逐行读取与着色；错误行选择也改成“行号 → EM_LINEINDEX”定位。

### 0.2 dev7 正式发布布局

```text
游戏目录\
├─ RPG.exe
├─ CastleModLoader.exe
├─ ddraw.dll                         ← 可选第三方图形兼容层，Loader 不管理/不 Hook
└─ mods\
   ├─ CastleLocaleBootstrap.dll      ← Loader 内部组件，不是用户 Mod
   ├─ CastleModCore.dll              ← Loader 内部组件，不是用户 Mod
   ├─ CastleModLoader.ini
   ├─ mods.ini
   ├─ modloader.log / game.log       ← 按设置生成
   ├─ asi\
   │  ├─ *.asi
   │  ├─ 同名 *.ini
   │  └─ ASI 自己依赖的 DLL
   └─ overrides\
      └─ 各文件 Mod
```

目录语义必须严格区分：

- `mods\` 根目录允许 Loader 自己的两个内部 DLL、配置、日志；
- **用户**代码 Mod 与它们的 DLL 依赖只进 `mods\asi`；
- 文件 Mod 只进 `mods\overrides`；
- `ddraw.dll` 不进入 `mods`，继续按 cnc-ddraw / DDrawCompat / dgVoodoo 等组件自己的部署规则放置；
- `scripts\`、`plugins\`、`update\`、游戏根目录 `*.asi` 均不参与当前 Mod 发现。

### 0.3 两个内部 DLL 如何在 `mods\` 中启动，而不恢复全局 DLL 搜索污染

当前方案不是：

```c
SetDllDirectoryW(L"mods");
```

而是 Launcher 在 suspended RPG.exe 的临时 Import Directory 中直接写入：

```text
mods\CastleLocaleBootstrap.dll
mods\CastleModCore.dll
```

Launcher 启动时已经把 CurrentDirectory 固定为自身/RPG.exe 目录，因此这两个相对名称只负责定位 Loader 自己的两个内部 DLL。`mods\` 不被加入整个 RPG.exe 生命周期的 DLL 搜索列表，第三方 DirectDraw wrapper 的依赖环境不会因此被统一改写。

这里必须保持的回归边界：

- `launcher.c` / `mod_loader.c` 不得重新调用 `SetDllDirectoryW`；
- `platform.h` 不需要重新声明该 API；
- Core/Overrides/Locale/USER32/GDI 不得重新把 `ddraw.dll` 加入 Patch 目标；
- Launcher 不扫描、不复制、不管理 `mods\ddraw.dll`；
- 两个 Loader DLL 的导入依赖自身非常收敛：Bootstrap 仅 `ntdll.dll`，Core 仅 `KERNEL32.dll`。

### 0.4 ASI 依赖当前方案

ASI 保持 dev6 的正确修正：

```text
mods\asi\Controller.asi
mods\asi\SDL3.dll
```

Core 先把 ASI 主文件转为**绝对路径**，再调用：

```c
LoadLibraryExW(absolute_asi_path, NULL, LOAD_WITH_ALTERED_SEARCH_PATH)
```

因此 ASI 自己的普通依赖可从 ASI 所在目录解析，不需要也禁止为了它们把 `mods\` 根目录设成长期 DLL 搜索路径。错误 126 的诊断也应优先提示“检查依赖是否和 ASI 一起放在 `mods\asi`”。

### 0.5 INI 编辑器颜色规则与 dev7 根因修复

当前颜色规则固定为：

- `;` / `#` / `//` 开头的整行注释：**整行统一绿色**；
- `[Section]`：紫色；
- `=` 左侧变量名：蓝色；
- `=` 本身：中性灰；
- `=` 右侧值：橙色；
- 明显违反通用 INI 结构的文本：红色。

关键实现变化：

```text
dev6（错误）
WM_GETTEXT 全文
→ 用返回缓冲区下标计算颜色范围
→ EM_EXSETSEL
→ CR/LF 计数差异逐行累积
→ 同一注释被错误切成多种颜色


dev7（当前）
EM_GETLINECOUNT
→ EM_LINEINDEX
→ EM_LINELENGTH
→ EM_GETTEXTRANGE
```


这条对照把问题边界从“老游戏是否挑 ddraw 实现”重新收回到 Loader：既然同一游戏、同一组件、同一机器只在经过 Loader 后失败，Loader 必须先恢复与直接启动尽量一致的 DLL/兼容层环境，而不是给某一个 wrapper 打特判。

随后用户进一步明确本项目原始目录设计：

- `mods\` 根目录 **只放 INI / LOG 等数据文件**；
- 所有用户 Mod 只进入 `mods\asi\` 与 `mods\overrides\`；
- ASI 依赖 DLL 通常与对应 ASI 一起放在 `mods\asi\`；
- Overrides 是借鉴 Ultimate ASI Loader `update\` 的“文件覆写”思想，不依赖 `SetDllDirectoryW`；
- `ddraw.dll` 是游戏运行兼容层，不属于 Mod Loader 管理的 Mod。

复核 dev5 后确认，dev5 已经偏离了这套规则：

1. Launcher 在创建 RPG.exe 前调用 `SetDllDirectoryW(g_mods)`；
2. Core 进入游戏后再次调用 `SetDllDirectoryW(g_mods_root)` 并长期保持；
3. `CastleLocaleBootstrap.dll` / `CastleModCore.dll` 被放在 `mods\`，从而反过来制造了“必须让 mods 参与 DLL 搜索”的需求；
4. ASI 用相对路径 `LoadLibraryW(mods\asi\xxx.asi)`，并把依赖 DLL 错误规定为放 `mods\` 根目录；
5. Launcher 还主动探测 `mods\ddraw.dll`；
6. Core / Overrides / Locale / USER32 Locale / GDI Locale 都把 `ddraw.dll` 纳入 IAT Patch 目标。

### 0.4 为什么 Loader 自身 DLL 移回游戏根目录

Launcher 会在挂起的 RPG.exe 内存 Import Directory 中加入：

```text
CastleLocaleBootstrap.dll
CastleModCore.dll
```

Windows 对这种裸 DLL 名本来就能从应用程序目录解析。把这两个 Loader DLL 与 `RPG.exe` 放在同一目录后，不再需要为了找到它们而把 `mods\` 强行加入 DLL 搜索环境。

因此 dev6：

- `launcher.c` 改为检查 `g_launcher_dir\CastleLocaleBootstrap.dll`；
- `launcher.c` 改为检查 `g_launcher_dir\CastleModCore.dll`；
- `build.bat` 把两个 DLL 输出到 `编译内容\` 根目录；
- 正式构建前主动删除 `编译内容\mods\` 中 dev5 旧位置残留，防止混合包。

### 0.5 `SetDllDirectoryW(mods)` 已完全从业务代码删除

当前源码中不再声明/调用 `SetDllDirectoryW`。

dev6 不采用“临时调用然后恢复”的折中，而是彻底移除，因为经用户确认：

```text
mods\ 根目录 = 配置/日志数据目录
```

它本来就不应该成为 DLL 搜索目录。

这项修改与 Overrides 无关。Overrides 依靠文件 API 重定向，根据 `mods.ini` 和 `mods\overrides\...` 寻找替代文件；它从未需要 DLL 搜索路径才能工作。

### 0.6 ASI 同目录依赖：绝对路径 + `LOAD_WITH_ALTERED_SEARCH_PATH`

#### 0.6.1 旧失败路线必须保留的教训

v0.2.1 曾经试过：

```text
LoadLibraryExW(相对路径, NULL, LOAD_WITH_ALTERED_SEARCH_PATH)
```

实机出现统一 Win32 错误 126。这个失败不能简单归结为“这个 flag 不可用”；真正问题是把**相对路径**交给了要求完整路径的装载方式。

#### 0.6.2 dev6 正确实现

用户侧仍然保持便携相对路径：

```text
mods\asi\Controller.asi
mods\asi\SDL3.dll
```

只有真正调用 Windows Loader 前才做：

```text
mods\asi\Controller.asi
        ↓ GetFullPathNameW
C:\...\Game\mods\asi\Controller.asi
        ↓
LoadLibraryExW(
    absolute_path,
    NULL,
    LOAD_WITH_ALTERED_SEARCH_PATH
)
```

好处：

1. INI / GUI / 日志中的用户目录结构仍是便携相对路径；
2. ASI 在装载自己的依赖时可使用 **ASI 所在目录**；
3. `SDL3.dll` 等依赖只需要和 ASI 一起放 `mods\asi`；
4. 不必复制到游戏根目录；
5. 不必放到 `mods\` 根目录；
6. 不必永久改变 RPG.exe 的全局 DLL 搜索环境。

错误 126 诊断也同步修改：若 ASI 主文件已经存在但装载返回 126，提示检查依赖 DLL/下级依赖，并要求把对应依赖放在 `mods\asi`。

### 0.8 Overrides 与 Ultimate ASI Loader `update\` 思路的关系

本项目继承的是“**不覆盖游戏原文件，而在文件打开时把路径重定向到 Mod 副本**”这套设计思想。

当前 Overrides 仍是：

```text
游戏/原版业务模块请求文件
        ↓
CreateFileA/W / GetFileAttributesA/W 等既有 Hook
        ↓
按 mods.ini 的 Overrides 顺序检查启用项
        ↓
最下面的启用 Mod 优先级最高
        ↓
找到替代文件 → 打开 overrides 中的副本
找不到       → 继续打开原文件
```

**这条链没有使用 `SetDllDirectoryW`。**

因此 dev6 删除 DLL 搜索目录不会动 Overrides 的核心语义，且本轮特意没有趁机改动覆盖优先级、只读重定向、CP950 ANSI 路径转换、模板排除等既有逻辑。

### 0.14 失败方案 / 踩坑累计

#### A. `LoadLibraryExW(相对路径, LOAD_WITH_ALTERED_SEARCH_PATH)` —— 历史 FAIL

v0.2.1 实机错误 126。dev6 不重走这条路；现在必须先生成绝对路径。

#### B. `mods\` 根目录作为长期 DLL 搜索目录 —— dev6 判定架构错误

即使某些组件可运行，也违反用户明确目录语义，并使游戏/第三方组件看到与直接启动不同的 DLL 环境。已删除。

#### C. 把 Loader 自身 DLL 放在 `mods\` —— dev6 判定架构错误

这会制造“为了找到 Loader 自己，必须污染 mods DLL 搜索环境”的循环依赖。已移回应用目录。

#### D. `mods\ddraw.dll` —— dev6 判定错误职责

DirectDraw wrapper 不是用户 Mod，不应由 Mod Loader 托管。已删除该机制。

#### E. Patch 第三方 `ddraw.dll` 的文件/Locale/USER32/GDI IAT —— dev6 判定越界

即使 Hook 本身透明，也不应该让“启用 Mod Loader”改变第三方图形兼容层的内部 API 路径。已全部排除。

#### F. 不能把当前修改宣称为“DirectDraw 实机已修复”

目前只有静态边界闭合；真正验收仍必须用用户此前会失败的同一 wrapper、同一配置、同一游戏目录进行 A/B 实测。

### 0.3 dev5 最小窗口实现

主窗口新增 `WM_GETMINMAXINFO` 处理，并使用统一辅助函数计算最小**外框**尺寸，而不是把 `1024`、`640` 直接塞给 `ptMinTrackSize`。

计算步骤：

```text
1024×640 DIP 客户区
    ↓ 按 current_dpi_ 换算物理像素
当前窗口 GWL_STYLE / GWL_EXSTYLE
    ↓
AdjustWindowRectExForDpi（Win10+ 可用时）
    ↓ 若系统没有该 API
AdjustWindowRectEx（兼容回退）
    ↓
得到“客户区 + 标题栏 + resize frame”的最小外框宽高
    ↓
WM_GETMINMAXINFO.ptMinTrackSize
```

关键原因：`WM_GETMINMAXINFO` 的 `ptMinTrackSize` 表示**整个顶层窗口**的最小追踪尺寸，而用户指定的 `1024×640` 是内容布局所需的客户区。如果直接写 `1024×640`，标题栏和边框会吃掉一部分客户区，实际可用内容会小于目标值。

默认窗口尺寸也调用**同一个最小外框换算函数**，然后在当前工作区居中。因此：

```text
默认尺寸 == 最小尺寸
```

用户可以继续放大窗口，也可以缩回默认大小，但不能再缩进截图中那种会把 GUI 挤坏的极端尺寸。

### 0.4 缩放残留的真正修复

#### 0.4.1 dev4 为什么仍可能残留

dev4 的主窗口在 `WM_SIZE` 中做：

```text
layout_main_();
InvalidateRect(parent, NULL, TRUE);
UpdateWindow(parent);
```

但 `layout_main_()` 内部对子控件调用的 `MoveWindow(..., TRUE)` 会让**每个子窗口在移动过程中各自立即请求重画**。当五个主要子控件依次移动时，父窗口和不同子窗口会在不同中间几何状态下交替绘制。连续拖动窗口边缘时，这种“边移动边单独重画”的顺序很容易让旧位置暴露区域、列表边线或 footer 像素没有在同一轮绘制中被统一擦除。

因此 dev4 的问题不是单纯“刷新不够快”，而是**布局变化与父子窗口重画没有作为一个完整批次完成**。

#### 0.4.2 dev5 最终刷新顺序

dev5 把主窗口布局阶段统一改成：

```text
1. 计算全部新矩形；
2. MoveWindow(child, ..., FALSE)；   // 只移动，不让每个子控件马上各画各的
3. 所有子控件几何位置稳定以后；
4. RedrawWindow(
       parent,
       NULL,
       NULL,
       RDW_INVALIDATE |
       RDW_ERASE |
       RDW_ALLCHILDREN |
       RDW_UPDATENOW
   );
```

这些标志的职责分别是：

- `RDW_INVALIDATE`：让需要更新的区域失效；
- `RDW_ERASE`：要求父窗口背景被重新擦除，旧卡片/边框/footer 像素不能原地保留；
- `RDW_ALLCHILDREN`：把所有子窗口也纳入同一轮重画，而不是只更新父窗口；
- `RDW_UPDATENOW`：立即完成本轮绘制，不等拖动结束以后再慢慢处理。

`WM_DPICHANGED` 也复用同一套“先布局、后父子完整重画”路径，避免 DPI 改变时产生同类旧像素问题。

这意味着 dev5 同时做了两件独立的事：

- **最小尺寸**负责明确 GUI 支持范围；
- **完整父子重画**负责真正清理缩放残留。

两者不是互相替代关系。

### 0.12 本轮失败方案/踩坑

#### dev4：取消最小尺寸 + 只刷新父窗口

这条路线已经被用户实机截图否决。问题包括：

- 可以把工具窗口缩进布局根本不需要支持的极小范围；
- `InvalidateRect(parent)+UpdateWindow(parent)` 没有把所有子窗口移动和重画统一成一个批次；
- 因此既存在布局压坏，也仍可能出现旧子窗口区域残留。

后续不得再把它描述为当前正确方案。

#### 交叉构建：直接接受 x86 stdcall 装饰名

当前 Linux/Clang 交叉构建过程中曾出现一次临时失败：x86 clang 对 Windows stdcall 外部符号产生 `__imp__Function@N` 形式，而简单生成的导入库提供的是未装饰导入符号。若直接让 PE 导入表保留装饰名，Windows API Import-by-Name 就会不正确，包内检查器也会失败。

最终使用链接器 `/alternatename` 把编译器侧装饰引用映射到真正的未装饰 Windows 导入名，最终 PE Import Table 已恢复为正常 API 名。这个仅是当前容器重建候选时的工具链踩坑；Windows 正式 `build.bat + MSVC + Windows SDK` 不需要该交叉构建兼容层，也没有把临时导入库/资源对象作为用户工具塞进包里。

### 0.4 dev4 缩放残影根因与最终修复

#### 0.4.1 用户实机症状

用户把主窗口缩小时，截图出现：

- 左右卡片旧边框重复残留；
- 列表旧位置的横线大量叠加；
- footer / 按钮区域旧背景没有及时清除；
- 视觉上像窗口内容被连续“拓印”在客户区。

这不是 Mod 数据模型损坏，也不是列表尺寸计算真的需要一个固定下限，而是窗口连续缩放期间父窗口的旧像素没有及时擦除/重画。

#### 0.4.2 曾考虑但最终明确放弃的方案

一开始根据截图曾考虑使用：

```text
WM_GETMINMAXINFO
ptMinTrackSize
```

把主窗口最小尺寸固定成默认尺寸。这个方案可以避免用户把窗口缩到容易暴露残影的范围，但它只是绕开症状，并且会不必要地剥夺自由缩放。

用户随后明确指出：**实测只是窗口没有实时刷新，拖动后立刻刷新就行，不用锁尺寸。**

所以 dev4 最终源码中没有上述最小尺寸限制；检查器还会反向检查，防止后续维护者误把这个已经被否决的方案加回来。

#### 0.4.3 最终代码路径

主窗口收到 `WM_SIZE` 时现在按以下顺序处理：

```text
layout_main_();
InvalidateRect(hwnd, NULL, TRUE);
UpdateWindow(hwnd);
```

逐步含义：

1. `layout_main_()` 先按照最新客户区尺寸重新计算并移动所有子控件；
2. `InvalidateRect(..., TRUE)` 把整个父窗口客户区标记为需要重画，并要求背景也失效，旧位置留下的卡片/分隔线/footer 像素会被清掉；
3. `UpdateWindow()` 不等消息循环以后某个空闲时刻，而是立即处理当前需要的绘制；
4. 因此用户**按住鼠标继续拖动窗口边缘时**就能看到连续更新，不必等松开鼠标后才恢复。

设置窗口本身没有用户报告同类问题，所以本轮只对主窗口修这个根因，不扩大修改面。

### 0.5 dev4 RPG.ico 资源链

```text
   ↓ cl.exe
```

`build.bat` 会先检查 `rc.exe` 是否可用，再生成 `launcher.res`，并把它加入 Launcher 链接。这样资源管理器文件图标、Windows 图标资源和程序运行时标题栏图标都来自同一份用户提供的 `RPG.ico`。

### 0.6 为什么图标没有破坏静态依赖边界

项目长期要求 Launcher 静态导入保持：


GUI 所需 USER32/GDI32 API 本来就是运行时动态解析，所以 dev4 没有因为设置窗口图标就直接静态链接 `user32.lib`。

`LoadIconW` 继续通过现有动态 USER32 装载框架解析，并在窗口类注册时把资源 101 加载为：

```text

```

因此：

- EXE 本身有 RT_ICON / RT_GROUP_ICON 资源；
- 标题栏/任务切换可使用该图标；
- Launcher 的 PE Import Table 仍不新增 USER32.dll 静态项。

4. **“文件缺失的mod旁边加个移除按钮”**
   - dev3 在 `present=0` 的缺失条目右侧显示小型 `移除` 按钮；
   - 该按钮只清理 `mods\mods.ini` 中已经陈旧的引用，**绝不删除磁盘文件/目录**；
   - 配置层再次检查 `present=0`，不能仅靠 GUI 是否显示按钮作为安全边界。

### 0.3 dev3：ASI / Overrides 显式拖动排序

底层排序架构继续使用已存在的：

```text
LauncherModConfig_Move(mods_root, kind, from_index, to_index)
```

并保持以下语义：

- 只能在同一类型内部排序，ASI 不会拖进 Overrides，反之亦然；
- ASI 从上到下依次加载；
- Overrides 越靠下，覆盖优先级越高；
- 修改后立即原子保存 `mods.ini`；
- 重复有效键等既有保护不因 GUI 改造而取消。

本轮新增“可发现性”与反馈：

- 行内固定绘制三条短横线作为拖动把手，不依赖字体特殊 glyph；
- 鼠标按下行的普通区域即可开始潜在拖动，把手是明确视觉提示，不强迫用户只能精准点 22 DIP 小区域；
- 复选框区域继续只负责启停，不误触拖动；
- 缺失项的 `移除` 按钮区域也不会启动拖动；
- 按下后超过 4 DIP 阈值才进入拖动；
- 进入拖动后把手转为强调色，并继续显示插入线；
- `SetCapture` 保证鼠标在拖动中短暂离开 ListBox 仍能正常结束操作；
- ASI 卡片副标题固定为 `从上到下加载  ·  可拖动排序`；
- Overrides 卡片副标题固定为 `越靠下优先级越高  ·  可拖动排序`。

### 0.4 dev3：缺失 Mod 的安全“移除”入口

新增配置 API：

```text
LauncherModConfig_RemoveMissing(mods_root, kind, index)
```

安全边界：

1. GUI 只有在 `item.present == 0` 时才绘制行尾 `移除`；
2. 配置层收到调用后**再次**检查 `present == 0`；
3. 如果磁盘对象实际仍存在，函数拒绝执行；
4. 成功操作只删除目标类型 section 中同名的有效配置键；
5. 不调用 `DeleteFileW` / `RemoveDirectoryW`，不删除任何 Mod 实体；
6. 若历史配置里同一个类型下存在多个同名有效键，会一次清掉全部同名键，避免“第一条删掉、第二条马上重新接管，看起来像没删”；
7. 保存继续复用原有 `同目录临时文件 → Flush → MoveFileEx 原子替换` 路径；
8. 原子保存失败时回读磁盘配置，避免内存模型假装删除成功；
9. 成功后重建模型并刷新存在性，不顺便登记其它尚未“重新扫描”的新文件。

行布局为：

```text
[复选框] [三横线拖动把手] Mod 名称 ........ [文件缺失] [移除]
```

存在且正常的 Mod 不显示 `移除`，因此这个按钮不会变成普通“卸载/删文件”功能。

### 0.12 截至 dev3 的失败方案 / 禁止回退项

除后文完整历史失败记录外，本轮新增/强化：

1. **不可把“底层支持拖动”当成 GUI 已支持拖动**：dev2 有底层拖动但用户仍明确认为没有排序能力，说明可发现性本身就是功能的一部分；
2. **不可恢复没有视觉把手/文字提示的隐藏交互**；
3. **不可把设置页每一个简单开关做成大卡片**：用户已经指出会压框且不利于后续增加功能；
4. **不可给缺失项的“移除”按钮加入磁盘删除语义**：当前动作定义严格是配置清理；
5. **不可只删第一条同名配置键**：历史重复键会让下一条马上接管，必须一次清理同类型全部同名有效键；
6. **不可因 GUI 便利绕过配置层安全检查**：即使 GUI 只给缺失项显示按钮，API 仍必须自己验证 `present=0`；
7. **不可因增加 GUI 功能引入新的静态 USER32/GDI32 依赖或重量级 UI 框架**；
8. **不可把 Linux 容器中的交叉构建冒充 Windows MSVC 正式构建**；
9. **不可用静态检查结果冒充实际 Windows DPI/拖动/视觉验收**。

### 0.7 当前 PE32 候选与交叉链接踩坑

当前容器没有完整 Visual Studio / Windows SDK，正式 `build.bat` 仍应在 Windows Visual Studio x86 Native Tools 下执行。

- 直接用临时 `.def` 生成的 x86 import library 会让最终 PE 出现 `_CreateFileW`、`_NtOpenFile` 这种**带前导下划线的错误 Import-by-Name**；这类 PE 即使“链接成功”也不能当 Windows 可运行候选；
- 因此该方案正式判失败，未进入交付包；
- 最终临时短导入对象使用 `IMPORT_NAME_NOPREFIX` 语义并逐项复核最终 Import Table，确保导入名是 `CreateFileW`、`NtOpenFile` 等真实未装饰 Win32/NT 名字；
- 这些临时链接辅助只存在构建工作目录，最终 ZIP 不携带。

## 三、Mod 目录硬规则

### 3.1 ASI

唯一目录：

```text
mods\asi\
```

`mods.ini`：

```ini
[ASI]
NoCD=1
BUGFix=1
AnytimeSave=1

```

规则：

1. 左侧写裸文件名，不写 `.asi`；
2. 从上到下就是实际 LoadLibraryW 顺序；
3. `1` 启用，`0` 禁用；
4. 新发现项只追加到末尾并默认启用；
5. Loader 不重排既有项目；
6. 暂时缺失项不擅自删除。

v0.2.7 这次日志发现了 4 个 ASI，但由于 Locale 文件自检在 ASI 加载之前失败，因此不能把“发现 4 个”误写成“4 个均已成功加载”。

### 3.2 Overrides

唯一目录：

```text
mods\overrides\<Mod名>\
```

保持游戏原相对路径。

优先级：`[Overrides]` 越下面越高。

安全边界：只重定向读取型 `OPEN_EXISTING`；任何写入、新建、覆盖、存档、配置写入都走游戏原目录。

### 3.3 模板

```text
mods\overrides\模板_复制后改名\
```

永久排除：

- 不写配置；
- 不参与覆盖；

## 六、总体启动架构

```text
CastleModLoader.exe
    ↓ CreateProcessW(CREATE_SUSPENDED)
RPG.exe（挂起）
    ↓ 仅修改目标进程内存 PE Import Directory
CastleLocaleBootstrap.dll
    ↓
CastleModCore.dll
    ↓
RPG.exe 原静态依赖
    ↓
ResumeThread
```

### 6.1 为什么不用普通远程线程 LoadLibrary

目标是让 CP950/NLS 环境尽可能早于 KERNEL32 和游戏业务建立。普通“进程启动后远程线程 LoadLibrary”已经太晚，因此采用双 Early Import，把 LocaleBootstrap 和 Core 放进正常 Loader 装载图。

### 6.2 磁盘 RPG.exe 不修改

Import 扩展只发生在挂起目标进程的内存映像，磁盘 RPG.exe 保持原文件。

## 七、Locale Bootstrap：pre-Kernel32 CP950

`CastleLocaleBootstrap.dll` 静态依赖严格只有 ntdll。

主要流程：

```text
读取/映射 c_950.nls、l_intl.nls
        ↓
RtlInitNlsTables
        ↓
RtlResetRtlTranslations
        ↓
写 PEB.AnsiCodePageData
写 PEB.OemCodePageData
写 PEB.UnicodeCaseTableData
```

历史踩坑：

- 不能把 `NLSTABLEINFO` 中内部观察字段是否等于 950 当启动硬门槛；不同 Windows 布局/语义可能使该字段为 0；
- v0.2.4 已因此改成只记录诊断值，不作成功标准；
- 成功标准看实际 PEB 指针和后续真实 GetACP/GetOEMCP/实体文件行为。

Bootstrap DllMain 始终返回 TRUE，把详细状态保存给 Core，避免 Locale 失败被 Windows Loader 折叠为难诊断的 `0xc0000142`。

## 十一、v0.2.7 文件名硬验收：决定性失败证据

### 11.1 设计目的

此前“标题栏正常”“GetACP=950”都不足以证明真实文件 API 能处理 Big5 文件名，所以 v0.2.7 增加两级硬自检。

### 11.2 实机结果

用户 Windows 实机日志：

```text
[Locale/NLS自检] 真实 GetACP=950
[Locale/NLS自检] 真实 GetOEMCP=950

[Locale/文件自检 1/2] PASS：真实 CP_ACP 已把预置 Big5 原始字节精确转换为预期繁体 Unicode 文件名。

[Locale/文件自检 2/2] FAIL：真实 CreateFileA 无法用 Big5 ANSI 文件名打开同一个 Unicode 实体文件，Win32错误码=2

[致命] CP950 文件名实体自检失败；拒绝进入 RPG.exe，避免繁体资源文件在半转区状态下随机读取失败。
```

### 11.3 这排除了什么

已经排除：

- RPG.exe 根本没创建；
- LocaleBootstrap 完全没工作；
- GetACP/GetOEMCP 只是 Loader IAT Hook 假返回；
- 普通 `MultiByteToWideChar(CP_ACP)` 仍用宿主 ACP；
- 只是标题栏/UI 层视觉问题；
- ASI 导致启动失败（失败发生在 ASI 放行前）。

### 11.4 新根因模型

系统 DLL 可能在 Bootstrap 切换 PEB/NLS 以前已经缓存一份宿主代码页 `CPTABLEINFO`。

于是：

```text
公开 ACP / 普通 CP_ACP = 950
但 CreateFileA 内部某段 A→W thunk 仍携带旧 CPTABLEINFO
→ Big5 文件名字节被按错误表转换
→ Unicode 名称不等于磁盘实体
→ ERROR_FILE_NOT_FOUND
```

这个模型与成熟 Locale Emulator Core 对 `RtlCustomCPToUnicodeN` 的处理方向一致，因此 v0.2.8 转向补齐这一层。

## 十二、v0.2.8 核心新增：CPTABLEINFO 修复层

### 12.1 目标函数

运行时从 ntdll 导出表动态取得：

```text
RtlCustomCPToUnicodeN
RtlInitCodePageTable
```

ModCore 因此仍然不新增静态 ntdll 导入，最终 PE 静态依赖继续只有 KERNEL32。

### 12.2 修复逻辑

`Hook_RtlCustomCPToUnicodeN_`：

```text
收到 custom_cp
    ↓
NULL? → 直接原函数
CodePage==65001? → 保持 UTF-8 特例
CodePage==950?   → 已正确，不动
其它 CodePage    → 认为是陈旧宿主表候选
    ↓
获取最小自旋锁
    ↓
再次检查 CodePage
    ↓
读取当前 PEB+0x58 = AnsiCodePageData
（Bootstrap 已切到 c_950.nls）
    ↓
RtlInitCodePageTable(目标 CP950 原始表, 同一个 CPTABLEINFO)
    ↓
修复计数 +1
    ↓
释放锁
    ↓
调用 Windows 原始 RtlCustomCPToUnicodeN
```

重要边界：

- 不自己实现 Big5 映射算法；
- 不把每个 CreateFileA/FindFirstFileA/CRT API 一个个硬改成 W；
- 修的是共用底层代码页表，让最终走该 ntdll 转换原语的 ANSI 路径共同受益；
- UTF-8 表不强行改成 950。

### 12.3 并发

`CPTABLEINFO` 可能是共享缓存。使用 x86 `lock cmpxchg` 最小自旋锁；抢锁后二次检查，避免两个线程重复初始化同一表。

### 12.4 普通函数 trampoline 安全性

`RtlCustomCPToUnicodeN` 不是固定 syscall stub，所以绝不盲切 5 字节。

v0.2.8 增加保守 x86 入口解码器：

- 逐条计算完整指令长度；
- 总长度至少 5；
- 最多 16 字节；
- 明确支持普通 prologue 常见指令；
- 相对 CALL/JMP/Jcc 直接拒绝；
- 0x67 16 位地址模式拒绝；
- 未识别 opcode 拒绝；
- 无法证明安全就 fail-closed。

日志会明确：

```text
[Locale/Native错误] 普通 ntdll 函数入口无法安全解码，拒绝 Hook：RtlCustomCPToUnicodeN
```

这比为了“兼容所有 Windows”盲覆盖未知机器码安全。

### 12.5 诊断计数

实体文件自检后记录：

```text
[Locale/Native] 本次启动已修复的陈旧 CPTABLEINFO 次数=N
```

`N` 只提供根因证据；最终门槛仍是 CreateFileA 实体文件自检。

- 只读 `OPEN_EXISTING` 才允许替换；
- 写路径绝不重定向；
- v0.2.8 的 ntdll NLS 修复不改变 Overrides 逻辑；
- 实机 Big5 验收会区分“系统真实 CreateFileA 成功”和“Override Unicode 替代成功”。

## 十七、失败方案与踩坑累计

### 17.1 Proxy Loader 历史

代理 DLL 路线无法保证 Locale/NLS 足够早，已放弃为主架构。

### 17.2 v0.1：栈/入口探测式 PreLoader

启动时序和入口稳定性不足，放弃。

### 17.3 v0.2：相对路径重复拼接

Launcher/Core 路径语义不统一，曾出现路径重复。后续固定同目录相对路径模型。

### 17.4 v0.2.1：代码 Mod 相对加载错误 126

ASI 相对路径与目标进程 DLL 搜索目录不正确。后续固定 `mods` 搜索目录并使用相对 LoadLibraryW。

### 17.5 v0.2.2：转区假成功

公开 API/标题表现不足以说明真实 NLS 环境成立，推动 pre-Kernel32 Bootstrap。

### 17.6 v0.2.3：普通 Core 内重建真实 NLS 导致初始化失败

NLS 重建发生太晚；拆出 ntdll-only LocaleBootstrap。

### 17.7 v0.2.4：内部 NLS CodePage 字段过严导致假失败

观察字段可能为 0，不应作为真实运行态门槛。改成诊断值。

### 17.8 v0.2.5：真实 ACP/OEM=950 但仍不等价完整区域环境

推动 Native Locale/UI/TEB/时区/Registry、USER32、GDI 补全。

### 17.9 v0.2.6：视觉/公开 API 成功仍没有文件级证据

推动 v0.2.7 实体文件 A/W 硬验收。

### 17.10 v0.2.7：GetACP=950 + CP_ACP 转换正确，但 CreateFileA 仍 FAIL

这是当前最关键历史失败：

```text
文件自检 1/2 PASS
文件自检 2/2 FAIL
ERROR_FILE_NOT_FOUND(2)
```

说明系统 DLL 内部陈旧 `CPTABLEINFO` 不能被公开 ACP 结果代表。v0.2.8 因此对齐 LE Core 的底层转换表修复行为。

### 17.11 当前禁止回退的错误思路

- 不能因为 GetACP=950 就宣布转区完成；
- 不能因为标题栏繁体正常就宣布转区完成；
- 不能用 Overrides 的 Unicode 打开成功冒充真实 CreateFileA 成功；
- 不能关闭 v0.2.7 fail-closed 门槛“先让游戏跑起来”；
- 不能盲切未知 ntdll 函数前 5 字节；
- 不能把历史 Oracle SHA 再写成当前用户 EXE 精确 SHA。

## 十八、Locale Emulator 研究与实现边界

用户在 v0.2.7 失败后明确要求：如果局部修补不稳，保险起见按 Locale Emulator 完整复刻。

当前执行解释：

> 对本游戏固定 x86 单进程 zh-TW/CP950 Profile 真正涉及的 Locale Emulator Core 运行语义继续按成熟实现对齐，而不是继续只补表面 API；但保留本项目架构，不把 LE GUI/Shell/其它语言 Profile/异常转储等无关产品功能搬进来。

本轮官方行为研究确认重点：

- NLS 表初始化/重置/PEB 数据指针；
- `RtlCustomCPToUnicodeN`；
- `RtlInitCodePageTable`；
- 遇到不是 UTF-8、也不是目标 ACP 的陈旧 `CPTABLEINFO` 时，用目标 ANSI NLS 表重新初始化该结构。

本项目是独立重写，不直接复制/分发 LE Core 实现源码或 DLL。

如果 v0.2.8 Windows 实机仍失败，下一步继续对照 LE Core 实际执行链找剩余差异，而不是退回“多 Hook 几个 GetLocaleInfoA”式试错。
