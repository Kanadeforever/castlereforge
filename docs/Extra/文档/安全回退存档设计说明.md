# 《幽城幻剑录》v0.3.2 / AnytimeSave 安全回退存档设计说明

> v0.3.2 没有改动 v0.3.1a 已验证的安全回退算法；本轮功能变化只发生在 BUGFix.asi（合并稳定 CrashFix test2）。AnytimeSave 的 3 个 Hook、fallback 规则与 TSF 兼容策略保持不变。

> 2026-08-28 起，正式功能源码位于 `src/SaveEnhance`，不再位于 `src/Extra`。先前 Probe 工具未随当前源码目录继续保留，但这次目录整理没有修改本说明中的任何算法结论。

## 1. 为什么不再追 TSA

v0.3.0-dev1～dev3 曾尝试“原版 TSF + 独立旁挂文件”的精确恢复架构：

- dev1：`.YCS`；
- dev2 起改名 `.TSA`（TS追加）；
- dev2：TSA 任务只排队，保存菜单期间没有可靠后续 Map Tick 执行机会；
- dev3：Writer 返回后立即第一次真实 I/O，用户日志得到 `Win32 错误码=2`，即 `ERROR_FILE_NOT_FOUND`。

这说明插件构造的 TSF 文件路径与游戏自己的文件系统实际写盘位置并不一致。继续做下去需要进一步逆向原版文件系统/路径解析，不再是当前“先得到安全可用随时存档”的最短路线。

同时，dev1 已经实机证明：即使没有任何旁挂文件，只要把 TSF 的场景恢复头规范化到入口级安全状态，磐沙堡楼梯坏档就能变成正常可读档。

因此 v0.3.1a 正式删除 TSA/YCS 正式链，只保留已经得到实机正向结果的 vanilla fallback。

## 2. 原版为什么会坏档

旧随时存档把 `0x40A0C0` 的场景存档许可强制改为返回 1。

原版 TSF 能保存大量持久状态，但不是完整运行时快照。已经闭合的一条缺口是：

- Map SCI byte0 在载图时初始化 `scene_container+4`；
- EVE opcode `0x3D` / `0x40DA50` 可以在运行中动态改写 `scene_container+4`；
- `0x40AE50` 按该 index 选择 `runtime_array + index*0x38`；
- 原 TSF 没有独立保存这个动态 selected Map runtime index。

因此可能出现“保存的 X/Y 属于 mode 1，但读档重新载图先回到默认 mode 0”的不一致，楼梯/多层场景尤其容易暴露。

## 3. 当前原则（自 v0.3.1a 固化）

### 3.1 原版允许：完全原版

先调用 RPG.exe 自己的 `0x40A0C0`。

如果原版返回非 0，插件直接返回原值；不检查地点名、不检查 Event flag、不建立扩展授权，也不修改 Writer 数据。

### 3.2 原版拒绝：只看有没有可靠 fallback

不再维护：

- “新图”黑名单；
- 纯数字地点名黑名单；
- deferred Event 总门；
- VM blocked 总门；
- entity transition 总门；
- 楼梯地图名单。

唯一核心条件是：当前地图是否已经冻结一份 default Scene Mode 下真实运行过的入口级 vanilla fallback。

### 3.3 fallback 如何冻结

每张地图 runtime 身份变化后重新开始：

1. 只在 `selectedIndex == defaultIndex` 时采样；
2. 原版 Map Tick 先执行，插件后观察；
3. 连续稳定 8 Tick；
4. 固化这段稳定窗口的第一个样本；
5. 这张地图生命周期内不再更新锚点。

这样锚点优先靠近场景入口，而不会随着玩家继续走到楼梯/传送边缘。

## 4. 为什么是 200-byte World header

当前 EXE 已确认：

- World 长度为 `0x27D8`；
- `0x00C8` 之前是 200-byte scene restore header；
- `0x00C8` 之后才开始 5000 个 `int16` GameVar。

因此 fallback 只回退前 200 bytes。

这样可以把：

- Scene Descriptor；
- 原版恢复所需的场景头；
- 受控角色 X/Y/state/index；

放回一个真实稳定时刻，同时不把后续获得的剧情 GameVar 整体倒退到入口。

## 5. Writer 期间怎样保证游戏本身不被移动

插件不直接移动 live actor。

Writer Hook 只做：

```text
备份当前 World[0..0xC7]
→ 临时覆盖为 frozen fallback header
→ 调原版 0x43B360
→ 恢复原 World[0..0xC7]
```

所以修改只存在于“原版 Writer 看见的快照”中。

## 6. fail-closed

如果扩展存档已经被菜单允许，但到真正 Writer 时出现任一情况：

- 地图身份已经变化；
- fallback 与当前地图不再匹配；
- runtime manager 的 World 长度/指针异常；
- World 200-byte 范围不可读；

插件直接让本次扩展保存失败，不会退回旧的“把当前位置硬写进 TSF”。

原版本来允许的存档不受这条规则影响。

## 7. 能保住什么，不能承诺什么

当前目标是“保进度”，不是“精确快照”。

原版其它存档块仍保存当前角色、队伍、道具、GameVar 等进度；场景恢复位置则用较早的安全锚点。

不能承诺：

- 原版所有禁止场景都一定能在 8 Tick 后开放；
- 任意剧情瞬间都不存在新的 fallback 反例；
- 战斗中任意帧保存；
- 读档回到按保存键时的精确坐标。

一旦发现“使用当前 fallback 仍会形成坏档”的新场景，应作为新的反例继续研究，而不是放宽 fail-closed。
