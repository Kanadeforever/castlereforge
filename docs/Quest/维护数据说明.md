# Castle_Quest dev6zd 维护数据说明

## 1. 运行目录

任务运行数据固定为 ASI 同目录下：

```text
Castle_Quest/
├─ manifest.toml
├─ Q001_main_story.toml
├─ Q001_main_story_addon.toml
├─ ...
├─ Q025_supp_affection.toml
└─ Q025_supp_affection_addon.toml
```

共 51 个 TOML、0 子目录；没有 `routes.toml`。

## 2. Manifest

当前必须是：

```toml
format_version = 7
database_version = "research-v0.6+dev6zd-runtimesdk-migration"
quest_count = 25
addon_count = 25
stage_count = 146
canonical_stage_count = 146
```

这些数字不是手写参考值，而是必须和实际文件机械一致。以后增加/删除 Base Stage 或任务文件时，必须同时更新 Manifest 并重新统计。

Manifest 不再包含：

```text
warning_count
guidance_stage_count
```

因为两套运行机制都已经退役。

## 3. Base v7

Base 是原版任务事实层：

```toml
format_version = 7

[quest]
quest_id = "..."

[[stage]]
stage_id = "..."
when = "..."
```

Base v7 不再存在 `stage_type` 字段；任何 Base `[[stage]]` 都天然表示原版真实 Stage。人工提示、人工调查步骤、为了 HUD 体验虚构的阶段都不能写进 Base，必须使用 Addon `[[insert]]`。

`condition_status / evidence / reads_var / writes_var / stage_result / notes` 等研究字段可以继续存在，因为详细 Base 同时承担可审计原版研究结果，但这些字段不能被普通体验修改误当成第二套推进逻辑。

## 4. Addon v2

Addon 是 Remastered 体验层：

```toml
format_version = 2

[addon]
quest_id = "..."
```

主要操作只有两类：

```text
[[override]]  覆盖已有 Base Stage 的明确字段
[[insert]]    在两个相邻 Base Stage 之间增加人工体验步骤
```

Base 与 Addon 的同义字段必须使用完全相同的名字，例如：

```text
stage_id
runtime_event
world_x
world_y
name
hint
```

不恢复 `id/event/marker_name/marker_hint` 这类第二套别名。

## 5. Insert 锚点

必须同时填写：

```toml
after = "base_stage_a"
before = "base_stage_b"
```

并且两者必须在 Base 中相邻。只给一个锚点、锚点不存在、顺序错误或中间已经隔着另一个 Base Stage，都应硬报错并保留上一份有效数据库。

人工阶段完成身份固定为：

```text
addon.quest_id + insert.stage_id
```

同 ID 表示同一个步骤；如果维护者故意把它改成完全不同的新体验，应主动更换 `stage_id`。

## 6. Q004 当前示例

Base：

```text
ask_mother -> world_trigger
```

Addon：

```text
ask_mother -> [investigate_aji_clues] -> world_trigger
```

旧 `optional_clues` 已从 Base 删除，因为孩子对话不是原版阿吉任务硬性推进链。

## 7. Warning 与 Guidance

当前运行格式均已取消：

```text
[[warning]]
stage_type = "guidance"
guidance_scene
```

旧研究文档可以讨论这些历史路线，但不能把它们重新写回现行 Base/Manifest/C++。

## 8. 原版任务链修正纪律

发现 Base 问题时必须回到原版证据验证，而不是用 Addon 掩盖。

典型例子 Q002：Event37 后 `find_doll.when` 成立，但 Quest 顶层 Active/Journal 旧条件没覆盖 `Var1007=1`。正确修复是补 Base 顶层真实状态域，而不是在 Addon 人工强行显示 `find_doll`。

用户提供的 `任务分析_0.1.5_原版事件空间数据` 是当前重要证据层；Scene/Event/Object/触发几何等修改应尽量与该数据及已有冻结研究互证。

## 9. 热重载

Ctrl+F8 是事务：

```text
读取 INI + manifest + 25 Base + 25 Addon
↓
全部解析/配对/校验成功
↓
一次提交
```

任何失败都继续使用上一套有效数据。

dev6zd 起成功热重载不清空进程内 Addon 完成集合，且不再根据 `Available/Unavailable` 自动擦除；在 `.state` 接入前，同一进程内完成键只增不减。

## 10. `.state`

本版没有 `.state` 读写实现。未来共享增强存档由主 SDK 统一负责 TOML 读写和跨模块协调；Quest 只保存原版 TSF 无法表达的自身新增状态，首先是 Addon Insert 完成集合。
