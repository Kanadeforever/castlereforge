## 1. 本轮解决的问题

v0.5 唯一任务状态硬缺口为 `Var25=2→3`。全游戏有效 EVE 中确实没有任何直接 `SET_VAR 25,3`，因此旧结论“EVE层缺失”本身没有错；真正原因是这一步根本不在 EVE。

## 2. Item460 证据

当前完整游戏 `public/Ail2.ENC` SHA-256：

```text
a24784316c2bd23fc2683637ab860c0e54f1b4175f6db990398843bd0a13c5d8
```

ItemID 460：

- 名称：羊皮封卷
- `record+0x20 = 460`
- `record+0x28 = 17`
- 说明：在沾染血氣之後，忽然浮現字跡圖樣的空白卷軸，其內容似乎藏有極重要的祕密....

## 3. 原版 EXE consumer

目标原版 `RPG.exe` SHA-256：

```text
8294839343b1a7845ddae31ed16216b05850efd39a742e5ca7701aadca97287f
```

`0x43AEC0` 的物品应用逻辑读取 Ail2 `+0x28`。值大于0时写入 `DataCenter+0xC4`，当前 ItemID 写入 `DataCenter+0xEC`。

`0x40CE23` 读取这两个字段，动作码17经 `0x40D110` selector 映射到 index7，再由 `0x40D0EC` jump table 进入 `0x40CFE4`。

`0x40CFE4` 的关键逻辑等价于：

```text
if GET_VAR(25) < 3:
    SET_VAR(25, 3)
```

地址：`GET_VAR=0x44B0D0`，`SET_VAR=0x44B0B0`。

## 5. 冻结结论

- 25 个正式 Quest 均不再存在“未知状态迁移”的硬阻塞。
- 146 个正式 Stage 的 `condition_status` 全部为 A。
- 主线 69 个真实 Var1 Stage、稳定条件 Route、失效警告继续保持 v0.5 已验证结论。
- 以后除非出现新的原版程序反证，否则任务状态语义不再作为常规开发变动对象。
