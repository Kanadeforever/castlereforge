# Castle_Quest v0.1-dev6zd 任务可见性与附加步骤规范

## 1. 唯一原则

Base 主任务 TOML 只解释原版游戏真实存在的任务状态。只要某个“步骤”不是原版推进链本身的真实阶段，就不能为了 HUD、Marker 或玩家体验而塞进 Base。

因此 dev6zd 起 Base v7 **不再保存 `stage_type` 字段**。只要一条记录位于 Base 的 `[[stage]]` 中，它就天然表示原版真实 canonical Stage；人工体验步骤只能写入 Addon。

旧 `stage_type="guidance"`、`stage_type="canonical"` 显式类型字段，以及专门绕过 Quest Active 的 Guidance 运行分支已经完全退役。

## 2. Base Stage 的显示条件

Base Stage 能成为当前目标必须同时满足：

1. 当前 Quest 被顶层 `active_when` 判定为 Active；
2. 当前 Stage 自己的 `when` 成立；
3. Stage 的 `show_in_journal`、Marker 可见性和场景物理绑定继续按各自规则处理。

这里不再有“Guidance 可以绕过 Quest Active”的特殊例外。

这条规则正是 dev6zc 彩石弹珠问题的教训：`find_doll.when` 本身正确，但旧 Q002 顶层 Active/Journal 漏掉 `Var505=1 && Var1007=1`，所以 Stage 被整个 Quest 状态挡住。当前 Base 已同时修正顶层 Active 与 Journal。

## 3. Addon Insert 是唯一人工体验步骤

Remastered 想让玩家额外完成的对话、调查、观察等步骤，一律写进同名 `_addon.toml` 的 `[[insert]]`。

示例：

```toml
[[insert]]
stage_id = "investigate_aji_clues"
after = "ask_mother"
before = "world_trigger"
objective = "向水井旁的孩子打听阿吉的消息。"
player_notes = ["水井旁的孩子也许知道阿吉去了哪里。"]
show_in_journal = true
optional = true
scene = "mp0101"
runtime_event = "33"
object = "聊天四小鬼之左"
world_x = "663"
world_y = "734"
```

`after` 与 `before` 必须同时存在，并且必须是 Base 中相邻的两个稳定 `stage_id`。不满足就整次 Addon/数据库事务失败，不能静默猜位置。

## 4. Q004 阿吉任务当前边界

旧版 Base 曾有：

```text
optional_clues
```

它把“孩子对话是线索”提升成一个 Base Stage，但原版实际上没有把四个孩子设成阿吉任务的硬性推进门槛，因此这种表达混淆了“原版事实”和“Remastered 体验设计”。

dev6zd 已把 `optional_clues` 从 Q004 Base 完整删除。Base 当前只保留原版真实链：

```text
ask_mother
↓
world_trigger
```

Addon 再把人工调查步骤插入：

```text
ask_mother
↓
[investigate_aji_clues]
↓
world_trigger
```

人工步骤完成仍只看真实 Event33 开始，不写 Var503/Var504，也不阻止原版剧情自行推进。

## 5. Q001 鸡汤阶段为什么仍在 Base

`guide_get_chicken_soup` 这个历史 `stage_id` 名字虽然带 `guide_`，但重新核对后它对应原版真实 Event18 和 Var1=0→1 的主线推进，因此它不是人工 Guidance。

dev6zd 保留稳定 `stage_id`，并保留真实原版条件：

```toml
when = "var[1] == 0"
```

Base v7 不再额外写 `stage_type`。同时把 Q001 顶层 Active/Journal 覆盖到 Var1=0。这是“保留原版真实阶段”，不是保留旧 Guidance 系统。

## 6. `optional` 字段仍然保留

退役的是 `stage_type="guidance"`，不是通用 `optional` 字段。

`optional=true` 仍可以表达某个 Addon 人工步骤不是原版剧情硬门槛；如果未来原版真实任务链本身存在可选 Stage，也可以在有原版证据时使用。它不能被解释成“允许 Base 虚构一个人工阶段”。

## 7. 热重载后的人工步骤状态

Addon Insert 的进程内完成身份固定为：

```text
quest_id + stage_id
```

dev6zd 起 Ctrl+F8 成功热重载不会再清空这组完成记录，而且不再因 Quest 暂时求值为 `Available/Unavailable` 就删除完成键。因此修改 Base/Addon 条件、文案、坐标、Marker 或其他字段，只要人工步骤 ID 不变，就仍然视为同一个已经完成的步骤。当前进程内完成键只增不减；同进程读取更早 TSF 的回滚留给未来 SDK `.state` 按真实存档身份处理。

跨游戏重启和跨 TSF 存档的完成状态仍未持久化；未来交由主 SDK 的共享 `.state` 服务处理。

## 8. 已退役的运行概念

当前运行格式不再存在：

```text
stage_type = "guidance"
guidance_scene
Guidance 特殊选段
Guidance 绕过 Active
Base 人工体验 Stage
[[warning]]
```

研究文档可以保留这些历史名词说明旧路线为什么失败，但运行 Base/Manifest/C++ 不得重新引入。
