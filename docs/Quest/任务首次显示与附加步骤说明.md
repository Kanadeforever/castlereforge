# Castle_Quest v0.1-dev6zd 任务首次显示与附加步骤说明

## 1. 首次显示由原版状态决定

Base 任务首次出现时，Quest 顶层状态与 Canonical Stage 必须来自同一套原版 GameState 事实。任务系统只解释原版，不通过自己写 GameVar 来“激活任务”。

Base Stage 的正常选择顺序是：

```text
先求 Quest 状态
↓
只有 Active Quest 才选择当前 Base Stage
↓
在 Base Stage 中查找 when 成立的真实阶段
↓
Addon 再对 Presentation 层做 override / insert
```

旧 Guidance 绕过 Active 的特殊路径已经删除。

## 2. Main Story 的 Var1=0

Q001 的 `guide_get_chicken_soup` 已确认对应原版真实 Event18 / Var1=0→1，因此 dev6zd 把它保留为 Base 的原版真实 Stage，并让 Q001：

```toml
active_when = "var[1] >= 0"
journal_when = "var[1] >= 0"
```

这样新游戏 Var1=0 时能正常显示原版真实第一阶段，而不需要 Guidance 特判。

## 3. Addon Insert 的首次显示

人工体验步骤只有在运行时 Presentation 链走到它的插入位置时才显示。

以 Q004 为例：

```text
Base:
ask_mother -> world_trigger

Addon:
after = "ask_mother"
before = "world_trigger"
```

当 Base 原版链已经完成/离开 `ask_mother`，但还处于进入 `world_trigger` 的过渡位置时，Addon 可以成为当前显示步骤。它不会把自己写成新的原版 GameVar 阶段。

## 4. 已经跨过去的人工步骤

当前 dev6zd 解决“同一游戏进程内 Ctrl+F8 热重载保留完成集合”，并采用完成键只增不减的临时规则。如果关闭游戏后重新载入 TSF，尚没有持久化 Addon 完成记录；如果同一进程直接读取更早 TSF，也不会自动回滚人工完成键。两种情况都必须由未来 SDK `.state` 的真实存档生命周期解决。

未来主 SDK `.state` 服务接入后，应以 TSF 为原版事实，以 `.state` 只保存原版无法表达的 Remastered 新增状态。旧存档第一次没有 `.state` 时，还需要根据原版当前进度抑制已经被 Base 链跨过去的人工 Insert，避免几十小时前的附加步骤重新弹出。

## 5. 不允许的做法

为了“让任务首次出现”不得：

- 新造 GameVar；
- 写回原版 TSF；
- 把纯 UX 步骤伪装成 Base `[[stage]]`；
- 恢复 Guidance 绕过 Active；
- 用 Addon 覆盖掩盖 Base 顶层条件本身写错的问题。

如果 Base Stage 条件成立但 Quest 顶层不 Active，应修 Base 的真实状态覆盖关系，Q002 `find_doll` 就是这种情况。
