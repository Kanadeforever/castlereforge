# Castle_Quest RuntimeSDK 迁移与增强状态规划

## 1. 本版实际接入范围

Castle_Quest v0.1-dev6zd 已迁入主项目 `src/Quest` / `docs/任务系统` 布局，并接入 RuntimeSDK Client 生命周期。

本版只接现在已经存在明确所有权冲突的部分：Quest 会修改 RPG.exe 两个固定函数入口，所以 Integrated 模式必须通过 Runtime Hook v1 的事务声明，而不能继续绕过 Runtime 自行写机器码。

当前两个入口：

```text
0x00409580 ExplorationUpdate
0x004064E0 Present
```

两者都是覆盖 6 字节函数开头的 E9 detour。在 Integrated 模式中作为同一事务的两个 `CastleExclusivePatchClaimV1` 提交，expected bytes 与 Standalone 版本护栏共用同一份常量。

## 2. 为什么没有把所有代码都“SDK 化”

RuntimeSDK 接入的目的不是为了形式上调用 SDK，而是统一跨插件资源所有权。

Quest 目前自己的这些业务仍保留：

- Base/Addon TOML 任务语义；
- 原版 GameState 只读解释；
- Marker 业务；
- Stage-local Route；
- Ctrl+F7/F8/F11；
- 软件 Overlay；
- Addon Insert 生命周期。

它们当前没有必须由 RuntimeSDK 接管的跨项目资源冲突，所以本版不为了迁移目录而重写。

## 3. 三种 Client 模式

### Integrated

Runtime 可用时：

```text
Client -> IntegratedInitialize
       -> Quest 初始化公共业务
       -> Query Hook v1
       -> BeginTransaction
       -> AddExclusivePatch x2
       -> Preflight
       -> Commit
```

Quest 不直接 VirtualProtect 两个 RPG.exe 入口。

### Standalone

完全不存在 `Castle_Runtime.dll` 时，Client 调用 Standalone。Quest 继续用已经实机验证过的私有 6 字节 E9 Hook，因此这个 ASI 仍可脱离主 Runtime 独立运行。

### Fault

Runtime 文件存在但无法安全工作时只进入 RuntimeFault。Quest 不允许把“坏 Runtime”伪装成“没有 Runtime”，因此不会在 Fault 下重新安装本地 Hook。

## 4. DllMain 边界

迁移后 DllMain 只做 RuntimeSDK Client 的装载期登记：

```text
PROCESS_ATTACH -> CastleRuntimeClient_OnProcessAttach
PROCESS_DETACH -> CastleRuntimeClient_OnProcessDetach
```

任务数据库读取、日志打开、INI、Hook 安装等业务都移到 Client 正式初始化回调以后，避免在 Loader Lock 内执行复杂工作。

`InitializeASI` 保留给传统加载器和两阶段 Client，只调用 `CastleRuntimeClient_RunNow()`，不自行判断模式或安装 Hook。

## 5. 稳定插件身份与导出

稳定插件 ID：

```text
org.castlereforge.quest
```

插件文件名可以变化，但 Runtime 资源所有权应始终认稳定 ID。

`CastleQuest.def` 固定：

```text
CastlePlugin_Query
InitializeASI
CastleRuntimeClient_NotifyLoaderReady
```

## 6. `.state` 本版不实现

用户已经确定：原版 TSF 必须 100% 保持原版兼容，Remastered 自己增加的游戏进度信息不能写进 TSF。

未来计划使用与 TSF 同名的共享增强状态文件：

```text
..\multimedia\save\Save001.TSF
..\multimedia\save\Save001.state
```

但 `.state` 不是 Castle_Quest 私有文件，而是整个 Remastered 的跨项目能力。因此本版明确**不在 Quest 里实现文件读写器**。

## 7. 未来 SDK 状态服务职责

主 SDK 未来应提供统一 TOML/状态服务，至少承担：

- TOML 标准解析与序列化；
- 当前 TSF 身份；
- 同名 `.state` 路径；
- 整个共享状态树的内存所有权；
- 每个插件的稳定命名空间；
- 多插件写入顺序和并发协调；
- 临时文件、Flush、原子替换；
- 格式版本与迁移；
- 未知模块字段保留；
- 新游戏、读取、保存、另存为生命周期。

Quest 未来只向 SDK 表达“读/写自己的状态”，不直接打开 `.state`。

## 8. Quest 未来首先需要的持久状态

只保存原版 TSF/GameState 无法表达的 Remastered 新状态。

当前第一项就是：

```text
Addon Insert completed set
key = quest_id + stage_id
```

Base Stage 完成状态、GameVar、Item、Scene 等原版能够恢复的内容不重复保存，避免 `.state` 变成第二套原版剧情存档。

## 9. dev6zd 的过渡行为

SDK 状态服务尚未存在，所以：

- Ctrl+F8 成功热重载：保留当前进程内 Addon Completion Set；
- 关闭游戏：该集合消失；
- 不创建 `.state`；
- 不修改 TSF；
- 将来接状态服务时，稳定键仍使用 `quest_id + stage_id`，因此现有 Addon 文件无需因持久化方案重写。
