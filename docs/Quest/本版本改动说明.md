# Castle_Quest v0.1-dev6zd 本版本改动说明

## 一、本版目标

本版把 Castle_Quest 从独立源码包布局迁到 CastleReforge 主项目布局，并只接入当前确实需要 RuntimeSDK 协调的游戏代码补丁所有权。同时清理旧 Guidance/人工 Base Stage 遗留，并修复 Addon 热重载完成状态被清空的问题。

## 二、目录迁移

旧独立包：

```text
src/source
src/templete
src/tools
```

新主项目位置：

```text
src/Quest/source
src/Quest/templete
src/Quest/tools
docs/任务系统
```

Quest 不复制 RuntimeSDK；构建时引用同级 `src/RuntimeSDK/include` 和 `src/RuntimeSDK/client`。

## 三、RuntimeSDK 最小正确接入

Quest 已注册稳定插件 ID：

```text
org.castlereforge.quest
```

Integrated 模式中，两处旧私有固定 E9 Hook：

```text
0x00409580 ExplorationUpdate
0x004064E0 Present
```

改为 Runtime Hook v1 同一事务中的两个 `ExclusivePatch`。Runtime 负责 expected bytes、冲突预检和提交所有权。

仍保留 Standalone；Runtime 文件存在但故障时只进入 Fault，不允许偷偷转私有 Hook。

DllMain 只登记 Runtime Client；业务初始化离开 Loader Lock。

新增 `CastleQuest.def`，固定导出：

```text
CastlePlugin_Query
InitializeASI
CastleRuntimeClient_NotifyLoaderReady
```

## 四、build.bat 迁移

新脚本从 `src/Quest/build.bat` 工作，沿用主项目通过 `vswhere + VsDevCmd -arch=x86` 建立 Visual Studio x86 环境的方式，但 Quest 本体使用 MSVC `cl + link + dumpbin`，并把 RuntimeSDK 三个 Client C 源编进同一 Quest ASI。

Quest 使用 C++17/STL，因此保持 `/MT /std:c++17` 静态 CRT；这与 Widescreen/RuntimeSDK 的纯 C、clang-cl/lld-link、`/NODEFAULTLIB` 构建路线是有意区分的，不能在文档里把两者写成同一工具链。

成功前所有对象都只在 `src/Quest/_build`；脚本不再清空整个根 `build/`，只在最终验证通过后替换 Quest 自己的：

```text
build/Castle_Quest.asi
build/Castle_Quest.ini
build/Castle_Quest/
```

主项目 `build_all.bat` 后续需要把数据目录和 ASI/INI 一起归入 `build/mods/asi`。

## 七、Ctrl+F8 保留 Addon 完成集合

旧代码在成功提交新数据库时清空 `g_completedAddonStageKeys`。这会导致只修改 TOML 文案/Marker 后，已经做过的人工步骤重新触发。

dev6zd 取消这次清空，并同时删除“Quest 回到 Available/Unavailable 就擦除该 Quest 人工完成键”的旧猜测式清理。当前进程内只要 `quest_id + stage_id` 不变，完成键只增不减；修改 Base/Addon 条件、文案、Marker 或坐标后热重载都不会间接复活同一人工步骤。

当前临时代价是：同一进程读取更早 TSF 时人工完成状态不会自动回滚。跨游戏进程、跨 TSF 的正确恢复必须等待主 SDK `.state` 服务按真实存档身份管理。

## 八、`.state` 只写规划，不实现

本版没有打开、创建或修改 `.state`。

未来原版 TSF 保持 100% 原版格式；Remastered 新增状态放同名 `.state`。由于它是跨项目共享能力，TOML 解析、共享内存树、写入顺序、事务和落盘应由主 SDK 统一协调，Quest 只调用状态接口。
