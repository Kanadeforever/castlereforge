## Castle Mod Loader 正式生命周期（test3 新硬前提）

当前 Loader 的 ASI 加载顺序是：

```text
LoadLibraryExW(ASI)
  -> DllMain 只做最小装载
  -> OverrideLoader_PatchModule
  -> LocaleLayer_PatchModule
  -> GetProcAddress("InitializeASI")
  -> 调用 InitializeASI()
```

所以 SaveEnhance 的机器码预检查与 Hook 安装从 test3 开始只允许在 `InitializeASI()` 内发生。`InitializeASI` 是否实际导出已经加入随包验证器的硬检查。


## test4 自动档文件路径尝试（已由实机判定仍失败）

原版 SaveSlot/Writer 构造并使用的是相对路径 `Save\Save%03d.TSF`。test3 的轮换查询错误地自行拼接 EXE 目录，实机表现为原版保存成功但轮换永远认为 91 空。test4 曾把 91~99 查询改成同样的相对字符串后交给 Windows 当前工作目录解析，但实机仍看不到原版已成功保存的 91；因此该方案已废弃，test5 改用下节的游戏 File 对象。

这条结论来自 test3 实机“连续自动存档全部槽=91”与原版存档路径调用链的联合复核，后续不得恢复 EXE 目录硬拼。


## test5 游戏 File 对象

| VA | 作用 | 关键调用语义 |
|---|---|---|
| `0x4416F0` | File ctor | `this=fileObject`, 栈参数 `1` |
| `0x441710` | File dtor | 释放内部路径并关闭 |
| `0x4417C0` | File Open | `path, mode, flags`；LoadSlot 使用 mode=1 |

原版 Writer/LoadSlot 都先构造 0x14 字节 File 对象再进入这套文件层。test5 的自动槽存在判断复用同一层，不再通过 Win32 路径推断。
