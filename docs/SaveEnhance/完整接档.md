用户对 test4 的实机日志确认：

1. **自动存档每次都报告槽 91**，连续多次场景切换仍没有使用 92~99；
2. **F5 Quick Save 确实收到输入，但每次日志都是 `原版 save gate 当前拒绝`，因此没有写 `Save000.TSF`**；
3. **F9 Quick Load 能成功走原版 LoadSlot(0)**，说明 Quick 输入、连按确认与 Load 链本身已经可运行；
4. **外置 WAV 已由用户确认能正常播放**。

### test4 修复 A：91~99 轮换使用原版相对路径语义

test3 自己判断自动档是否存在时，错误地用 `RPG.exe` 所在目录拼成绝对路径：

```text
<EXE目录>\Save\Save091.TSF
```

重新对照原版 `0x43B320 -> 0x43B360`，游戏真正交给文件层的是：

```text
Save\Save091.TSF
```

即**相对于进程当前工作目录**。启动器/Mod Loader 可以让工作目录与 EXE 目录不同，因此会出现“原版保存成功，但 test3 的轮换检查永远看不到文件”，于是每次都把 91 当空槽。

test4 删除 EXE 目录拼接，`游戏 File::Open` 直接检查与原版 Writer 相同的 `Save\SaveNNN.TSF` 相对路径。保存成功后还会立刻用同一语义复查；如果仍看不到文件，会输出 `[自动存档诊断]`，不再静默假装轮换正常。

### test4 修复 B：Quick Save 可以使用已经闭合的安全 fallback

test3 把 Quick Save 额外限制成“严格自由行动 **并且** 原版 save gate 必须返回允许”。实机证明这个假设错误：游戏即使处于我们的严格自由行动门，原版 gate 仍可能返回 0。

test4 仍然保留严格自由行动门，所以剧情、战斗、菜单、楼梯 transient 等状态不会进入 Quick Save；但如果：

- 当前确实是严格自由行动；
- 同一地图已经连续 8 个严格自由 Tick；
- 当前地图已经冻结安全锚点；

那么原版 gate=0 时允许给下一次 Writer 装入**当前地图安全 fallback**，再调用原版 SaveSlot(0)。没有锚点时仍立即失败，不排队。

### test4 新增：SaveEnhance 外置 WAV 独立音量

```ini
[Sound]
Volume=70
```

- `0`：静音；
- `1~99`：只读外置 WAV 到私有内存，对 **PCM 8/16/24/32-bit（含 extensible PCM）** 样本按百分比缩放，再 `SND_MEMORY` 异步播放；
- `100`：不解析 WAV，直接让 Windows 按原文件播放，因此保留 Windows 自身支持的其它 WAV 编码；
- 默认 `70`；
- 音量处理只影响 SaveEnhance 提示 WAV，不改游戏音量、不改 Windows 总音量；
- `Volume<100` 遇到不支持的压缩/float WAV 时静默禁用该文件，推荐自行准备 16-bit PCM WAV。

## 1. 本版本最终功能定义

### 槽位

```text
0       = Quick Save，只允许快捷存档写，普通存档菜单只读
1~90    = Manual Save，普通菜单正常读写
91~99   = Rolling Auto Save，共 9 代，普通存档菜单只读
```

整个存档页面从原版 32 槽扩成：

```text
25 页 × 每页 4 行 = 100 槽 = 0~99
```

### 快速存档/读档

```text
F5              = Quick Save -> Save000.TSF
F9 连按 N 次     = Quick Load <- Save000.TSF
RB + R3          = Controller Quick Save
RB + Start       = Controller Quick Load 请求
```

`QuickLoadPresses` 默认 2，可设 2 或 3；默认确认窗口 1200ms。

键盘与 Controller 共用同一个 Quick Load 确认状态机，例如第一次按 F9、第二次按 RB+Start，也会完成两次确认。

### 自动存档

- 真正切换地图后自动保存；
- 可配置每 N 分钟自动保存；
- 目标固定为 `Save091.TSF`~`Save099.TSF`；
- 有空槽先按 91、92……99 使用；
- 9 个都存在后读取 Windows `LastWriteTime`，只覆盖时间最旧的一份；
- **不重命名九个文件、不保存 NextSlot 指针、不依赖额外数据库/sidecar。**

### 循环翻页

- 第一页 `0~3` 再执行“上一页” -> 最后一页 `96~99`；
- 最后一页 `96~99` 再执行“下一页” -> 第一页 `0~3`；
- 实际 page base 仍然只使用原版结构的 `0,4,8,...,96`，因此 Controller 能观察到真实 `0↔96` 变化。

### 可选外置声音

只支持外置 WAV，不再优先使用游戏原生音效。

目录：

```text
mods\asi\Castle_SaveEnhance.asi
mods\asi\Castle_SaveEnhance.ini
mods\asi\Castle_SaveEnhance\SaveOK.wav
```

INI 只填写单个 WAV 文件名。空、非法、文件不存在、`winmm.dll`/`PlaySoundW` 不可用均静默，不影响真正的存档/读档结果。

test4 新增 `Volume=0~100`。`Volume<100` 为了保持无 CRT，只对明确可解析的 PCM WAV 做内存振幅缩放；`Volume=100` 直接调用文件播放。

## 2. 最重要的历史证据纠正

曾经在研究资料里出现过 `Save001`~`Save159`。用户明确指出：这是别人制作的**人工编号流程存档包**，不是原版存档菜单自然产生的 159 个槽。

因此这批 TSF 只能作为剧情阶段样本，**永久禁止用于证明原版支持 159 槽或超过 32 槽。**

本版本 100 槽结论只来自：

1. 原版 `RPG.exe` 存档菜单机器码；
2. 本次用户 `MiscInfo.ENC` 解码后 `+0x3C2 = 8`；
3. SaveSlot/LoadSlot 的动态槽号参数与 `%03d` 文件命名链。

---

## 3. 原版为什么是 32 槽

用户本次 `MiscInfo.ENC`：

- 编码大小：`0x41E = 1054`；
- 解码：`decoded[i] = encoded[i] XOR (i % 255)`；
- 解码后 SHA-256：`cd18d110d458fe60928eb874f76453f751489cf2d0341d2c7c250c4ece13e6e9`；
- 解码后 `+0x3C2` DWORD = `8`。

EXE 存档菜单两处读取这个字段：

- `0x424ECB`；
- `0x42565A`。

后面原版都执行 `<<2`，即乘 4。因此原版容量：

```text
8 页 × 4 行 = 32 槽
```

SaveEnhance 不修改 `MiscInfo.ENC` 文件，而是在运行时把这两处读页数的指令替换为常量 25，保留原版乘 4，因此得到 100。

## 4. 100 槽与循环分页固定机器码

### 六个 1基 -> 0基槽号点

| VA | 原版 | 新语义 |
|---|---|---|
| `0x424D8D` | `8D 54 01 01` | LoadSlot `page+row+1` -> `page+row` |
| `0x424DE7` | `8D 4C 02 01` | SaveSlot 槽号改 0 基 |
| `0x425324` | `8D 54 02 01` | 聚焦行控件槽号改 0 基 |
| `0x4253C0` | `8D 54 10 01` | 元数据/文件检查槽号改 0 基 |
| `0x425486` | `8D 4C 10 01` | 当前选择标签改 0 基 |
| `0x4255BA` | `8D 54 11 01` | 每行标签改 0 基 |

`0x425324` 是早期 AnytimeSave dev1 漏掉的点；该旧 7 点候选已经废弃，SaveEnhance 不得退回那一版。

### 两个 25 页点

| VA | 原版 | SaveEnhance |
|---|---|---|
| `0x424ECB` | `8B 8A C2 03 00 00` | `B9 19 00 00 00 90` |
| `0x42565A` | `8B 91 C2 03 00 00` | `BA 19 00 00 00 90` |

### 两个页箭头边界

| VA | 原版 | SaveEnhance |
|---|---|---|
| `0x425626` | `7E 11` | `90 90`，第一页仍允许上一页 |
| `0x425665` | `7D 11` | `90 90`，最后页仍允许下一页 |

这十项作为一组事务安装。

### 循环 page base 两条 6-byte Hook

- `0x424E90`：原版 `mov eax,[esi+598]`；第一页时 helper 临时返回 100，原版后续 `-4` 得 96；
- `0x424EC2`：同一原版读取；最后页 96 时 helper 临时返回 -4，原版后续 `+4` 得 0。

最终真实 `SaveSlot+0x598` 仍是 0 或 96，不保存虚假的 100/-4。

## 6. 保留槽为什么键鼠和 Controller 都不能普通保存

保留槽：

```text
0
91~99
```

### 第一层：原生 Button disabled

SaveAction 三项真实 index：

```text
index 2 = 存档
index 1 = 读档
index 0 = 取消
```

SaveAction constructor：`0x425FE0`，vtable=`0x460B90`；vtable `+0x18`，即绝对 `0x460BA8`，原来指向 Update `0x4262C0`。

SaveEnhance 只替换这个 Update vtable 指针。进入原版 Update 前：

1. 找到当前 SaveAction 对应的父 SaveSlot；
2. 计算 `pageBase + selectedRow`；
3. 如果是 0 或 91~99；
4. 临时把 index2“存档”Button 的 `+0x04` disabled byte 设成 1；
5. 调原版 `0x4262C0`；
6. Update 返回立即恢复原字节。

这样不会把已销毁 UI 指针保存到下一帧，降低 use-after-free 风险。

### Controller 兼容

当前 Castle_PadSupport 的 SaveAction Event 同样检查 Button `+0x04 == 0` 才允许事件，所以这层 disabled 对鼠标、键盘和 Controller 的实际执行都生效。

**已知 UI 边界：** Controller 当前视觉聚焦 Hook 可能仍让焦点停在 disabled 的“存档”项上，但真正 Event 会再次检查 disabled，因此不能实际写盘。test3 只承诺“不能执行保存”，不提前承诺“手柄视觉焦点一定自动跳过灰项”。

### 第二层：SaveSlot 调用保护

即使未知输入绕过 UI，以下两个已找到的手动 SaveSlot CALL 也被 Hook：

- `0x424DF2` 正常存档菜单；
- `0x44A82D` 隐藏/文字命令。

目标槽为 0 或 91~99 时直接返回失败，不进入原版 SaveSlot。

LoadSlot 路径不 Hook，因此保留槽仍可读取。

## 7. SaveSlot owner / SaveAction 父对象定位

test1 曾为了知道 SaveAction 属于哪个 SaveSlot，Hook 三个 SaveSlot constructor CALL：

- `0x413C3F`；
- `0x434E93`；
- `0x4477C8`。

用户第一次实机启动时出现“目标机器码预检查失败”，而 test1 日志把十几项检查合并成一个布尔结果，没有指出具体哪一项冲突。虽然无法从旧日志反推出确切地址，但这三个 constructor Hook 本身不是功能必需，而且会额外扩大与其它 ASI 的交叉修改面，所以 **test2 已全部删除，不再写这三个地址。**

test2 改为每次 SaveAction Update 当帧只读当前三个已经闭合的 owner：

| owner 全局 | SaveSlot 位置 | 用途 |
|---|---:|---|
| `[0x008E241C]` Title | `+0x5B4` | 标题/前端存档页 |
| `[0x008DED0C]` Interface | `+0x654` | Interface state7 存档页 |
| `[0x0089FCD0]` SavePoint wrapper | `+0x580` | 地图存档点 |

对候选 SaveSlot 只读取 `SaveSlot+0x5A4`，只有它等于当前 SaveAction 指针才认作父对象。

这条路线的优势：

- 不再修改 SaveSlot 构造链；
- 不缓存已经销毁 UI 的裸 SaveSlot 指针；
- 不写 Controller 私有状态；
- SaveAction disabled 逻辑仍然能够根据真实 `pageBase+row` 判定 0、91~99。

## 8. 普通“安全随时存档”基线继续保留

SaveEnhance 包含之前 AnytimeSave 已经得到实机正向结果的 vanilla fallback 架构，不需要同时加载旧 `AnytimeSave.asi`。

核心：

- 正常保存许可 CALL：`0x40CCC2`；
- Map Tick CALL：`0x40B078`；
- SaveSlot 内 Writer CALL：`0x43B34C`；
- 原版 save gate：`0x40A0C0`；
- 原版 Map Tick：`0x40ADE0`；
- SaveSlot：`0x43B320`；
- Writer：`0x43B360`。

如果原版本来允许保存：完全按原版状态写盘。

如果原版拒绝：只有当前地图已经建立冻结安全锚点，才在 Writer 的极短窗口把 World 前 `0xC8` 字节替换成入口级安全 header，Writer 返回立即恢复精确内存。`0xC8` 后的 GameVar/进度不回滚。

历史已经失败并废弃的 TSA/YCS sidecar 方案不再恢复。

## 9. 安全锚点结构

已确认：

- DataCenter*：`0x0089F804`；
- DataCenter `+0x280`：Map scene container；
- scene container：recordCount `+0x00`，selectedIndex `+0x04`，raw SCI `+0x0C`，runtimeEntry `+0x10`；
- SCI record stride：`0x473`；
- actor runtime array：`0x0089F7F0`；
- controlled actor index：`0x00468BF0`；
- actor stride：`0x74`；X `+0x10`，Y `+0x14`，state `+0x1A`；
- World*：`0x00978508`；
- World 长度：`0x27D8`；
- scene restore header：前 `0xC8`；
- header X/Y/state/actor：`+0x32/+0x36/+0x3A/+0x3E`；
- runtime manager*：`0x008E1C48`；
- manager World length/pointer：`+0x13C/+0x140`。

地图身份不是只比较一个可能被 allocator 复用的指针，而是组合：

- sceneContainer；
- rawSource；
- recordCount；
- defaultIndex；
- 所有 raw SCI record 的 FNV-1a fingerprint。

连续 8 个严格自由行动 Tick 后冻结这一稳定窗口的第一份样本。

---

## 10. Quick Save 语义

Quick Save 比普通随时存档更严格：

1. 必须严格自由行动；
2. 重新验证 actor；
3. 调原版保存准备 `0x44B150`；
4. 调**原版** save gate `0x40A0C0`；
5. 如果原版此刻允许，直接按原版状态保存；如果原版拒绝但当前地图已经冻结安全锚点，则允许 Writer fallback；没有锚点才失败；
6. 不使用入口 fallback；
7. 成功才调用原版 SaveSlot(0)。

理由：用户按 F5 是在要求“现在这里保存”，不能在楼梯 transient 里悄悄写成入口位置而让用户误解。

---

## 11. Quick Load 语义

F9 / RB+Start 请求先进入确认状态机。达到 N 次后才真正读取。

真正 Load 复刻原版隐藏 Load 命令链：

1. runtime manager `+0x13C = 0x27D8`；
2. `+0x140 = 当前 World`；
3. 原版 LoadSlot(0) `0x43B4D0`；
4. 原版 post-load `0x44B1F0`；
5. 成功后重置地图/自动存档基准，避免刚读档就误判成场景切换自动覆盖。

即使 LoadSlot 返回失败，post-load 调用也跟随原版隐藏命令已确认的顺序。

---

## 12. 严格自由行动门

Quick Save、Quick Load、冻结安全锚点都要求：

- 当前 Map selectedIndex == defaultIndex；
- `0x0089F808` map action busy == 0；
- `0x0046F670` dialogue id == 0；
- Battle UI `0x0089FD74` 为空；
- Title UI `0x008E241C` 为空；
- Interface UI `0x008DED0C` 为空；
- Save Point UI `0x0089FCD0` 为空；
- Movie `0x0046F390` 不活动；
- controlled actor 有效；
- World 可读。

因此剧情、战斗、菜单、对话、影片、存档界面、地图切换 transient 都应拒绝 Quick 操作。

这套门在 test3 仍需实机逐场景验收；静态验证只能确认地址/代码，不可能替代真实状态测试。

## 13. 自动存档调度

### 场景切换

第一次看到地图只建立 baseline，不保存。

地图 identity 真正改变后：

- `SceneAutoPending=true`；
- 等新图拿到 frozen anchor；
- 再写 91~99。

### 定时

`IntervalMinutes=0` 关闭定时；1~1440 有效。

自动保存成功会重置计时基准，避免刚换图成功写完下一秒又因为旧定时器到期重复写一次。

### 失败退避

如果已经真正尝试写盘而失败，至少 5 秒后再尝试，避免 20Hz Map Tick 连续打硬盘/日志。

如果只是还没安全锚点，不算“失败尝试”，第 8 个稳定 Tick 一形成锚点即可立刻补存。

## 14. 91~99 滚动算法为什么不用重命名

没有采用：

```text
Save098 -> Save099
Save097 -> Save098
...
新档 -> Save091
```

因为一次自动存档会修改多个文件，中途崩溃/权限失败可能破坏整条历史。

当前算法每次最多让原版 Writer 改一个 TSF：

1. 查询 `Save091.TSF`~`Save099.TSF`；
2. 文件不存在错误 2/3 -> 立刻选择最小空槽；
3. 其它查询失败不假装“文件不存在”；
4. 全部存在 -> 比较 `ftLastWriteTime`，选择最旧；
5. 如果九个都无法可靠读取属性 -> 本次不覆盖任何自动档。

因此用户删除一个自动档、恢复旧备份、丢失 INI，都不会让某个持久 NextSlot 指针和现实文件错位。

## 15. Controller API 接入

SaveEnhance 不读 Controller 私有全局，而是动态：

```text
GetModuleHandleA("Castle_PadSupport.asi")
GetProcAddress("CastlePad_GetApi")
GetApi(version=1)
```

校验：

- magic `0x44415043`；
- API version 1；
- struct_size；
- ButtonDown；
- AllowsExternalUiInput。

若 SaveEnhance 比 Controller 先加载，第一次找不到不会永久放弃，而是每 1000ms 低频重试。

若 Controller 不存在，F5/F9 正常工作。

手柄组合不依赖 Controller 某一个很短的 `Pressed` 采样帧；SaveEnhance 使用 ButtonDown 组合并自己做 chord 上升沿：

- `RB && R3` 从 false->true = Quick Save 请求；
- `RB && Start` 从 false->true = Quick Load 请求。

只有 API Ready、Connected、GameForeground、AllowsExternalUiInput 都允许时才接受。

## 16. 外置 WAV 反馈

运行时才动态加载：

- `user32.dll`：F5/F9 和前台窗口检查；
- `winmm.dll`：可选 `PlaySoundW`。

二者不形成静态 Import Table 依赖。

每个声音字段只允许一个 `.wav` 文件名，禁止：

- `\`、`/`；
- `:`；
- `* ? " < > |`；
- `..` 路径跳转；
- 非 `.wav` 后缀。

实际只拼接到：

```text
<ASI目录>\Castle_SaveEnhance\<文件名>
```

声音播放只提供反馈，不参与操作成功逻辑。

## 17. 启动 fail-closed、逐地址诊断与回滚

### test1 实机失败记录

用户第一次运行 `v0.1.0-test1` 得到：

```text
[启动失败] SaveEnhance 目标机器码预检查失败；未开始安装。
[状态] SaveEnhance 未完整安装；为保护存档，本轮不提供增强功能。
```

这说明 fail-closed 本身起作用了：插件没有在未知状态下强写机器码。但 test1 的诊断设计不足——所有地址都塞在一个 `||` 表达式里，所以日志没有告诉人类到底是哪一项不同。

已经排除“目标 EXE 本身选错”这个误导：项目当前实际运行基线仍锁定 SHA-256 `8294839343b1a7845ddae31ed16216b05850efd39a742e5ca7701aadca97287f`。Controller 某个旧头文件里残留过另一份哈希，应视为文档未同步，不作为运行基线。

### test2 的改动

安装前仍然验证真正需要写入的地址，但现在每一项独立检查并在失败时输出：

- 人类可读用途；
- 绝对地址；
- 期望机器码；
- 当前实际机器码；
- 如果当前仍是 `E8 CALL`，解出当前 CALL 目标；
- 用 `VirtualQuery` 尽量判断目标属于 `Castle_PadSupport.asi`、旧 `AnytimeSave.asi`、其它常见 Castle 模块还是未知模块；
- vtable 冲突同样打印当前函数目标和模块基址。

test2 真正要求保持可写原版状态的范围缩减为：

- 10 个固定菜单补丁；
- 2 个循环分页 6-byte Hook；
- **5 个** 5-byte CALL Hook：保存许可、Map Tick、Writer、菜单手动保存、隐藏命令保存；
- SaveAction Update vtable；
- save gate 本体需为原版或已知旧无条件补丁（后者先恢复原版）。

不再把三个 SaveSlot constructor CALL 当成安装前提。

### test2 第二次实机失败：正式安装停在 DllMain

用户 test2 日志只到 `[配置]`，而 `InstallAllHooks()` 预检查、成功和失败日志一个都没有；所有存档增强同时失效。该证据与 Castle Mod Loader 的正式 `InitializeASI` 生命周期对照后，定位为插件初始化位置错误，而不是存档槽算法错误。

### test3 的生命周期修复

- DllMain 不再打开日志、读 INI、查其它模块或写机器码；
- Loader 调用 `InitializeASI` 后才正式开始所有业务；
- `InitializeASI` 有单次幂等保护，防止调试环境重复调用打两遍 Hook；
- 正常启动额外写 `[装载]`、`开始预检查`、`已完整安装` 阶段日志；
- 最终 PE 必须导出名为 `InitializeASI` 的函数，否则验证器和 build.bat 都拒绝产物。

### 回滚

组补丁继续使用事务备份。单 CALL 如果出现“字节已写，但 FlushInstructionCache/页保护恢复失败后函数返回 false”的极端情况，先恢复**当前失败条**，再倒序撤此前成功条目。SaveAction vtable 写失败也立即恢复原指针。

如果检测到旧 `AnytimeSave.asi` 已经在 SaveEnhance 前加载，仍明确拒绝双 Hook；如果它或其它插件在 SaveEnhance 之前改了剩余核心地址，test2 会打印精确冲突而不是只报一句失败。

## 18. 历史失败方案与禁止恢复路线

### 在 DllMain Loader Lock 内做完整 Hook 安装（test1/test2）

**已由 test2 实机判定失败，不得恢复。** Castle Mod Loader 本身会在 `LoadLibraryExW` 返回并完成 Locale/Overrides IAT 处理后调用 `InitializeASI`。SaveEnhance 必须使用这个正式生命周期；DllMain 只保留最小模块记录。

### SaveEnhance test1 过度宽泛的预检查

用户实机确认启动失败。安全上没有发生坏写，但日志无法定位冲突；test2 已删除三个不必要 constructor Hook 并改为逐地址诊断。**不得恢复 test1 的整组布尔预检查与 constructor 跟踪表。**

### TSA / YCS sidecar

早期希望把更多 transient 写进独立 sidecar，但实机遇到：

- 菜单期间没有可靠后续 Map Tick；
- 路径与游戏实际写盘位置不一致；
- Writer 后 I/O 曾得到 `ERROR_FILE_NOT_FOUND`。

因此已删除，不恢复。

### 无条件把 save gate 改为 true

会允许游戏在没有完整恢复结构的位置产生坏档风险。当前插件若看到已知旧 9 字节补丁，会先恢复原版；第三种未知字节直接 fail-closed。

### 用 Save001~Save159 证明容量

证据错误，永久废弃。

### 7 点 0~99 扩槽

遗漏 `0x425324`，永久废弃。

### 自动档重命名链

没有采用，避免一次操作多个 TSF 的事务风险。

### INI 持久 NextAutoSaveSlot

没有采用。文件删改/恢复备份会让指针和现实不一致；当前以真实文件 LastWriteTime 为权威。

### 永久修改 SaveAction Button disabled

没有采用。UI 对象可能销毁/地址复用；当前只在原版 Update 执行期间短暂 override，返回立刻恢复。
