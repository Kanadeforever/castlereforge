# CastleReforge 运行时协调系统总体设计

> 文档状态：总体设计已确定，代码尚未开始实现。
>
> 未来规范源码目录：`src/RuntimeSDK`。
>
> 本文描述目标架构，不代表当前插件已经接入。现有插件的真实行为仍以各自源码、完整接档和实机结论为准。

本文是 RuntimeSDK 的施工权威文档。开始实现后，源码文件、公开头、状态机、错误码、Hook 事务、领域接口、测试和迁移步骤都必须与本文一致。发现设计不足时先修改本文和完整接档，再修改源码；禁止让代码先形成事实、事后再用文档追认。

本文中的“必须、禁止、固定、只能”属于实现约束；“建议、方向、可以”才属于尚可评审的选择。任何偏离硬约束的实现不得进入稳定分支。

## 一、结论

CastleReforge 需要建设一套面向官方插件和第三方 Mod 作者的公共 SDK，并以固定文件名 `Castle_Runtime.dll` 提供进程内运行时核心引擎。

这套系统的首要职责不是提供游戏业务，也不是替代 ASI Loader，而是协调多个插件对同一进程资源的使用，特别是：

- 同一段 RPG.exe 机器码；
- 同一个 `E8 rel32 CALL`；
- 同一个 IAT、vtable 或函数指针槽；
- 同一个窗口过程、输入所有权或全局 Win32 状态；
- 插件之间公开的版本化服务；
- 初始化、失败回滚和进程结束阶段。

最终采用以下结构：

1. `Castle_Runtime.dll` 是加载器中立的 ASI 运行时核心，统一驱动、统合、协调、管理和调度所有已接入 SDK 的 ASI；
2. `CastleRuntime_API.h` 是稳定的公共 C ABI；
3. `CastleRuntime_Client.c/.h` 是编进每个 ASI 的轻量客户端；
4. `Castle_Runtime.dll` 固定放在 ASI 文件夹，与所有 ASI 插件处于同一目录；
5. MODLoader、其它 ASI Loader 和游戏本体都不直接加载该 DLL，由 ASI 在 Loader Lock 外按自身目录主动加载；
6. 文件不存在时，每个插件必须保留不依赖 Runtime 的独立运行路径；
7. 文件存在且 ABI 可用时，所有已接入 SDK 的 ASI 必须自动加入整合模式，不允许插件配置绕过 Runtime；
8. Castle Mod Loader 可以利用 SDK 提供更好的诊断和排序，但不是 SDK 的所有者，也不是插件运行前提；
9. 任意其它 32 位 ASI Loader 仍然可以加载这些插件；
10. SDK 只保证完整协调遵守协议的插件。未知插件若直接修改机器码，只能被检测并安全拒绝覆盖，不能承诺自动兼容。

一句话定义：

> **没有 Runtime 时，每个 ASI 都能独立正常工作；存在 Runtime 时，所有 ASI 自动组成由 Runtime 统一驱动、协调和调度的整体。**

## 二、为什么现在需要这套系统

当前代码已经出现多个“各插件分别解决同一类基础问题”的实现：

- `Controller`、`Backlog`、`Widescreen` 各自拥有不同的 `runtime/platform`；
- `SaveEnhance` 与 `Extra` 系插件拥有多份 `Win32Mini/PatchUtil/PluginLog`；
- `Controller` 与 `SaveEnhance` 会接触相同的 SaveAction CALL，目前依靠专门识别对方模块并手工保存 `next` 来兼容；
- `Widescreen` 与 `FPSUnlock` 对绘制 CALL 的兼容同样依赖双方提前知道对方行为；
- `Controller` 已经发布 PadSupport Public API v1，`Backlog` 和 `SaveEnhance` 通过复制公共头文件接入；
- 不同插件采用 DllMain 立即初始化、DllMain 创建工作线程、游戏 Tick 初始化、`InitializeASI` 等多种生命周期。

这些做法在插件数量较少时可以工作，但大型插件继续增加后，双边兼容关系会快速增长。三个插件可能需要三组协议，五个插件最多会出现十组双边关系，而且每次加载顺序变化都可能产生新的组合。

SDK 的价值不是消灭插件内部差异，而是把以下规则变成项目级协议：

- 谁正在使用某个地址；
- 这个地址能否串联；
- 串联时调用约定和 `next` 是什么；
- 哪些补丁必须独占；
- 一组补丁失败时应回滚哪些内容；
- 服务提供者和消费者如何协商版本；
- Runtime 缺失时插件怎样安全进入独立模式；
- Runtime 存在时怎样禁止插件绕过统一所有权和调度。

## 三、设计优先级

所有设计和实现决策按以下顺序裁决：

1. **不破坏游戏和存档；**
2. **一个插件失败不得连坐其它插件；**
3. **插件可脱离 Castle Mod Loader 独立运行；**
4. **不存在协调器时仍可安全运行；**
5. **未知状态优先拒绝修改，而不是猜测兼容；**
6. **ABI 长期稳定，旧插件不能因新运行时升级而崩溃；**
7. **迁移可以逐个插件进行，不要求全仓一次性重构；**
8. **第三方作者只需理解少量清晰概念；**
9. **诊断信息必须能指出真正的插件、地址和失败阶段；**
10. **性能优化不能破坏前面九项。**

如果便利性、性能或功能数量与上述优先级冲突，必须让位于安全和隔离。

## 四、明确不做什么

`Castle_Runtime.dll` 是整个 ASI 生态的核心引擎，但“核心引擎”不等于把所有插件业务复制进一个 DLL。它负责统一规则、接口、状态、时序和后端选择；具体算法仍由最了解该领域的插件实现。第一阶段明确不承担：

- 战斗、菜单、存档、宽屏、帧率或手柄业务；
- SDL3 初始化和手柄设备所有权；
- Locale Emulator、Overrides、Launcher GUI；
- 自动识别未知 RPG.exe 并猜测地址；
- 自动修复没有使用 SDK 的第三方插件；
- 在插件之间共享可随意写入的业务结构体；
- 跨 DLL 暴露 C++ 类、STL 容器、异常或编译器私有对象；
- 在运行时自动下载或替换任何文件；
- 为了“兼容”而覆盖来源不明的现有 Hook；
- 第一版支持运行中热卸载已经拥有 Hook 的插件。

这些边界用于防止 Runtime 因复制所有业务实现而变成无法维护的巨型单点。Runtime 可以对外提供涉及显示、输入、任务、UI、场景、战斗、存档等所有方面的统一接口，但具体插件应通过后端注册把权威实现交给 Runtime 统合。

## 五、总体结构

### 5.1 组件

| 组件 | 形式 | 是否必须 | 职责 |
|---|---|---:|---|
| `Castle_Runtime.dll` | 普通 32 位 DLL | 单插件独立模式可缺失；整合模式必须 | ASI 运行时核心、统一接口、调度、Hook 所有权、事务、后端、服务和诊断 |
| `CastleRuntime_API.h` | 公共 C 头文件 | SDK 插件必须 | 固定 ABI、结构体、错误码、能力位和函数表 |
| `CastleRuntime_Client.c/.h` | 插件内嵌源码 | SDK 插件必须 | 发现协调器、版本协商、幂等启动、独立降级和少量安全包装 |
| 游戏业务 ASI | 普通 ASI/DLL | 按用户选择 | 只实现自己的功能，并向协调器声明资源需求 |
| 任意 ASI Loader | 第三方或本项目 Loader | 必须有一种 | 把 ASI 加载进 RPG.exe；不拥有 SDK 语义 |
| Castle Mod Loader | 本项目可选 Loader | 否 | 可额外读取描述、排序和展示诊断，但不得成为 SDK 运行前提 |

### 5.2 关系

```text
任意 32 位 ASI Loader
        │
        ├── 加载插件 A.asi ── 内嵌 SDK Client ─┐
        ├── 加载插件 B.asi ── 内嵌 SDK Client ─┼── Castle_Runtime.dll
        └── 加载插件 C.asi ── 内嵌 SDK Client ─┘          │
                                                          ├── 插件登记
                                                          ├── Hook/补丁协调
                                                          ├── 服务发现
                                                          └── 冲突诊断

Castle_Runtime.dll 不存在：

插件 A/B/C 各自进入独立模式，只使用自己的 fail-closed 安装路径。

Castle_Runtime.dll 存在：

所有已接入 SDK 的插件必须自动加入整合模式。文件存在但损坏或 ABI 不兼容时，插件不得悄悄绕过 Runtime 后继续写入游戏；必须停用需要写入的能力并输出明确诊断，避免同一进程同时出现“受管理 Hook”和“私自 Hook”。
```

### 5.3 为什么运行时使用 DLL，而不是 ASI

`Castle_Runtime.dll` 不应命名为 `.asi`，原因如下：

- 它本身不提供用户功能，不应该出现在普通 Mod 启停列表中；
- 它不应该依赖某个 ASI Loader 的扫描目录和排序规则；
- ASI Loader 只扫描并加载 `.asi`，不会把 Runtime 当成一个业务 Mod；
- 游戏本体没有对它的静态导入，也不会因为文件位于 ASI 文件夹就自动加载；
- SDK 客户端在 Loader Lock 外取得自身 ASI 的实际目录，追加固定文件名，再加载同目录的准确文件；
- 普通 Windows 模块加载规则可以保证同一模块实例在进程中复用；
- 它可以被 Castle Mod Loader、Ultimate ASI Loader 或其它加载器环境共同使用。

固定文件名永久使用 `Castle_Runtime.dll`。版本通过 `CastleRuntime_GetApi`、结构大小、能力位和文件版本协商，不把 ABI 主版本写进文件名。Runtime 必须长期保留旧接口语义；未来新增能力使用新的版本化子接口，不得原地重解释已经发布的接口。

## 六、为什么不选择其它方案

### 6.1 不放进 CastleModCore.dll

Castle Mod Loader 是可选内容，ASI 插件的重要程度和可移植性高于 Loader。把公共 API 放进 `CastleModCore.dll` 会导致：

- 使用其它 ASI Loader 时公共能力消失；
- 第三方插件被迫依赖本项目 Launcher；
- Loader 的 Locale/Overrides 生命周期与普通插件协调生命周期耦合；
- Loader 更新可能无意中改变所有插件的基础依赖。

因此 Castle Mod Loader 只能是 SDK 的可选使用者和增强适配器。

### 6.2 不要求额外安装 Castle_Core.asi

独立核心 ASI 会引入新的加载顺序问题：它必须先于其它插件加载，但不同 ASI Loader 的排序规则不统一。用户还可能误关、改名或删除它。

普通 DLL 配合插件内嵌客户端更容易明确发现、加载和协商版本，也不会伪装成一个可选业务 Mod。

### 6.3 不采用“首个插件自动成为协调器”

把协调器代码静态编进每个插件，再让第一个插件成为宿主，表面上少了一个 DLL，但会产生隐蔽风险：

- 普通业务插件会意外成为全局单点；
- 宿主插件必须永久固定驻留；
- 不同 SDK 版本需要进行复杂的宿主选举；
- 先加载的旧插件可能迫使所有新插件使用旧协调逻辑；
- 调试时很难判断当前究竟由哪个插件持有全局状态；
- 卸载或初始化失败可能连锁影响其它插件。

独立、业务中立、主版本固定的 DLL 更清晰，也更容易测试和替换。

### 6.4 不只做公共头文件

公共头文件能够统一名称和结构，却不能共享进程内所有权状态。每个 ASI 静态编译一份补丁工具后，仍然不知道其它插件已经修改了什么。

因此 SDK 同时需要稳定头文件和可选的进程内协调实例。

### 6.5 建立全领域统一门面，但不建立僵硬巨型表

Runtime 必须能够统合游戏各个方面，包括显示、输入、任务、UI、场景、战斗、存档、音频和未来尚未出现的领域。但不能把所有函数提前塞进一张固定巨型表，否则任何新需求都会修改根 ABI。

正确结构是：

- 根 API 永久保持很小，只提供版本、插件登记、`QueryInterface`、事务、后端注册和诊断；
- 每个游戏领域使用独立的版本化子接口；
- Runtime 对外提供统一领域门面和原版默认后端；
- Widescreen、Controller、SaveEnhance 等插件向 Runtime 注册更专业的领域后端；
- 消费者只查询 Runtime，不直接按文件名依赖另一个插件；
- 未知的新领域通过新的接口标识加入，不需要在旧结构中预留大量空函数指针。

因此“提前留下接口”的实现不是猜测所有未来函数，而是永久保留稳定的接口查询与后端注册机制。需要新领域时发布新子接口，旧插件和旧接口完全不变。

## 七、运行模式与降级规则

### 7.1 整合模式

同一 ASI 文件夹存在 `Castle_Runtime.dll` 时，所有已接入 SDK 的插件必须尝试进入整合模式。满足以下条件后正式激活：

- 找到同目录的 `Castle_Runtime.dll`；
- `CastleRuntime_GetApi` 存在；
- ABI 主版本、`magic`、`struct_size` 和必需能力通过；
- 插件登记成功；
- 插件需要的事务和服务通过预检。

整合模式下：

- 所有新增 Hook、补丁、公共服务和领域后端必须通过 Runtime；
- 插件不得提供“绕过 Runtime”配置；
- 插件不得在 Runtime 拒绝事务后改走私有写入器强行安装同一能力；
- Runtime 统一决定初始化阶段、资源所有权、Hook 链、后端和调度顺序；
- 单项能力失败按事务隔离，不让其它已批准能力连锁失效。

### 7.2 独立模式

只有同目录**确实不存在** `Castle_Runtime.dll` 时，插件才进入独立模式。

文件存在但无法加载、导出损坏、ABI 不兼容或 Runtime 初始化失败时，不得悄悄转入独立写入路径。否则同一进程可能同时存在受管理插件和绕过管理的插件，Runtime 无法再保证全局稳定。

这种情况进入“Runtime 故障安全停用”状态：

- 保留 DLL 已被 Windows 映射这一事实；
- 不安装任何尚未由 Runtime 批准的游戏写入；
- 只允许不修改游戏的诊断能力；
- 日志明确说明 Runtime 文件存在但不可用；
- 提示修复或删除错误 Runtime 文件后再决定进入整合模式或独立模式。

独立模式必须满足：

- 不依赖 Castle Mod Loader；
- 保留当前插件已经验证的 fail-closed 预检；
- 不覆盖未知 Hook；
- 日志明确写出“未发现同目录 Castle_Runtime.dll，进入独立模式”；
- 只关闭必须依赖协调器的跨插件增强，不关闭插件自身核心功能。

独立模式保证每个 ASI 单独正常工作，但不承诺多个独立 ASI 的完整全局协调。多个插件希望获得确定性链路和长期组合稳定性时，应安装 Runtime。

### 7.3 冲突降级

Runtime 发现资源冲突时，默认只拒绝发生冲突的事务或能力。不得因为一个可选 UI Hook 冲突而让整个运行时、其它插件或游戏停止。

插件可以把能力分成多个事务，例如：

- 核心功能事务；
- 可选 Controller 联动事务；
- 可选宽屏联动事务；
- 调试/统计事务。

这样可选事务失败时，核心事务仍可保留。

### 7.4 未接入 SDK 的旧插件

运行时无法控制未知插件已经执行的直接内存写入。发现目标字节不是原版、也不是运行时管理的链时，必须：

1. 不写入；
2. 记录目标地址和当前字节；
3. 尽可能使用 `VirtualQuery` 标识当前目标所属模块；
4. 把冲突结果返回给请求插件；
5. 由请求插件关闭对应能力。

不得自动把未知目标当作合法 `next`。

## 八、统一生命周期

### 8.1 插件状态机

每个迁移后的插件使用同一套幂等状态：

```text
未启动
  ↓ 请求初始化
已调度
  ↓ 某一路成功取得初始化所有权
初始化中
  ├── 同目录无 Runtime             → 独立运行
  ├── Runtime 可用且登记成功       → 整合运行
  ├── Runtime 文件存在但不可用     → 故障安全停用
  └── 自身关键预检或事务失败       → 隔离对应能力/安全停用
```

`InitializeASI`、兼容 Loader 回调和 DllMain 安排的延迟工作只能竞争同一个原子初始化状态。获得状态转换权的一方执行，其他入口立即返回，禁止重复打 Hook。

### 8.2 DllMain 硬边界

DllMain 只允许：

- 保存自身 `HMODULE`；
- `DisableThreadLibraryCalls`；
- 初始化不访问磁盘、不加载 DLL、不修改游戏的原子状态；
- 安排一个 Loader Lock 外的延迟初始化入口。

DllMain 禁止：

- 读写 INI 和日志正文；
- `LoadLibrary` 协调器或第三方依赖；
- 安装游戏 Hook；
- 等待线程、锁或事件；
- 调用其它插件；
- 执行业务初始化。

### 8.3 双入口兼容

为了兼容 Castle Mod Loader 和普通 ASI Loader，SDK 客户端提供同一个幂等初始化核心，并允许两种触发方式：

1. Loader 在 Loader Lock 外调用标准兼容导出；
2. 普通 ASI Loader 只调用 DllMain 时，由插件安排的延迟入口触发。

两条路径只能决定“谁先进入”，不能产生两套业务流程。

### 8.4 当前 SaveEnhance 的迁移要求

当前 SaveEnhance 正式初始化依赖 Castle Mod Loader 调用 `InitializeASI`。这是当前实现事实，不能在代码迁移前从现有接档中删除。

迁移后应改为：

- 保留 `InitializeASI` 兼容导出；
- 增加普通 ASI Loader 的 Loader Lock 外延迟入口；
- 两者进入同一原子状态机；
- 继续禁止把完整初始化放回 DllMain。

### 8.5 SDK Client 状态机

每个 ASI 内嵌的 Client 使用以下固定状态：

```text
CLIENT_COLD
CLIENT_SCHEDULED
CLIENT_DISCOVERING
CLIENT_STANDALONE
CLIENT_JOINING
CLIENT_INTEGRATED
CLIENT_RUNTIME_FAULT
CLIENT_PLUGIN_FAILED
```

允许的核心转换：

```text
COLD -> SCHEDULED -> DISCOVERING
DISCOVERING -> STANDALONE       仅当同目录文件不存在
DISCOVERING -> JOINING          同目录文件存在且成功加载根 API
DISCOVERING -> RUNTIME_FAULT    文件存在但加载/ABI失败
JOINING -> INTEGRATED           插件登记成功
JOINING -> PLUGIN_FAILED        插件身份或必需能力失败
```

状态只允许单向推进。任何入口看见终态都直接返回已有结果，禁止重新执行发现、加载和业务安装。

### 8.6 自动加入硬规则

同目录存在有效 `Castle_Runtime.dll` 时：

- 所有 SDK 插件自动加入；
- INI 不提供 `UseRuntime=0`、`Standalone=1` 等绕过开关；
- 命令行和环境变量也不允许普通用户绕过；
- 开发诊断若确需测试独立模式，应临时移走 Runtime 文件或使用专门测试进程，不把后门带入正式产物；
- Runtime 拒绝某项资源后，插件不得改用本地 PatchUtil 重试同一资源。

这条规则是整合模式能够承诺“所有已接入插件属于同一个整体”的前提。

### 8.7 插件激活顺序

插件加入 Runtime 后按以下施工顺序激活：

1. 登记插件描述并取得 `CastlePluginHandle`；
2. 查询游戏构建和必需领域接口；
3. 登记自己提供的领域后端，但状态先保持 `NOT_READY`；
4. 建立一个或多个 Hook/补丁事务；
5. 完成全部必需事务预检；
6. 提交事务；
7. 初始化插件私有业务状态；
8. 发布只读快照；
9. 把领域后端切换为 `READY`；
10. 向 Runtime 标记插件 `ACTIVE`。

任一步失败：

- 未提交事务直接废弃；
- 已提交但业务尚未公开的事务按该插件事务策略回滚；
- 后端保持 `NOT_READY`；
- Runtime 不把半初始化插件暴露给消费者；
- 其它插件继续运行。

### 8.8 不等待“所有插件加载完”

不同 ASI Loader 没有统一的“扫描结束”回调。Runtime v1 不使用固定睡眠时间猜测所有插件已经加载完成。

正确做法是支持晚到插件：

- 插件随到随登记；
- Hook 链按稳定顺序重新发布；
- 服务/后端代次递增；
- 消费者通过 Runtime 门面自动看到新后端；
- 已激活插件不保存其它插件模块名或私有指针。

这样加载顺序只影响“能力何时出现”，不影响最终所有权和链顺序。

## 九、ABI 稳定规则

### 9.1 基础规则

所有公开 ABI 必须：

- 使用 C ABI；
- 明确 x86 调用约定；
- 使用固定宽度整数；
- 每个公开结构包含 `magic`、`struct_size` 和版本；
- 只在结构尾部追加字段；
- 通过能力位判断可选函数；
- 不跨模块抛出异常；
- 不跨模块传递需要对方释放的堆内存；
- 不暴露可变化的内部结构体地址；
- 不依赖编译器名称修饰；
- 对字符串明确编码、长度、所有权和生命周期。

### 9.2 内存所有权

第一版采用最保守规则：

- 调用方分配缓冲区，接收方只写入指定容量；
- 运行时返回的 API 表和只读描述由运行时持有，进程结束前稳定；
- 插件提供的描述字符串必须是进程生命周期内稳定的静态 UTF-8；
- 服务函数表由提供者持有，提供者被运行时固定驻留后才允许发布；
- 不提供跨 DLL 通用 `Alloc/Free`。

### 9.3 线程与锁

- 运行时内部状态使用自己的锁；
- 持有运行时锁时禁止调用插件回调；
- 插件初始化和 Hook wrapper 不得假设运行时回调线程；
- Hook 热路径读取的 `next` 槽使用对齐指针和明确的原子可见性；
- 服务函数表必须在说明中声明可调用线程；
- 第一版不提供隐式跨线程业务调用。

### 9.4 导出边界

运行时 DLL 的首个稳定导出只有：

```text
CastleRuntime_GetApi
```

插件面向工具和可选 Loader 的标准描述导出建议为：

```text
CastlePlugin_Query
```

插件现有业务导出可以继续保留。SDK 不要求第三方 ASI Loader 主动理解这些导出；插件内嵌客户端会完成发现和登记。

### 9.5 公共基础类型施工规格

`CastleRuntime_API.h` 必须自己定义 ABI 所需的最小类型，不把 Windows SDK、C++ 标准库或编译器私有类型泄露给第三方头文件。

固定规则：

| 公共类型 | ABI 含义 |
|---|---|
| `CastleU8/CastleS8` | 固定 8 位整数 |
| `CastleU16/CastleS16` | 固定 16 位整数 |
| `CastleU32/CastleS32` | 固定 32 位整数 |
| `CastleAddress` | x86 进程地址，底层为 `CastleU32` |
| `CastleModule` | 不透明模块值，底层为 `CastleAddress` |
| `CastlePluginHandle` | Runtime 分配的非零 32 位句柄 |
| `CastleTransactionHandle` | Runtime 分配的非零事务句柄 |
| `CastleClaimHandle` | Runtime 分配的非零资源声明句柄 |
| `CastleProviderHandle` | Runtime 分配的非零领域后端句柄 |
| `CastleResult` | 固定 32 位有符号结果码 |

禁止在公开 ABI 中使用：

- `bool`；
- 编译器尺寸可能变化的 `long long` 以外未固定别名；
- `size_t`；
- C++ `enum class`；
- `std::string/vector/function`；
- Windows 头文件中的结构体值传递；
- 位域；
- 默认结构体对齐假设。

所有公共结构显式使用 4 字节对齐，并在构建检查器中验证 x86 `sizeof` 和关键字段偏移。头文件为 C89/C99 可包含形式，C++ 使用者通过 `extern "C"` 获得同一 ABI。

### 9.6 UTF-8 字符串视图

公共字符串统一使用：

```text
CastleStringView
  data    -> UTF-8 字节，只读
  length  -> 不含结尾 NUL 的字节数
```

调用者不能假设 `data[length]` 一定是 NUL。登记函数在返回前必须把需要长期保存的 ID、名称和版本文本复制进 Runtime 自己的内存；不得长期持有调用者临时缓冲区。

稳定标识只允许 ASCII 小写、数字、点、下划线和短横线。用户可见名称与诊断文字使用 UTF-8。

### 9.7 结果码分层

`CastleResult` 采用以下稳定约定：

- `0`：成功；
- 正数：成功但发生可说明状态，例如“已登记”“使用默认后端”“接口版本降级”；
- 负数：失败。

ABI v1 至少冻结以下结果语义：

| 数值 | 结果名 | 语义 |
|---:|---|---|
| `0` | `CASTLE_OK` | 完整成功 |
| `1` | `CASTLE_STATUS_ALREADY_DONE` | 同一幂等请求已经成功完成 |
| `2` | `CASTLE_STATUS_DEFAULT_BACKEND` | 成功，但当前使用 Runtime 原版默认后端 |
| `3` | `CASTLE_STATUS_OPTIONAL_UNAVAILABLE` | 可选能力不存在，调用方可以安全降级 |
| `-1` | `CASTLE_ERROR_INVALID_ARGUMENT` | 指针、大小、字符串或枚举非法 |
| `-2` | `CASTLE_ERROR_ABI_MISMATCH` | 根 ABI 或结构版本不兼容 |
| `-3` | `CASTLE_ERROR_RUNTIME_FAULT` | Runtime 文件存在但核心初始化失败 |
| `-4` | `CASTLE_ERROR_UNKNOWN_GAME_BUILD` | 当前 RPG.exe 不属于已确认构建 |
| `-5` | `CASTLE_ERROR_DUPLICATE_PLUGIN_ID` | 稳定插件 ID 已被另一个模块占用 |
| `-6` | `CASTLE_ERROR_INTERFACE_NOT_FOUND` | 领域接口不存在 |
| `-7` | `CASTLE_ERROR_INTERFACE_VERSION` | 接口存在但版本不支持 |
| `-8` | `CASTLE_ERROR_RESOURCE_CONFLICT` | 地址或命名资源已被不兼容占用 |
| `-9` | `CASTLE_ERROR_SIGNATURE_MISMATCH` | Hook 调用签名不一致 |
| `-10` | `CASTLE_ERROR_EXPECTED_BYTES` | 当前机器码不是声明的原始状态 |
| `-11` | `CASTLE_ERROR_TRANSACTION_STATE` | 事务状态不允许当前操作 |
| `-12` | `CASTLE_ERROR_TRANSACTION_ROLLED_BACK` | 提交失败且已完成回滚 |
| `-13` | `CASTLE_ERROR_NOT_READY` | 领域后端或本帧快照尚未准备好 |
| `-14` | `CASTLE_ERROR_STALE_GENERATION` | 请求和结果不属于同一发布代次 |
| `-15` | `CASTLE_ERROR_UNLOAD_UNSUPPORTED` | 活动资源存在，禁止热卸载 |

新增错误码只能追加，旧错误码的数字和语义永久冻结。

### 9.8 唯一根导出

`Castle_Runtime.dll` 的稳定根导出固定为：

```text
const CastleRuntimeApiV1* __cdecl CastleRuntime_GetApi(CastleU32 requested_abi_version)
```

规则：

- `requested_abi_version == 1` 请求根 ABI v1；
- 不支持时返回空指针；
- 成功返回进程生命周期内地址稳定、只读的函数表；
- 导出名通过 `.def` 固定为未修饰 `CastleRuntime_GetApi`；
- 不通过导入库静态链接，SDK Client 只在主动加载后使用 `GetProcAddress`；
- Runtime 可以保留内部导出，但任何未写入公共头和本文的导出都不构成兼容承诺。

根函数表头部字段顺序固定为：

```text
magic
struct_size
abi_version
runtime_version_major
runtime_version_minor
runtime_version_patch
capability_flags_low
capability_flags_high
```

根函数表首批函数顺序固定为：

```text
GetRuntimeInfo
RegisterPlugin
GetPluginState
QueryInterface
GetDiagnosticGeneration
CopyDiagnostics
```

以后只能在尾部追加函数，调用方必须先检查 `struct_size`。

### 9.9 插件登记结构

`CastlePluginDescriptorV1` 字段顺序固定为：

```text
magic
struct_size
descriptor_version
flags
module
plugin_id
display_name
version_text
build_id
```

语义：

- `module` 是当前 ASI 自身模块；
- `plugin_id` 是永久稳定 ID；
- `display_name` 只用于界面和日志；
- `version_text` 是用户可读语义版本；
- `build_id` 用于区分同版本测试构建；
- `flags` 声明是否支持独立模式、是否拥有 Hook、是否提供领域后端等基础事实。

`RegisterPlugin` 必须幂等：同一模块、同一 ID 和同一构建重复登记返回原句柄；同一 ID 被不同模块占用返回冲突。登记成功后，如果插件之后提交 Hook 或发布后端，Runtime 必须把该模块固定驻留。

### 9.10 QueryInterface 施工规格

根 API 的 `QueryInterface` 使用请求/结果结构，不直接返回无法解释的裸指针。

请求至少包含：

```text
interface_id
requested_version
minimum_struct_size
required_capabilities_low/high
```

结果至少包含：

```text
api_pointer
actual_version
actual_struct_size
capabilities_low/high
provider_generation
```

规则：

- `interface_id` 是稳定 ASCII 命名空间；
- Runtime 返回的是统一门面，不是任意插件私有函数表；
- `provider_generation` 在领域后端切换时递增；
- 调用者不得缓存后端模块地址，只缓存 Runtime 门面；
- 热路径接口必须保证门面地址稳定，后端切换由 Runtime 内部原子完成；
- 查询失败不改变任何状态。

### 9.11 ABI v1 固定 magic、版本和结构大小

第一轮头文件直接使用以下常量：

| 常量 | 数值 | ASCII 解释 |
|---|---:|---|
| `CASTLE_RUNTIME_API_MAGIC` | `0x4E555243` | 内存字节 `CRUN` |
| `CASTLE_PLUGIN_DESC_MAGIC` | `0x474C5043` | 内存字节 `CPLG` |
| `CASTLE_QUERY_MAGIC` | `0x59525143` | 内存字节 `CQRY` |
| `CASTLE_INTERFACE_API_MAGIC` | `0x49504143` | 内存字节 `CAPI` |
| `CASTLE_HOOK_API_MAGIC` | `0x4B4F4843` | 内存字节 `CHOK` |
| `CASTLE_DISPLAY_API_MAGIC` | `0x50534443` | 内存字节 `CDSP` |
| `CASTLE_RUNTIME_ABI_V1` | `1` | 根 ABI v1 |
| `CASTLE_PLUGIN_DESCRIPTOR_V1` | `1` | 插件描述 v1 |
| `CASTLE_QUERY_VERSION_1` | `1` | 接口查询结构 v1 |

x86、4 字节对齐下，首批结构大小固定为：

| 结构 | 固定大小 | 计算依据 |
|---|---:|---|
| `CastleStringView` | `8` | 指针 4 + 长度 4 |
| `CastlePluginDescriptorV1` | `52` | 4 个 U32 + module 4 + 4 个字符串视图 |
| `CastleInterfaceQueryV1` | `40` | 4 个 U32 + 接口 ID 8 + 4 个 U32 |
| `CastleInterfaceResultV1` | `40` | 4 个 U32 + API 指针 4 + 5 个 U32 |
| `CastleRuntimeApiV1` | `56` | 8 个 U32 + 6 个函数指针 |

构建检查器必须使用编译器生成的小程序或对象符号验证这些数字。若 C 结构定义无法得到上述大小，先修复对齐和字段定义；不得直接改文档数字来迁就意外 padding。

### 9.12 根能力位

根函数表的 64 位能力空间由 low/high 两个 U32 组成。v1 首批 low 位固定为：

| 位 | 常量 | 含义 |
|---:|---|---|
| `0` | `CASTLE_RUNTIME_CAP_PLUGIN_REGISTRY` | 插件登记与状态 |
| `1` | `CASTLE_RUNTIME_CAP_QUERY_INTERFACE` | 版本化领域查询 |
| `2` | `CASTLE_RUNTIME_CAP_DIAGNOSTICS` | 内存诊断与复制 |
| `3` | `CASTLE_RUNTIME_CAP_HOOK_TRANSACTION` | 补丁事务 |
| `4` | `CASTLE_RUNTIME_CAP_HOOK_CHAIN` | CALL/IAT/vtable 链 |
| `5` | `CASTLE_RUNTIME_CAP_SERVICE_PROVIDER` | 领域后端注册 |
| `6` | `CASTLE_RUNTIME_CAP_DISPLAY_V1` | Display v1 门面 |
| `7` | `CASTLE_RUNTIME_CAP_SCHEDULE_V1` | 调度接口已具备可用阶段源 |

未实现能力位必须保持 0。调用方不能因为 Runtime 版本号较新就跳过能力检查。

### 9.13 根函数签名和插件状态值

根 API 六个函数的 ABI 语义固定为：

```text
CastleResult GetRuntimeInfo(CastleRuntimeInfoV1* out_info)

CastleResult RegisterPlugin(
    const CastlePluginDescriptorV1* descriptor,
    CastlePluginHandle* out_handle)

CastleResult GetPluginState(
    CastlePluginHandle handle,
    CastlePluginStateV1* out_state)

CastleResult QueryInterface(
    const CastleInterfaceQueryV1* query,
    CastleInterfaceResultV1* out_result)

CastleU32 GetDiagnosticGeneration(void)

CastleResult CopyDiagnostics(
    CastleU32 after_generation,
    CastleDiagnosticBufferV1* output)
```

所有函数指针使用 `CASTLE_RUNTIME_CALL`，v1 在 x86 上展开为 `__cdecl`。

插件状态数字固定为：

| 数值 | 状态 |
|---:|---|
| `0` | `CASTLE_PLUGIN_UNKNOWN` |
| `1` | `CASTLE_PLUGIN_REGISTERED` |
| `2` | `CASTLE_PLUGIN_PREFLIGHTING` |
| `3` | `CASTLE_PLUGIN_ACTIVATING` |
| `4` | `CASTLE_PLUGIN_ACTIVE` |
| `5` | `CASTLE_PLUGIN_DEGRADED` |
| `6` | `CASTLE_PLUGIN_FAILED` |
| `7` | `CASTLE_PLUGIN_PROCESS_EXIT` |

状态只能按 Runtime 允许的方向推进。插件不能直接写状态；后续 Hook/Provider API 在事务和后端状态变化时由 Runtime更新。

### 9.14 根辅助结构施工规格

`CastleRuntimeInfoV1` 字段顺序固定为：

```text
magic, struct_size, info_version, flags
runtime_version_major, runtime_version_minor, runtime_version_patch, abi_version
capability_flags_low, capability_flags_high
process_id
runtime_module
game_module
game_build_id
runtime_path
diagnostic_generation
```

其中两个字符串视图各 8 字节，x86 固定大小为 `72`。

`CastlePluginStateV1` 字段顺序固定为：

```text
magic, struct_size, state_version, flags
plugin_handle
state
state_flags
last_result
plugin_generation
active_claim_count
provider_count
```

x86 固定大小为 `44`。

`CastleDiagnosticBufferV1` 字段顺序固定为：

```text
magic, struct_size, buffer_version, flags
utf8_buffer
buffer_capacity
bytes_written
first_generation
last_generation
required_capacity
```

x86 固定大小为 `40`。调用方提供 `utf8_buffer` 和容量；Runtime 只写入完整 UTF-8 诊断行，不截断一个 UTF-8 序列。容量不足时返回需要的最小容量，不跨 DLL 分配内存。

首批 magic 固定为：

| 常量 | 数值 | 内存字节 |
|---|---:|---|
| `CASTLE_RUNTIME_INFO_MAGIC` | `0x464E4943` | `CINF` |
| `CASTLE_PLUGIN_STATE_MAGIC` | `0x54535043` | `CPST` |
| `CASTLE_DIAGNOSTIC_BUFFER_MAGIC` | `0x41494443` | `CDIA` |

## 十、插件身份和能力

### 10.1 稳定插件标识

每个插件必须拥有不随文件名变化的 ASCII 标识，例如：

```text
org.castlereforge.controller
org.castlereforge.backlog
org.castlereforge.saveenhance
org.castlereforge.widescreen
org.castlereforge.fpsunlock
```

规则：

- 全部小写；
- 使用反向域名式层级；
- 发布后不得复用给另一个插件；
- 文件改名不改变标识；
- 分支测试版仍使用同一标识，通过版本和构建号区分。

### 10.2 插件描述

插件描述至少包含：

- 标识；
- 用户可见名称；
- 语义版本；
- SDK ABI 主版本；
- 插件能力位；
- 可选/必需服务；
- 当前模块句柄；
- 构建标识；
- 是否允许独立降级。

描述只陈述能力，不允许在查询阶段执行初始化。

### 10.3 依赖语义

依赖分三类：

| 类型 | 含义 | 缺失时行为 |
|---|---|---|
| 必需业务依赖 | 插件核心功能无法运行 | 插件自身安全停用 |
| 可选服务依赖 | 只增强联动 | 关闭对应增强 |
| 顺序提示 | 影响体验但可动态发现 | 记录提示，不阻止启动 |

官方插件应尽量使用可选服务依赖，避免形成脆弱的整套强绑定。

## 十一、资源声明模型

运行时将可能冲突的对象统一称为“资源”。第一版资源类型如下：

| 资源类型 | 默认策略 | 典型用途 |
|---|---|---|
| 独占字节范围 | 不可串联 | NOP、常量、条件跳转、整段函数入口替换 |
| rel32 CALL 链 | 同签名可串联 | `E8` 调用点 wrapper |
| IAT 指针链 | 同签名可串联 | Win32、Bink 等导入槽 |
| vtable 指针链 | 同签名可串联 | 原版对象 Update/Draw 槽 |
| 命名进程资源 | 按资源规则 | WndProc、定时器精度、输入所有权 |
| 版本化服务 | 多版本查询 | PadSupport、未来 UI/存档服务 |

每项声明必须带：

- 插件所有者；
- 游戏构建标识；
- 地址或稳定资源名；
- 范围大小；
- 当前预期字节或原目标；
- 资源类型；
- 调用签名标识；
- 是否可选；
- 所属事务；
- 冲突时允许的降级方式。

## 十二、Hook 与补丁协调

### 12.1 先声明，后写入

插件不得边发现边写。正确流程为：

1. 开始事务；
2. 声明本事务全部资源；
3. 运行时检查游戏构建、地址范围、字节和现有所有者；
4. 所有必需声明通过后才进入提交；
5. 提交中任意一步失败，恢复本事务已经修改的内容；
6. 返回逐项结果和统一错误码。

这可以避免“前四个 Hook 已安装，第五个失败后插件半工作”的状态。

### 12.2 独占字节范围

原始字节补丁默认不可串联。运行时使用半开区间 `[address, address + size)` 检查重叠。

即使两个插件希望写入相同结果，也不自动合并，除非未来出现经过单独设计的“共享恒定补丁”类型。第一版宁可明确拒绝，也不建立隐式共同所有权。

### 12.3 CALL、IAT 与 vtable 链

只有同时满足以下条件才允许串联：

- 地址完全相同；
- 资源类型相同；
- 调用签名标识相同；
- 原始目标一致；
- 每个 Hook 都明确声明会继续调用 `next`，或明确声明自己是终止节点；
- 优先级规则能够确定唯一顺序。

运行时为每个链节点提供稳定的 `next` 指针槽。插件 Hook 每次从该槽读取下一目标，不把安装时目标永久硬编码进私有全局。

这样后加载插件插入链中间时，运行时只需要更新稳定槽；不要求上层插件重新扫描机器码，也不要求它知道下层插件文件名。

### 12.4 调用签名标识

运行时不猜测函数参数。每个可串联 Hook 必须使用稳定签名标识，例如：

```text
castle.x86.thiscall.void.this
castle.x86.fastcall.long.this
castle.game.button_event.v1
castle.game.render_queue.v1
```

签名不匹配时，即使地址相同也视为冲突。

正式 SDK 应为已经确认的公共游戏调用点提供命名签名，第三方私有地址可以使用自己的命名空间。

### 12.5 确定性排序

Hook 链不能依赖 ASI 实际加载先后。第一版排序键固定为：

1. 明确阶段：`EARLY`、`NORMAL`、`LATE`；
2. 同阶段内使用受限优先级；
3. 优先级相同按稳定插件标识排序。

禁止插件使用极端数字“抢第一”。SDK 只提供有限、文档化的优先级档位。确需前后约束时，应通过显式 `before/after` 关系提交，循环依赖直接拒绝事务。

### 12.6 安装细节

统一写入器必须执行：

- 地址和长度溢出检查；
- 精确字节或当前链状态检查；
- `VirtualProtect` 临时开放最小范围；
- 完整写入；
- 恢复原页面保护；
- `FlushInstructionCache`；
- 写后复核；
- 失败时恢复事务开始前的真实内容；
- 保留原始内容和所有者诊断。

禁止业务插件绕过事务调用运行时内部写入器。

### 12.7 卸载规则

第一版以稳定为先：

- 拥有活动 Hook、发布服务或被其它链引用的插件由运行时固定驻留；
- 不承诺游戏运行中的 `FreeLibrary` 热卸载；
- 正常进程退出不做无意义的大规模机器码恢复；
- 调试环境显式卸载只能在没有任何活动资源时允许；
- 未来热卸载必须单独设计执行中计数和安全点，不能顺手加入 v1。

这比允许 DLL 被卸载后留下悬空函数指针更可靠。

### 12.8 Hook API v1 函数施工清单

`org.castlereforge.runtime.hook` v1 的统一门面首批函数固定为：

```text
BeginTransaction
AddExclusivePatch
AddRelativeCallHook
AddPointerHook
AddNamedResource
AddOrderConstraint
PreflightTransaction
CommitTransaction
AbortTransaction
GetClaimResult
GetHookBinding
DescribeResource
```

调用顺序固定为：

```text
Begin
  ↓ Add 一项或多项声明
Preflight
  ↓ 全部必需项通过
Commit
  ↓ 成功后取得 HookBinding
插件能力激活
```

插件不得跳过 `Preflight`。`Commit` 内部仍必须重新检查一次当前字节，防止预检与提交之间被其它线程或未知插件修改。

### 12.9 目标地址结构

所有地址声明使用 `CastleTargetAddressV1`：

```text
module
rva
size
```

规则：

- `module` 必须是已经登记或由 Runtime 识别的模块；
- `rva + size` 必须检查 32 位溢出；
- 目标范围必须完全落在同一已提交映像区域；
- 游戏公共地址优先使用 Runtime 符号查询得到的模块/RVA；
- 插件 Hook 函数地址可以是绝对 x86 地址，但 Runtime 必须验证它属于声明插件模块；
- 不允许用空模块隐式表示“随便哪个模块”。

### 12.10 独占补丁声明

`CastleExclusivePatchClaimV1` 至少包含：

```text
struct_size
flags
target
expected_bytes + expected_size
replacement_bytes + replacement_size
label
```

`expected_size`、`replacement_size` 和 `target.size` 必须完全相等。`AddExclusivePatch` 返回前，Runtime 把两段字节和标签复制到事务内存；调用方随后可以释放临时构造缓冲区。

第一版不支持通配机器码。确需忽略重定位字段时，必须新增经过评审的掩码声明类型，不能把“不检查某些字节”偷偷塞进 v1。

### 12.11 链式 Hook 声明

`CastleChainHookClaimV1` 至少包含：

```text
struct_size
hook_kind                  CALL / IAT / VTABLE
flags
target
expected_original_target
replacement_hook
signature_id
phase
priority
label
```

规则：

- `replacement_hook` 必须属于登记插件模块；
- `expected_original_target` 是链底原函数，不是安装时偶然看到的上一插件地址；
- Runtime 只接受原始状态或自己已经管理的同签名链；
- CALL 必须验证 `E8` opcode 和 rel32 目标；
- IAT/vtable 必须验证槽宽、当前指针可执行性和链底目标；
- `signature_id` 不同直接冲突；
- `phase/priority` 只使用 SDK 公开常量；
- 所有声明数据在 Add 时复制。

### 12.12 稳定 next 槽

事务提交成功后，插件使用 `GetHookBinding` 取得：

```text
claim_handle
next_slot
chain_generation
```

`next_slot` 是 Runtime 拥有、地址永久稳定的对齐指针单元。插件 Hook 每次调用前读取 `*next_slot`，再以声明签名调用下一节点。

Runtime 允许更新槽内目标，但不移动槽本身。这样后加载插件插入链中间时：

1. Runtime 在锁内重算确定顺序；
2. 先填写所有节点的下一目标；
3. 使用发布屏障；
4. 最后原子更新调用点的顶层目标；
5. 递增 `chain_generation`。

插件不得缓存某次读取到的 `next` 目标到永久私有变量，也不得通过模块名判断下一节点是谁。

### 12.13 事务状态机和失败原子性

事务状态固定为：

```text
BUILDING
  ├── Preflight成功 → PREFLIGHTED
  ├── Abort          → ABORTED
  └── 声明错误       → INVALID

PREFLIGHTED
  ├── Commit成功     → COMMITTED
  ├── Commit失败回滚 → ROLLED_BACK
  └── Abort          → ABORTED
```

硬规则：

- 一个事务只能由创建线程构建和提交；
- Runtime 可以串行化不同插件的提交；
- 事务锁只保护 Runtime 元数据和短时写入，持锁时不调用插件代码；
- 提交前保存每一处真实旧值；
- 中途失败按逆序恢复已写内容；
- 回滚后逐项复核；
- 回滚也失败时，把 Runtime 标记为严重故障，停止批准新的写事务，但不盲目改写已经稳定的其它插件资源；
- `COMMITTED` 事务记录保留到进程结束，供诊断和冲突查询。

### 12.14 第一版顺序约束

阶段固定为：

```text
FOUNDATION
PRE
NORMAL
POST
FINAL
```

普通第三方插件只能使用 `PRE/NORMAL/POST`。`FOUNDATION` 保留给 Runtime 自己的基础链，`FINAL` 只用于经过项目级评审的最终输出后端。

同阶段优先级只提供有限档位：

```text
EARLY
DEFAULT
LATE
```

第一版 `AddOrderConstraint` 只允许声明一个稳定插件 ID 必须位于本节点之前或之后。Runtime 对约束图执行拓扑排序；出现循环时拒绝包含循环的新增事务，不改变现有链。

### 12.15 Hook v1 固定数值与结构大小

Hook kind 数字固定为：

| 数值 | 类型 |
|---:|---|
| `1` | `CASTLE_HOOK_REL32_CALL` |
| `2` | `CASTLE_HOOK_IAT_POINTER` |
| `3` | `CASTLE_HOOK_VTABLE_POINTER` |

阶段数字固定为：

| 数值 | 阶段 |
|---:|---|
| `0` | `CASTLE_HOOK_PHASE_FOUNDATION` |
| `1` | `CASTLE_HOOK_PHASE_PRE` |
| `2` | `CASTLE_HOOK_PHASE_NORMAL` |
| `3` | `CASTLE_HOOK_PHASE_POST` |
| `4` | `CASTLE_HOOK_PHASE_FINAL` |

优先级数字固定为：

| 数值 | 优先级 |
|---:|---|
| `0` | `CASTLE_HOOK_PRIORITY_EARLY` |
| `1` | `CASTLE_HOOK_PRIORITY_DEFAULT` |
| `2` | `CASTLE_HOOK_PRIORITY_LATE` |

事务状态数字固定为：

| 数值 | 状态 |
|---:|---|
| `0` | `CASTLE_TRANSACTION_INVALID` |
| `1` | `CASTLE_TRANSACTION_BUILDING` |
| `2` | `CASTLE_TRANSACTION_PREFLIGHTED` |
| `3` | `CASTLE_TRANSACTION_COMMITTED` |
| `4` | `CASTLE_TRANSACTION_ABORTED` |
| `5` | `CASTLE_TRANSACTION_ROLLED_BACK` |

x86、4 字节对齐结构大小固定为：

| 结构 | 大小 |
|---|---:|
| `CastleTargetAddressV1` | `12` |
| `CastleExclusivePatchClaimV1` | `52` |
| `CastleChainHookClaimV1` | `64` |
| `CastleHookBindingV1` | `28` |
| `CastleHookApiV1` | `64` |

声明结构统一以 `magic, struct_size, version, flags` 四个 U32 开头。首批 magic 固定为：

| 常量 | 数值 | 内存字节 |
|---|---:|---|
| `CASTLE_EXCLUSIVE_PATCH_MAGIC` | `0x54415043` | `CPAT` |
| `CASTLE_CHAIN_HOOK_MAGIC` | `0x4E484343` | `CCHN` |
| `CASTLE_HOOK_BINDING_MAGIC` | `0x444E4243` | `CBND` |

`CastleHookApiV1` 使用 4 个 U32 表头和第 12.8 节列出的 12 个函数指针，因此固定为 `16 + 12×4 = 64` 字节。

## 十三、服务注册与发现

### 13.1 服务不是模块名

消费者不再把 `GetModuleHandleA("Castle_PadSupport.asi")` 当作长期项目级发现协议。服务使用稳定标识和版本，例如：

```text
org.castlereforge.input.pad / v1
```

提供者可以改文件名或内部实现，只要服务 ABI 保持不变，消费者就不需要修改。

### 13.2 服务表规则

服务采用与 Runtime API 相同的函数表模式：

- `magic`；
- `struct_size`；
- `api_version`；
- `capability_flags`；
- 明确线程语义；
- 只读稳定表；
- 尾部兼容扩展。

### 13.3 PadSupport v1 迁移

现有 `CastlePad_GetApi` 已经是成功的稳定只读 ABI，不应废弃。

迁移方式：

1. Controller 继续保留现有导出；
2. 整合模式下额外把同一张 v1 函数表注册为输入后端；
3. 新消费者优先查询 Runtime 服务；
4. Runtime 缺失时继续使用现有模块导出；
5. API v1 字段、枚举和语义永久冻结；
6. 不创建只服务于某一个新插件的 PadSupport 私有 v2。

这样可以渐进迁移，不会让 Backlog、SaveEnhance 或第三方插件突然失效。

### 13.4 晚到服务

第一版不在运行时内部锁中主动调用消费者。服务晚到时，消费者可以：

- 在自己的安全 Tick 中低频查询；
- 使用运行时的无回调变更计数判断是否值得重新查询；
- 在明确的安全调度服务出现后再选择订阅。

先用查询保证简单可靠，未来再增加回调式通知。

## 十四、全领域接口与宽屏显示后端

### 14.1 根接口与领域子接口

Runtime 对外是整个 ASI 生态的统一 API 门面。根接口保持稳定，通过 `QueryInterface` 取得版本化领域接口。首批命名方向如下：

```text
org.castlereforge.runtime.core
org.castlereforge.runtime.hook
org.castlereforge.runtime.schedule
org.castlereforge.game.state
org.castlereforge.game.display
org.castlereforge.game.input
org.castlereforge.game.ui
org.castlereforge.game.save
org.castlereforge.game.quest
org.castlereforge.game.battle
org.castlereforge.game.dialogue
org.castlereforge.game.audio
```

这里列出的是领域，不是要求第一版立即实现所有业务。根接口必须允许以后新增战斗、音频、剧情、任务日志或其它领域，而不修改已经发布的结构。

施工状态分级：

| 接口 | 当前施工状态 | 第一职责 |
|---|---|---|
| `runtime.core` | 第一阶段实现 | Runtime 信息、插件登记、QueryInterface、诊断 |
| `runtime.hook` | 事务阶段实现 | 所有权、补丁事务、Hook 链 |
| `runtime.schedule` | 接口位保留，安全阶段源确认后实现 | 主线程任务和游戏阶段调度 |
| `game.state` | 接口位保留 | 统一场景/UI/Battle/对话等只读状态 |
| `game.display` | 首个正式领域实现 | 显示几何、模式、投影和后端 |
| `game.input` | Pad API 迁移时实现 | 输入快照、语义输入、所有权 |
| `game.ui` | 未来实现 | UI 层级、叠加层和输入门 |
| `game.save` | SaveEnhance 迁移时设计 | 安全保存能力和状态 |
| `game.quest` | Quest 开始施工时设计 | 任务、Marker 和任务状态服务 |
| `game.battle` | 未来实现 | Battle 状态和公共阶段 |
| `game.dialogue` | 未来实现 | 对话/选择/电影式状态 |
| `game.audio` | 未来实现 | 公共音频能力和资源所有权 |

“接口位保留”只冻结命名空间和由 `QueryInterface` 返回 `NOT_FOUND` 的行为，不创建尚无证据的结构字段或空函数。真正施工某领域时，在本文增加该领域的完整结构、线程、后端和测试设计后再发布版本 1。

每个领域接口遵守：

- Runtime 拥有接口标识、版本规则、默认行为和对外门面；
- 具体插件向 Runtime 注册领域后端；
- Runtime 选择当前有效后端并隔离失败后端；
- 消费插件只调用 Runtime 领域接口；
- 后端插件文件名、加载顺序和内部实现不进入消费者 ABI；
- 没有专业后端时，Runtime 使用原版默认后端或返回明确“不支持”。

### 14.2 不允许整合模式中的插件直连

整合模式下，官方和新 SDK 插件不得通过下面方式建立长期依赖：

```text
GetModuleHandle("另一个插件.asi")
GetProcAddress("另一个插件私有导出")
扫描另一个插件机器码或内部全局变量
复制另一个插件私有结构偏移
```

现有 PadSupport Public API v1 作为迁移兼容入口继续保留，但新代码优先查询 Runtime Input 接口。其它新领域从一开始只面向 Runtime。

这条规则让 `Castle_Runtime.dll` 真正掌握整套插件的接口、后端和生命周期，而不是只做一个旁观登记簿。

### 14.3 Display API 是首个正式领域样板

宽屏和任务 Marker 的关系证明，显示坐标不能由消费者根据 INI、固定边宽或原版 Camera 自行猜测。Display API 应成为 Runtime 第一个完整领域接口。

统一调用关系：

```text
Quest / Marker / 其它叠加层
        ↓ QueryInterface(Display v1)
Castle_Runtime.dll 的 Display 统一门面
        ├── 没有宽屏后端：原版 640×480 投影
        └── Widescreen 后端：使用本帧最终 CameraPlan 投影
```

Quest 不直接依赖 `Castle_Widescreen.asi`，Widescreen 也不需要知道 Quest 的存在。

### 14.4 当前 Widescreen 实现提供的事实基础

当前 Widescreen v0.11-poc11 的原 renderer 始终只认识 640×480 世界区域。插件通过最多三次世界绘制，再拼成最终输出：

```text
中央：CameraX = plan.center_x
左侧：CameraX = plan.center_x - plan.left_shift
右侧：CameraX = plan.center_x + plan.right_shift
```

最终输出通常为：

```text
16:9：107 + 640 + 107 = 854
21:9：240 + 640 + 240 = 1120
```

但 `plan.center_x` 不一定等于游戏原始 CameraX。宽屏会根据地图边界、原版 viewport 和当前输出宽度进行安全 Clamp；地图不足 854/1120 时，左右实际补画宽度还会小于 107/240。

绘制结束后，Widescreen 会把 `GLOBAL_CAMERA_X` 恢复为游戏原值。因此其它插件在普通 Tick 中读取到的是“原版逻辑 Camera”，不一定是玩家本帧真正看到的显示 Camera。

这意味着下面的算法不能作为正式宽屏适配：

```text
screenX = worldX - gameCameraX + 固定边宽
```

权威算法必须由已经生成最终 CameraPlan 的 Widescreen 后端提供。当前实现证据见 [`../../src/Widescreen/source/widescreen.c`](../../src/Widescreen/source/widescreen.c)。

### 14.5 DisplayGeometrySnapshot v1

Display v1 至少提供一份只读、同一发布代次内自洽的最终显示几何快照。字段语义至少覆盖：

| 字段类别 | 必需信息 |
|---|---|
| ABI | `magic`、`struct_size`、`api_version`、能力位 |
| 发布一致性 | `generation`、显示帧/计划序号、后端标识 |
| 最终输出 | `output_width`、`output_height` |
| 原版逻辑区 | `logical_width=640`、`logical_height=480` |
| 中央区位置 | 中央 640×480 在最终输出中的矩形 |
| 权威 Camera | `effective_camera_x`、`effective_camera_y` |
| 诊断 Camera | 游戏原始 Camera，可选，只用于诊断，不用于正式投影 |
| 实际世界扩展 | `left_world_width`、`right_world_width` |
| 当前模式 | 普通宽屏世界、电影式 4:3、硬 4:3、Battle 4:3、过渡、不可用 |
| 世界叠加范围 | 全输出、仅中央 640、禁止显示 |
| 过渡状态 | 当前侧面板覆盖量或等价的标准化进度 |

`left_world_width/right_world_width` 表示本帧真正完成世界补画的宽度，不能简单返回用户配置中的 107/240。

### 14.6 WorldToScreen v1

Display v1 必须提供 Runtime 统一的世界坐标投影入口。调用者提交世界坐标，Runtime 通过当前有效显示后端返回：

```text
screen_x
screen_y
visibility
display_generation
```

`visibility` 至少区分：

```text
VISIBLE
OFFSCREEN_LEFT
OFFSCREEN_RIGHT
OFFSCREEN_TOP
OFFSCREEN_BOTTOM
NOT_PROJECTABLE
```

设计要求：

- 消费者不读取 Widescreen INI；
- 消费者不复制 CameraPlan 算法；
- 消费者不假定固定 107/240；
- 返回结果对应最终合成输出，而不是临时左/中/右某一次 renderer pass；
- 返回结果携带发布代次，避免几何快照和投影结果来自不同帧；
- 坐标精度和舍入规则由 Display ABI 固定；
- Widescreen 内部将来更换三 Camera 实现时，Display v1 语义保持不变。

### 14.7 显示模式与 Marker 策略

Display API 不直接实现任务系统，但必须提供足够状态让 Quest 作出稳定策略：

| 显示状态 | Display 投影范围 | Quest 推荐行为 |
|---|---|---|
| 原版 4:3 | 中央 640×480 | 使用原版投影 |
| 普通宽屏世界 | 完整 854/1120 | Marker 可使用完整世界区域 |
| 电影式对白 4:3 | 中央 640 或禁止 | 默认隐藏世界 Marker，或由 Quest 明确选择中央限制 |
| Battle 4:3 | 禁止世界叠加 | 隐藏世界 Marker |
| 标题/Bink/主 Interface 硬 4:3 | 禁止世界叠加 | 隐藏世界 Marker |
| 过渡/无稳定计划 | `NOT_PROJECTABLE` | 保持隐藏，不使用上一帧猜测 |

具体 Marker 产品策略属于 Quest，但“当前画面能否投影世界坐标”由 Display API 权威回答。

### 14.8 Widescreen 后端发布时机

Widescreen 后端必须在本帧 `CameraPlan` 完成计算、任何临时 Camera 写入之前，构造最终显示快照并提交给 Runtime。提交后：

- 快照在下一次完整发布前保持只读；
- 中央、左、右三次临时 Camera 变化不能覆盖该快照；
- 恢复 `GLOBAL_CAMERA_X` 不能把快照改回原版 Camera；
- Display 调用者通过代次检查获得自洽数据；
- Widescreen 未就绪或安装失败时撤销后端，由 Runtime 切回原版显示后端。

第一版可以使用奇偶 `generation` 或 Runtime 内部复制实现无撕裂发布，但最终 ABI 只承诺一致性，不暴露 Widescreen 私有 `CameraPlan` 结构。

### 14.9 Runtime 缺失时的 Quest 回退

Quest 必须保留独立模式：

- 同目录没有 `Castle_Runtime.dll` 时，使用原版 640×480 `World - Camera` 投影；
- 不扫描 Widescreen 私有变量；
- 不读取 Widescreen INI 推断当前宽度；
- 无法确认显示几何时宁可隐藏 Marker；
- Runtime 存在时必须使用 Runtime Display 门面，不得另走私有宽屏适配。

### 14.10 Display API v1 函数施工清单

`org.castlereforge.game.display` v1 的消费者门面固定提供：

```text
GetDisplayState
GetGeometry
WorldToScreen
ScreenToWorld             （能力位可选）
GetProviderInfo
```

提供者管理入口固定提供：

```text
RegisterDisplayProvider
PublishDisplayGeometry
SetDisplayProviderReady
GetDisplayProviderState
```

普通消费者只能使用消费者门面。只有持有有效 `CastlePluginHandle` 且声明 Display Provider 能力的插件才能调用提供者入口。

`GetGeometry` 的调用方先把输出结构的 `struct_size` 和请求版本填好；Runtime 只写调用方容量内已定义字段。`WorldToScreen` 请求至少包含：

```text
struct_size
requested_generation       0 表示接受当前代次
world_x
world_y
flags
```

结果至少包含：

```text
struct_size
actual_generation
screen_x
screen_y
visibility
projection_scope
```

如果调用方指定的 `requested_generation` 已过期，返回 `CASTLE_ERROR_STALE_GENERATION`，不得混用新几何和旧请求。

### 14.11 Display Provider v1

Widescreen 注册的 `CastleDisplayProviderV1` 是只读函数表，头部使用公共 ABI 头。第一版后端函数固定为：

```text
GetProviderState
CopyCurrentGeometry
WorldToScreen
ScreenToWorld             （可选）
```

Runtime 调用后端时遵守：

- 不持有 Runtime 全局锁；
- 提供者模块已固定驻留；
- 提供者函数不得再次进入 Hook 事务提交；
- 热路径不得读配置文件、加载 DLL 或写日志正文；
- 返回 `NOT_READY/STALE_GENERATION` 时 Runtime 最多按规定次数重试，不能无限循环；
- 后端异常或连续返回非法结构时被标记故障，Runtime 原子切回默认后端。

Display 领域只允许一个外部权威投影后端。Runtime 原版后端始终存在但优先级最低；两个外部插件同时申请权威投影后端时，后注册者收到明确资源冲突，不能按文件加载顺序随机覆盖。

### 14.12 Display v1 固定枚举与结构大小

显示模式数字固定为：

| 数值 | 模式 |
|---:|---|
| `0` | `CASTLE_DISPLAY_UNKNOWN` |
| `1` | `CASTLE_DISPLAY_ORIGINAL_4_3` |

| `3` | `CASTLE_DISPLAY_CINEMATIC_4_3` |
| `4` | `CASTLE_DISPLAY_HARD_4_3` |
| `5` | `CASTLE_DISPLAY_BATTLE_4_3` |
| `6` | `CASTLE_DISPLAY_TRANSITION` |

| `1` | `CASTLE_PROJECTION_CENTER_640` |

| 数值 | 可见性 |
|---:|---|

| `1` | `CASTLE_VISIBILITY_OFFSCREEN_LEFT` |

`CastleDisplayGeometryV1` 字段顺序固定为：

```text

magic, struct_size, result_version, flags
```

## 十五、游戏版本与地址目录

### 15.1 运行时是游戏身份与公共符号权威

`Castle_Runtime.dll` 负责给当前 RPG.exe 生成稳定构建标识，例如基于：

- PE 时间戳；
- ImageSize；
- 关键节哈希；
- 项目已确认的完整文件哈希。

Runtime 维护公共游戏符号和地址解析接口，是整合模式下的统一身份与符号权威。已经成为跨插件公共协议的地址应进入 RuntimeSDK 规范符号目录；只服务于单个插件实验阶段的私有地址可以先留在插件内，但注册 Hook 时仍要向 Runtime 声明。

Runtime 不应把每个实验地址都固化进根 API 函数表。新增符号通过版本化符号目录和查询接口扩展，避免每发现一个地址就破坏核心 ABI。

### 15.2 SDK 符号目录

规范源码目录中单独维护版本化游戏符号目录。符号至少包含：

- 稳定名称；
- 所属游戏构建；
- RVA；
- 地址类型；
- 已确认调用签名；
- 最小机器码证据；
- 来源模块和验证状态。

插件提交 Hook 时仍必须携带自己依赖的精确预期字节。符号目录用于减少地址漂移，不替代插件能力级预检。

### 15.3 未知构建

如果当前游戏构建不在支持表：

- Runtime 可以加载并输出诊断；
- 不能批准任何依赖固定地址的写事务；
- 不依赖地址的纯服务仍可选择运行；
- 插件必须按照自己的能力边界 fail-closed。

## 十六、Runtime 发现、加载与版本管理

### 16.1 同目录主动加载规则

MODLoader、其它 ASI Loader 和 RPG.exe 都不负责加载 `Castle_Runtime.dll`。每个 SDK 客户端只能在 Loader Lock 外执行：

1. 通过自身 ASI 的 `HMODULE` 调用宽字符模块路径 API；
2. 去掉 ASI 文件名，保留插件实际所在目录；
3. 追加固定文件名 `Castle_Runtime.dll`；
4. 先检查同目录文件是否存在；
5. 文件不存在时进入独立模式；
6. 文件存在时使用进程级互斥，避免多个 ASI 同时重复加载；
7. 互斥内再次查询进程是否已经加载同名 Runtime；
8. 尚未加载时，用刚构造的同目录完整路径主动加载；
9. 获取 `CastleRuntime_GetApi` 并完成版本协商；
10. 文件存在但任一步失败时进入 Runtime 故障安全停用，不得退回私有写入路径。

这里的“完整路径”不是硬编码用户安装盘符，而是运行时从 ASI 自身位置精确得到“同一个文件夹里的 DLL”。禁止只传裸文件名并依赖当前目录或系统 DLL 搜索顺序，也禁止修改进程 CurrentDirectory、`PATH` 或 `SetDllDirectory`。

SDK Client v1 的加载常量固定为：

```text
文件名：Castle_Runtime.dll
路径缓冲：1024 个 WCHAR
加载互斥：Local\CastleReforge.RuntimeLoad.v1.<8位十六进制PID>
互斥等待上限：10000 ms
```

加载互斥只保护“发现/首次加载/根 API 校验”这段过程，不保护插件业务。等待超时后 Client 再查询一次现有模块；仍无有效 Runtime 且同目录文件存在时进入 Runtime 故障安全停用。

发现同名模块已经加载时，Client 必须取得该模块的实际完整路径，与自己计算出的同目录 Runtime 路径进行不区分 ASCII 大小写的规范化比较。路径不一致视为重复/错误 Runtime，禁止随机选择其中一个。

首个 Client 使用同目录完整路径调用宽字符动态加载函数。根 API 校验成功后，Runtime 把自身模块固定驻留到进程结束；Client 不调用 `FreeLibrary`。

### 16.2 为什么不会被游戏或 Loader 误加载

- Runtime 使用 `.dll` 后缀，不属于 ASI Loader 的 `.asi` 扫描目标；
- RPG.exe 没有对它的静态导入；
- 各 ASI 也不得静态链接它，否则 Windows 会在 ASI DllMain 前自动加载；
- 只有 SDK 客户端在 Loader Lock 外显式调用动态加载；
- Runtime 的 DllMain 保持最小，不执行游戏业务和 Hook。

因此把它放在 ASI 文件夹不会导致游戏主动加载，反而能确保插件与自己需要的运行时处于可预测的同一部署单元。

Runtime v1 不允许静态依赖其它项目 DLL。正式目标为 PE32/x86、无 CRT、静态导入只使用 KERNEL32；领域后端和插件能力全部通过运行时函数表连接。

### 16.3 分发规则

- 官方整合包在 ASI 文件夹包含一份经过验证的 `Castle_Runtime.dll`；
- 单独插件包可以不带运行时，因为插件必须能够独立降级；
- 希望获得完整多插件协调的用户把同一份官方 Runtime 放到 ASI 同目录；
- 第三方插件不得在相同文件名下分发私自修改、ABI 不兼容的运行时；
- SDK 主版本 1 的新运行时必须兼容所有旧 v1 客户端；
- 新客户端查询不到某个可选领域能力时必须使用 Runtime 默认后端或关闭对应增强，不得绕过 Runtime；
- 不在游戏进程内自动覆盖、升级或删除运行时文件。

正式仓库构建输出固定为：

```text
build\mods\asi\Castle_Runtime.dll
```

Runtime v1 不创建 `Castle_Runtime.ini`。是否加入整合模式不属于用户配置；文件是否存在就是模式边界。

### 16.4 旧文件覆盖风险

ABI 主版本固定后，旧运行时被手工覆盖不会让旧插件崩溃。较新的插件如果需要旧运行时没有的能力，只关闭该增强并输出明确版本提示。

如果文件存在但根 ABI 已损坏或完全不兼容，插件必须故障安全停用；只有缺少某个可选子接口时，才允许在整合模式内降级该领域能力。

## 十七、错误隔离和诊断

### 17.1 错误码

错误必须分层，不使用单一 `false` 表示所有问题。至少区分：

- 运行时不存在；
- ABI 不兼容；
- 游戏构建不支持；
- 插件重复登记；
- 地址范围冲突；
- 调用签名冲突；
- 原字节不匹配；
- 事务依赖循环；
- 页面保护失败；
- 写后复核失败；
- 服务版本不支持；
- 当前操作只支持进程退出时清理。

### 17.2 日志边界

运行时维护自己的协调日志，只记录：

- 运行时版本和游戏构建；
- 插件登记；
- 事务提交/回滚；
- 资源所有者和链顺序；
- 服务注册；
- 冲突和错误。

日志文件固定放在 Runtime 同目录：

```text
Castle_Runtime.log
```

第一版每次进程启动清空旧日志，使用 UTF-8 BOM、CRLF 和简体中文。日志只能在 Loader Lock 外打开。文件创建失败时继续维护固定容量的内存诊断环，供 `CopyDiagnostics` 查询。

插件业务日志仍由各插件负责。运行时不得吞并战斗、存档、输入等业务日志。

冲突日志必须同时提供：

- 请求插件标识；
- 已有所有者标识，若能识别；
- 地址/RVA 或资源名；
- 资源类型；
- 预期与实际摘要；
- 决定结果；
- 被关闭的是哪个可选能力。

### 17.3 无日志也必须安全

日志文件创建失败不能改变内存安全决策。所有拒绝、回滚和状态判断必须独立于日志是否可写。

| `CastleRuntime.def` | 固定未修饰公共导出名 | 私有测试导出、按序号导出 |
| `client/runtime_client.c` | ASI 同目录发现、主动加载、双入口状态机和独立模式 | 运行时全局注册表、业务逻辑 |

每个文件只承担表中职责。需要跨职责的新功能先修改本文和模块边界，不能直接把方便代码塞进现有文件。

### 18.2 SDK 快照与单包独立性

仓库内 `src/RuntimeSDK` 是唯一权威源。为了让第三方或单独源码包不依赖完整仓库，构建/打包工具可以生成版本化 SDK 快照：

```text
CastleRuntimeSDK-v1/
├─ include/
├─ source/RuntimeClient.c
├─ examples/
├─ 构建与接入说明.md
├─ 截至该版本的完整接档.md
└─ 文件校验清单.md
```

快照必须由工具生成并校验哈希，禁止在各插件目录手改副本。官方插件若需要随源码包携带快照，也必须由同一工具同步并通过版本/哈希检查。

## 十九、迁移策略

迁移必须渐进完成，禁止一次性把全部插件切到尚未实机验证的新地基。

### 阶段 0：设计冻结

- 评审本文；
- 冻结 ABI 原则、目录和运行模式；
- 不改现有插件行为。

### 阶段 1：最小骨架

- 建立 `src/RuntimeSDK`；
- 实现只读版本查询、插件登记和诊断；
- 实现同目录主动加载、双入口幂等状态机、自动加入、独立模式和 Runtime 故障安全停用；
- 此阶段不修改任何 RPG.exe 字节。

### 阶段 2：影子登记

- 选择一个低风险插件；
- 插件仍使用原有补丁工具，但把计划占用的地址同时登记为“观察项”；
- 对比运行时诊断与插件真实写入；
- 验证不同加载顺序、缺失运行时和旧运行时。

### 阶段 3：独占补丁事务

- 先迁移不可串联的固定字节补丁；
- 验证范围重叠、事务回滚和未知旧插件检测；
- 保留插件原有独立模式。

### 阶段 4：第一个真实 Hook 链

首选 `Controller + SaveEnhance` 的 SaveAction 重叠点，因为当前已经存在经过思考和实机准备的手工链式兼容，可以作为新旧结果对照。

迁移目标：

- 删除按模块名识别对方 Hook 所有者的必要性；
- 由运行时提供稳定 `next` 槽；
- 任意加载顺序得到相同链；
- 同目录无 Runtime 时继续保留当前手工安全路径，直到新路径实机通过；
- Runtime 存在时只能使用受管理链，不允许回退私有链。

### 阶段 5：Display v1 与 Widescreen 后端

- 先实现 Runtime 原版 640×480 Display 默认后端；
- Widescreen 发布最终 CameraPlan 几何快照；
- 实现 Runtime `WorldToScreen` 统一门面；
- 使用静态模拟和实机验证原版、16:9、21:9、窄地图 Clamp、对白、Battle、硬 4:3 和过渡；
- Quest 仅在该阶段通过后接入 Display v1。

### 阶段 6：绘制链与输入后端

- 迁移 `Widescreen + FPSUnlock` 的当前目标协作；
- 把 PadSupport Public API v1 注册为版本化服务；
- Backlog、SaveEnhance 改为“服务优先、旧导出回退”。

### 阶段 7：第三方 SDK

- 发布最小示例插件；
- 发布 ABI/资源声明检查工具；
- 发布常见 Hook 类型模板；
- 明确兼容承诺和禁止事项；
- 新增大型官方插件默认使用 SDK，旧插件按风险逐步迁移。

## 二十、各现有模块的目标边界

| 模块 | 当前特点 | 首批迁移目标 |
|---|---|---|
| Controller | 自有 Runtime、工作线程、Pad Public API、Hook 数量多 | 服务注册、Hook 声明、共享地址和事务 |
| Backlog | 自有 Runtime/线程，通过 Pad API 协作 | 服务发现、生命周期客户端、少量 Hook 登记 |
| SaveEnhance | `InitializeASI` 生命周期、独立 PatchUtil、与 Controller 手工链 | 双入口初始化、SaveAction 链、事务回滚 |
| Widescreen | DllMain 内初始化、绘制 CALL、Bink IAT、权威 CameraPlan | Display 后端、几何快照、WorldToScreen、统一生命周期、绘制链和 IAT 链 |
| FPSUnlock | 独立大文件实现，显式兼容宽屏当前目标 | 绘制链查询、计时资源声明、统一补丁事务 |
| Extra 系插件 | 小型、独立、共享三份工具头 | 先验证独占事务与 SDK 独立模式，不强行一次性重构 |
| 未来 Quest | 需要任务 Marker 和世界投影 | 只查询 Runtime Display/Game State，不读取 Widescreen 私有状态或 INI |
| MODLoader | 可选 Launcher/环境/ASI 管理 | 只做可选 SDK 诊断和排序适配，不拥有 Runtime ABI |

## 二十一、测试矩阵

任何 RuntimeSDK 正式版本至少验证以下组合。

### 21.1 单插件独立模式

- 每个官方 ASI 在同目录没有 `Castle_Runtime.dll` 时单独加载；
- 使用 Castle Mod Loader；
- 使用另一种兼容 32 位 ASI Loader；
- 插件业务功能和日志符合现有基线。

### 21.2 整合模式

- Runtime 先存在；
- 两个插件并发发现 Runtime；
- 所有插件和 Runtime 位于同一 ASI 文件夹；
- 不同插件加载顺序全排列或代表性排列；
- 同一插件重复初始化；
- 插件文件改名但稳定标识不变；
- 文件存在时确认没有插件进入独立写入路径；
- MODLoader 和其它 ASI Loader 均不直接加载 Runtime。

### 21.3 版本兼容

- 旧客户端 + 新 Runtime；
- 新客户端 + 旧 Runtime；
- 缺少可选能力；
- 文件存在但 ABI 主版本不匹配时进入故障安全停用；
- 结构尾部扩展；
- 未知能力位。

### 21.4 Runtime 文件故障

- `Castle_Runtime.dll` 位数错误；
- 文件损坏；
- 唯一导出缺失；
- 根 API magic/size/version 不合法；
- Runtime 初始化中途失败；
- 所有 SDK 插件均拒绝私自写入并输出一致诊断；
- 删除错误文件后，各插件恢复独立模式。

### 21.5 Hook 安全

- 原版字节匹配；
- 原版字节不匹配；
- 独占范围部分重叠；
- CALL 签名不匹配；
- 链优先级不同；
- `before/after` 循环；
- 提交中途 `VirtualProtect` 失败；
- 写后复核失败；
- `FlushInstructionCache` 失败；
- 未接入 SDK 的插件先修改目标；
- 可选事务失败但核心事务继续。

### 21.6 生命周期

- DllMain 与 `InitializeASI` 同时竞争；
- 初始化线程创建失败；
- 进程正常结束；
- 调试器尝试主动卸载；
- 服务提供者晚于消费者；
- 插件登记后业务初始化失败。

### 21.7 Display 与 Quest

- 原版 640×480 默认后端；
- 854×480 与 1120×480；
- `plan.center_x != original_camera_x`；
- 左右扩展小于 107/240 的窄地图；
- 对白电影式 4:3；
- Battle 4:3；
- 标题/Bink/主 Interface 硬 4:3；
- 进入/退出过渡；
- Widescreen 后端未就绪、故障和回退；
- Quest Marker 不读取 INI、不固定加边宽、不在禁止状态显示；
- `generation` 变化时不混用投影结果。

### 21.8 实机

静态测试、模拟内存和单元测试通过后，仍必须在目标台湾第三版 RPG.exe 上验证：

- 游戏可进入；
- 各插件单独功能；
- 组合功能；
- 加载顺序；
- 返回标题、新游戏、读档和退出；
- 日志与实际行为一致；
- 未出现输入穿透、重复调用、重复 Present 或存档路径变化。

## 二十二、正式实现前必须冻结的接口

开始写代码前，应先把以下内容评审并冻结为 ABI v1 草案：

1. `CastleRuntime_GetApi` 调用约定；
2. 基础整数和字符串类型；
3. `CastleRuntimeApiV1` 头部字段；
4. 插件稳定标识规则；
5. 插件登记结构；
6. 事务和资源声明结构；
7. 资源类型枚举；
8. 错误码；
9. Hook 签名标识格式；
10. 稳定 `next` 槽的生命周期；
11. 服务表注册和查询；
12. 独立模式状态与日志格式；
13. 固定文件名 `Castle_Runtime.dll` 与同目录主动加载规则；
14. 文件存在时强制整合、文件缺失时独立、文件故障时安全停用；
15. Display v1 几何、模式、可见性和代次；
16. Display Provider v1 发布时机；
17. 插件固定驻留规则。

在这些接口冻结前，不应开始批量迁移现有插件。

## 二十三、防止连锁坏影响的硬性不变量

未来实现和评审必须逐条检查：

1. 同目录没有 Runtime 时，单个插件仍能正常运行；
2. Runtime 根 ABI 兼容但版本较旧时，新插件只降级缺失的可选领域能力；
3. Runtime 文件存在但根 ABI 不可用时，插件绝不转入私有写入路径；
4. 一个插件登记失败不会破坏已经运行的插件；
5. 一个事务失败只回滚本事务；
6. Runtime 自身基础写入与插件写入全部通过同一事务/所有权系统；
7. 所有游戏写入都来自已登记并通过预检的事务；
8. 未知现有 Hook 不自动加入链；
9. 持锁时不调用插件代码；
10. Hook 所有者不会在函数指针仍可达时被卸载；
11. 新字段只追加，不重解释旧字段；
12. Castle Mod Loader 缺失不改变 SDK 基础语义；
13. 插件实际加载顺序不改变已声明链的最终确定顺序；
14. Runtime 存在时所有 SDK 插件自动加入且不可绕过；
15. 消费插件只面对 Runtime 领域门面，不直接依赖后端插件；
16. Display 投影使用最终显示计划，不使用原版 Camera 猜宽屏坐标；
17. 日志失败不改变安全判断；
18. 任何自动化工具都不能替代目标游戏实机验收；
19. 尚未迁移的插件继续以当前已验证实现为准，不被强制改写。

任意实现如果违反其中一项，必须停在设计/实验阶段，不能作为公共根基发布。

## 二十四、第一轮代码工作的严格边界

第一轮只允许建立“不会修改游戏”的骨架：

- Runtime DLL 最小入口；
- API 版本查询；
- 插件登记；
- 内存中的诊断快照；
- SDK 客户端发现和独立降级；
- Runtime 文件存在时的强制加入与故障安全停用；
- 双入口幂等状态机；
- 单元测试和 ABI 检查工具；
- `docs/runtime/截至该版本的完整接档.md`。

第一轮禁止：

- 迁移 Controller 大量 Hook；
- 修改 SaveEnhance 存档逻辑；
- 接管 Widescreen/FPSUnlock 绘制链；
- 删除现有公共 Pad API；
- 改变任何当前实机已确认功能；
- 宣称第三方 SDK 已稳定发布。

只有骨架在多 Loader、缺失 Runtime、旧/新版本和重复初始化矩阵中通过后，才进入影子登记阶段。

## 二十五、当前接档摘要
