## 二、最高优先级定位

### 2.1 Runtime 的地位

`Castle_Runtime.dll` 是整套 ASI 类型 Mod 的最核心运行时引擎，负责：

- 统合所有已接入 SDK 的 ASI；
- 驱动和管理插件生命周期；
- 调度插件能力和游戏阶段任务；
- 统一 Hook、补丁、IAT、vtable 和命名资源所有权；
- 维护事务、回滚和冲突隔离；
- 提供涉及游戏各方面的统一领域 API；
- 选择原版默认后端或插件提供的专业后端；
- 维护插件身份、版本、依赖、状态和诊断；
- 防止插件之间依赖文件名、私有结构和加载顺序。

Runtime 不是 MODLoader 子组件。MODLoader 是仓库内的可选加载器和环境增强工具，优先级低于可独立运行的 ASI 插件。

### 2.2 双模式硬规则

没有 `Castle_Runtime.dll`：

- 每个 ASI 使用自己的现有安全路径；
- 单独安装能够正常工作；
- 不依赖 MODLoader；
- 不承诺多个独立插件拥有完整全局协调。

同目录存在有效 `Castle_Runtime.dll`：

- 所有 SDK 插件必须自动加入；
- 不允许 INI、环境变量或普通命令行绕过；
- 所有新增游戏写入必须经过 Runtime；
- 所有跨插件接口必须通过 Runtime 领域门面；
- 各 ASI 组成一个由 Runtime 统一驱动和协调的整体。

同目录文件存在但无法加载或根 ABI 不可用：

- 不得悄悄退回独立写入；
- 进入 Runtime 故障安全停用；
- 只保留无游戏写入的诊断；
- 防止同一进程出现受管理与绕过管理的混合状态。

## 三、固定文件名、位置与加载责任

文件名永久固定为：

```text
Castle_Runtime.dll
```

位置固定为所有 ASI 所在文件夹，例如：

```text
mods\asi\Castle_Runtime.dll
mods\asi\Castle_PadSupport.asi
mods\asi\Castle_Widescreen.asi
mods\asi\Castle_SaveEnhance.asi
```

加载责任：

- RPG.exe 不加载 Runtime；
- Castle Mod Loader 不直接加载 Runtime；
- 其它 ASI Loader 不直接加载 Runtime；
- ASI 不静态导入 Runtime；
- 每个 SDK Client 在 Loader Lock 外，根据自身 `HMODULE` 取得 ASI 实际目录，追加固定 DLL 名并主动加载；
- 动态构造完整路径只是保证“准确加载同目录文件”，不是硬编码用户盘符；
- 禁止仅传裸文件名并依赖 CurrentDirectory、PATH 或系统搜索顺序；
- 禁止为此修改 `SetDllDirectory`。

施工常量已经确定为：

```text
路径容量：1024 WCHAR
进程互斥：Local\CastleReforge.RuntimeLoad.v1.<8位十六进制PID>
等待上限：10000ms
日志：同目录 Castle_Runtime.log
子项目构建输出：build\Castle_Runtime.dll
整合包最终位置：build\mods\asi\Castle_Runtime.dll
```

Runtime v1 不提供 `Castle_Runtime.ini`，不允许用户配置绕过整合模式。目标产物为 PE32/x86、无 CRT、静态导入只使用 KERNEL32。

## 四、全领域 API 模型

Runtime 根 API 保持很小，通过 `QueryInterface` 提供版本化领域子接口。

已规划的领域包括：

```text
runtime.core
runtime.hook
game.state
runtime.schedule
game.display
game.input
game.ui
game.save
game.quest
game.battle
game.dialogue
game.audio
```

以后需要 Battle、Quest、Audio、Dialogue 或其它领域时增加新接口 ID，不修改旧接口结构，也不提前填充大量空函数。

统一关系：

```text
消费者插件
  ↓ 只查询 Runtime
Castle_Runtime.dll 统一门面
  ↓ 选择领域后端
原版默认实现 / 专业插件后端
```

专业插件实现自己最了解的算法，但接口、版本、后端状态和对外调用入口由 Runtime 统合。

## 五、Widescreen 与 Quest 的 Display v1 结论

### 5.1 已确认根因

当前 Widescreen v0.11-poc11：

- 原 renderer 始终只处理 640×480；
- 最多通过中央、左、右三次世界绘制拼出 854/1120；
- `CameraPlan.center_x` 可能被地图边界 Clamp；
- 窄地图的 `left_shift/right_shift` 可能小于 107/240；
- 绘制结束会恢复游戏原始 `GLOBAL_CAMERA_X`。

因此其它插件读取原版 Camera 后固定加 107/240，不能得到玩家本帧实际看到的坐标。

### 5.2 正式方案

Runtime 提供 `game.display` v1 统一门面：

- 没有 Widescreen 后端时使用原版 640×480；
- Widescreen 注册权威显示后端；
- 后端发布本帧最终显示几何快照；
- Runtime 对消费者提供 `WorldToScreen`；
- Quest 不读取 Widescreen INI、私有状态和 CameraPlan；
- Quest 不固定添加 107/240；
- Widescreen 更换内部渲染实现时，Display v1 语义保持。

几何快照至少包含：

- 最终输出宽高；
- 原版逻辑宽高；
- 中央 640×480 在输出中的矩形；
- 本帧权威 Camera；
- 左右实际世界扩展宽度；
- 显示模式；
- 世界投影范围；
- 过渡状态；
- 发布代次。

显示模式至少区分：

- 原版 4:3；
- 普通宽屏世界；
- 电影式对白 4:3；
- Battle 4:3；
- 标题/Bink/主 Interface 硬 4:3；
- 过渡；
- 不可投影。

### 5.3 发布时机

Widescreen 在 CameraPlan 完成后、临时修改 Camera 之前发布最终快照。快照不能随着中央/左/右临时 pass 改变，也不能在恢复原始 Camera 时被改回。

## 六、Hook 与事务施工结论

所有游戏写入遵守：

1. 插件先登记；
2. 开始事务；
3. 声明全部地址和资源；
4. 预检游戏构建、范围、字节、签名和现有所有者；
5. 所有必需声明通过后提交；
6. 提交前再次检查；
7. 中途失败逆序回滚；
8. 写后复核、恢复页面保护、刷新指令缓存；
9. 保留进程生命周期诊断记录。

资源类型：

- 独占字节范围；
- rel32 CALL 链；
- IAT 指针链；
- vtable 指针链；
- 命名进程资源；
- 版本化领域后端和服务。

链式 Hook 使用 Runtime 拥有的稳定 `next` 槽：

- 槽地址不变；
- Runtime 可以更新槽内下一目标；
- 插件 Hook 每次读取当前 `next`；
- 插件不得永久缓存安装时目标；
- 链顺序由阶段、有限优先级、稳定插件 ID 和显式前后约束决定；
- 未知 Hook 不自动加入链。

## 七、ABI 施工边界

已确定：

- 纯 C ABI；
- x86 明确调用约定；
- 固定宽度整数；
- 4 字节公开结构对齐；
- 所有结构包含 `magic/struct_size/version`；
- 字段只能尾部追加；
- UTF-8 字符串视图带显式长度；
- 不跨 DLL 共享堆内存所有权；
- 不公开 STL、C++ 类、异常和私有结构；
- 根导出固定为 `CastleRuntime_GetApi`；
- SDK 插件必须导出 `CastlePlugin_Query`、`InitializeASI` 与 `CastleRuntimeClient_NotifyLoaderReady`；
- 根 API 提供 `RegisterPlugin` 和 `QueryInterface`；
- 结果码区分缺失、版本、冲突、事务、机器码和代次问题。

已经在权威设计中冻结首批数字和字段；代码阶段必须用编译器验证：

- 文档常量与真实头文件一致；
- 每个结构得到文档规定的精确 `sizeof`；
- 每个字段偏移与生成的 ABI 清单一致；
- `.def` 最终导出表；
- 头文件在 C 与 C++/MSVC/clang-cl 下的一致性。

## 八、生命周期施工结论

DllMain 只允许：

- 保存模块句柄；
- 关闭线程通知；
- 初始化原子状态；
- 安装/验证精确 5 字节 SDK Entry Gate。

禁止在 DllMain：

- 加载 Runtime；
- 读写 INI/业务日志；
- 安装 Entry Gate 以外的 Hook；
- 创建 bootstrap thread 与游戏主线程竞争；
- 等待线程或锁；
- 调用其它插件；
- 执行业务初始化。

普通启动型 ASI Loader 由 RPG Entry Gate 在主线程、Loader Lock 外触发；MODLoader 先加载全部 ASI，再第二遍调用 `InitializeASI`。两条路径进入同一 BootstrapAll。SaveEnhance 当前只依赖 MODLoader 回调，未来迁移时增加标准 Gate/Query，但不能把完整初始化放回 DllMain。

Runtime v1 不等待固定毫秒猜扫描结束：普通 Loader 以 RPG 原入口作为全部启动 ASI 已映射的边界；MODLoader 以明确两阶段作为边界。游戏入口后的晚注入不支持。

## 九、已否决方案及原因

### 9.1 Runtime 放进 CastleModCore.dll

否决。会让可独立 ASI 反向依赖可选 MODLoader。

### 9.2 Runtime 使用 `.asi`

否决。会进入 ASI 扫描、排序和用户启停语义，形成新的顺序问题。

### 9.3 首个插件自动成为协调器

否决。普通插件会变成隐式全局单点，版本选举、固定驻留、故障和卸载都不干净。

### 9.4 只传 `LoadLibrary("Castle_Runtime.dll")`

否决。会依赖当前目录和系统 DLL 搜索顺序。正式方案仍是“同目录”，但由 ASI 自己动态构造准确完整路径。

### 9.5 文件存在但 Runtime 不兼容时回退独立写入

否决。会在同一进程混合受管理和绕过管理的 Hook，破坏 Runtime 的全局保证。

### 9.6 Quest 复制 Widescreen CameraPlan 或读取 INI

否决。消费者会与宽屏内部实现和每帧实际状态漂移。

### 9.7 巨型固定 API 表预埋所有未来函数

否决。使用稳定根 API + `QueryInterface` + 版本化领域接口扩展。

没有发现需要推翻“独立模式 + Runtime 整合模式 + 全领域门面 + 专业后端”的根架构。RuntimeSDK 先独立完成，旧插件随后允许大改适配；FPSUnlock 暂不合并。剩余风险来自 SDK 实现、逐插件适配和实机，而不是某个已完成子项目无法套用设计。

### 11.6 MODLoader 最小兼容裁决

源码确认当前 MODLoader Gate Thunk 在 `CastleModCore_Initialize` 返回后自己重放 RPG 入口前 5 字节，再跳 `EntryPoint+5`。因此 SDK 插件在 ASI DllMain 安装的新 Gate不会由 MODLoader 自然执行。

用户已批准未来对 MODLoader 做唯一受控兼容修改：

1. 先 LoadLibraryExW 全部启用 ASI；
2. 每个成功模块仍立即补挂 Locale/Overrides IAT；
3. 保存成功 HMODULE；
4. 全部加载结束后，再按相同顺序第二遍调用 InitializeASI；
5. 第一个 SDK 插件触发 BootstrapAll，后续幂等返回。

不修改：

- MODLoader Entry Gate；
- Locale/CP950；
- Overrides；
- GameAudit；
- mods.ini 顺序；
- 传统 DllMain-only ASI；
- Runtime 的所有权边界。

MODLoader 仍不加载 `Castle_Runtime.dll`、不包含 SDK 头、不理解插件 ID。

可见影响只有：自定义 `InitializeASI` 从“每个 ASI 加载后立即调用”延后到“全部 ASI DllMain 完成后调用”。当前官方 SaveEnhance 不依赖早于后续 DllMain，预计无负面影响；第三方若依赖旧时序必须迁移。传统 DllMain-only ASI 无变化。
