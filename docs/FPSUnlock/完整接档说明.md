# 《幽城幻剑录》Castle_FPSUnlock 截至 v1.3 的完整接档说明

> 本文是截至 v1.3 的累计接档文档。任何人只拿到本包，也应能理解目标、原版架构、关键地址、成功/失败路线、宽屏兼容方式、实机证据、当前实现、测试结论、风险与下一步。

## 一、项目目标

最终目标：

```text
Legacy Logic：原版约20Hz / 50ms
普通探索 Render/Present：目标约60Hz
```

不可破坏原则：

1. 不增加 Legacy Tick；
2. 不把 EVE WAIT、Battle Tick、AI、RNG、SF2 逻辑倒计时提频；
3. 不把已证明有副作用的完整 GUI Draw Queue 重放到60Hz；
4. 60FPS必须既有真实 Present，也应尽量有世界位置中间态；
5. 与 Castle_Widescreen 共存。

## 二、原版可信基线

RPG.exe

## 三、20Hz Legacy Clock 已确认结论

研究固化38确认：

```text
DDDES.SCI +0x11 = 20
名义 Legacy Tick = 20Hz = 50ms
```

固化40确认 Battle runtime 39 槽只在合格 Legacy Tick 上推进。

因此禁止：

```text
DDDES 20 -> 60
50ms Timer -> 16.67ms
直接把 0x44A970 调到每秒60次
```

这类方案会改变逻辑速度。

## 四、主循环与一帧结构

主循环：

```text
0x401707  检查 0x46F38D Legacy pending
0x40171C  CALL 0x44A970
...
0x40179C  CALL [0x460198] = WaitMessage
```

`0x44A970`：

```text
0x44A9B3 -> 0x434830  对象/队列准备
0x44A9BA -> 0x4345F0  Legacy Update，调用对象 vtable[0]
0x44A9BF -> 0x4020A0  Pre-Draw helper
0x44A9C6 -> 0x434710  Draw Queue，调用对象 vtable[1]
0x44A9CB -> 0x4020F0  Post helper
0x44A9E6 -> 0x405A10  Present
```

这证明 Logic Update 与 Draw Dispatch 是分开的。

## 五、Draw Queue

```text
count   = 0x8DDA38
entries = 0x8DDA40
entry   = 8 bytes = sort key + object pointer
max     = 200
```

Scene World Manager：

```text
vtable[1] draw = 0x40B050
```

BattleManager：

```text
vtable[1] draw = 0x4429F0
```

### 关于 world object +0x280 的修正

v1.2 曾把：

```text
world_object + 0x280
```

当作 `scene_identity`。

重新核对原版 `0x40B050`：

```asm
0x40B072  mov ecx,[esi+0x280]
0x40B078  call 0x40ADE0
```

机器码只证明 `+0x280` 是 world draw 传给内部渲染函数 `0x40ADE0` 的子对象/运行对象指针，没有证据证明它跨 Legacy Tick 恒定，也没有证据证明它适合作为“场景身份”。

v1.3 删除该假设。连续场景使用 Scene World Manager 对象指针本身判断。

## 六、Camera 已确认结构

```text
GLOBAL_CAMERA_X             0x978514
GLOBAL_CAMERA_Y             0x978518
GLOBAL_CAMERA_FOLLOW_OBJECT 0x978550
follow +0x10                X
follow +0x14                Y
```

`0x44B360` 会读取 follow 对象坐标并更新 Camera X/Y，同时做地图边界限制。

Camera shake：

```text
0x978534
```

`0x40B050` 会调用 `0x44B500`；shake 状态下该路径会推进状态并触及 RNG，因此 Camera shake 不允许额外 world draw，保持20Hz。

## 七、v1.0 实机结论

v1.0 成功证明独立额外 Present 调度是可行的。实机日志曾出现：

```text
原版Present=175，额外Present=315
原版Present=375，额外Present=699
原版Present=575，额外Present=1083
```

但失败点：

- 只是重复同一20Hz状态，Camera/人物视觉仍像20Hz；
- 完整 Draw Queue 被重放，多个 GUI 动画闪烁频率翻倍；
- 直接占用宽屏 Render/Present Hook，产生加载顺序冲突。

结论：

- 独立 WaitMessage/Present 调度保留；
- 完整队列重放永久废弃；
- 必须 Render-only 生成中间世界状态；
- 不得与宽屏争用同一 CALL。

## 八、v1.1 实机结论

v1.1 改成 world-only 思路，但错误要求原始完整 Draw Queue 只能存在 Scene World Manager。

实机：

```text
LegacyFrame=997
ExtraPresent=0
非纯世界跳过=931
```

说明正常探索 Draw Queue 本来就是混合队列。

正确协议：

```text
完整混合队列原版绘制一次
额外帧只筛出其中 draw=0x40B050 的 world entry
```

该协议与宽屏当前实现一致。

## 九、v1.2 实机结论

v1.2 修复混合队列后，用户实机：

```text
LegacyFrame=223
ExtraPresent=0
无world跳过=102
Battle跳过=0
运行态保护跳过=15
等待运动历史=106
```

这份日志非常关键：

- 约121个 Legacy Frame 已经捕获到 world；
- 其中15个被运行态保护挡住；
- 剩余106个全部因为“运动历史未准备”不安排 extra frame；
- `ExtraPresent` 仍然为0。

所以 v1.2 的真正错误是：

```text
是否有两帧运动历史
        ↓
错误地决定是否允许60Hz补帧
```

而不是 world 识别失败。

同时 `+0x280 scene identity` 假设没有机器码证据支撑，很可能导致历史不断重置。

## 十、v1.3 当前正式架构

### 10.1 本插件写入的 Hook

```text
0x40171C  Legacy Frame CALL -> LegacyFrameHook
0x44A9BF  Pre-Draw helper CALL -> PreDrawHook
0x460198  WaitMessage IAT -> FrameWaitHook
```

不写：

```text
0x44A9C6 RenderQueue CALL
0x44A9E6 Present CALL
```

额外帧执行时动态解析这两个 CALL 当前目标，因此可跟随宽屏 Hook。

### 10.2 PreDrawHook

顺序：

1. 先执行原版 `0x4020A0`；
2. 在 `0x434710` 消费队列前扫描实时混合 Draw Queue；
3. 只复制 `draw=0x40B050` 的 world entries；
4. 其它 GUI/SF2/HUD 条目允许存在但不复制；
5. 看到 `draw=0x4429F0` 时记录 Battle gate。

### 10.3 LegacyFrameHook

v1.3 每个真实 Legacy Frame 开始前先清空本帧捕获状态，防止 `0x44A970` 早退时误用上一帧 world queue。

然后完整执行原版 `0x44A970`。

返回后：

1. 如果本帧没有 world：不补；
2. 如果 Battle：不补；
3. 读取本 Tick 最终 Camera/follower 状态；
4. 更新运动历史；
5. 通过运行态安全 gate；
6. 无论运动历史是否已经可预测，都安排：

```text
+17ms Extra World Render + Present
+33ms Extra World Render + Present
```

这条是 v1.3 的核心硬保证。

### 10.4 Motion history

`MotionState` 记录：

```text
camera_x/y
follow_object
follow_x/y
follow_valid
world_object
```

连续性规则：

- `world_object` 相同：Camera 历史连续；
- `world_object` 变化：Camera/follower 历史重置一帧；
- follower 指针变化：只取消 follower 本帧预测；Camera 仍可继续预测。

### 10.5 预测

对每轴：

```text
delta = current - previous
predicted = current + delta * elapsed_ms / 50
```

如果：

```text
abs(delta) > MaxPredictionStep
```

则直接使用 current，避免传送/切图飞屏。

Camera 预测后还夹到 `0x44B300/0x44B360` 使用的地图边界。

### 10.6 无历史时的行为

v1.3 不再“等待”。

如果还没有两个状态：

```text
predicted = current
```

仍会执行 world-only draw + Present。

所以日志里的：

```text
无插值历史但仍补帧
```

只表示该组帧暂时没有位置预测，不是跳过。

## 十一、额外 world frame

每次 extra frame：

1. 再次检查运行态 gate；
2. 动态读取 `0x44A9C6` 当前 RenderQueue 目标；
3. 动态读取 `0x44A9E6` 当前 Present 目标；
4. 计算 Camera/follower 临时预测；
5. 临时写入预测值；
6. 把保存的 world-only entries 恢复成 synthetic queue；
7. 强制消息 target/current 状态在 world draw 短窗口为0；
8. 调当前 RenderQueue；
9. 立即恢复真实 Camera/follower 逻辑坐标；
10. 清理 synthetic queue 残留；
11. 调当前 Present；
12. `ExtraPresent++`。

真实逻辑状态不会把预测值保留下来。

## 十二、运行态安全 gate

当前禁止 extra world frame 的状态包括：

- main active gate 不满足；
- 新 Legacy Tick 已 pending；
- transition/debug/capture；
- 消息/对话；
- 标题；
-主 Interface；
- Camera shake；
- scene render override；
- world extra overlay；
- frame gate object 激活；
- 原版完整 draw queue 在空闲期又出现新项；
- follower 在17~33ms空闲窗口被其它代码换对象。

这些保护不是逻辑帧率控制，而是防止把尚未闭合副作用的世界分支重复到60Hz。

## 十三、宽屏兼容协议

当前宽屏会 Hook：

```text
0x44A9C6 RenderQueue
0x44A9E6 Present
```

FPSUnlock 不写这两个 CALL，只解析当前目标。

因此：

```text
FPSUnlock先加载 -> 宽屏仍可安装自己的Hook
宽屏先加载 -> FPSUnlock额外帧进入宽屏当前Hook
```

这是 v1.0 冲突后的正式解决方案。

## 十四、GUI 闪烁问题的正式结论

v1.0 实机已证明完整 Draw Queue 中存在 draw-side effect：重复 draw 会让 GUI 闪烁频率翻倍。

所以正式规则：

```text
完整 GUI/SF2/HUD queue：20Hz，只原版一次
Scene World Manager：安全状态下可额外重放
```

不得恢复“复制完整队列到额外帧”的方案。

## 十六、已确认成功方案

- 20Hz Legacy Logic 保留；
- WaitMessage 空闲期安排额外帧；
- 额外 Present 机制本身已由 v1.0 实机证明可达到约40次/秒额外调用；
- 混合队列中筛 world-only；
- GUI/SF2/HUD 不重放；
- 与宽屏不争用 Render/Present CALL；
- Camera/follower 只做 Render-only 临时写入；
- Camera shake 保持20Hz；
- v1.3 将“是否补帧”和“是否有插值历史”彻底解耦。

## 十七、明确失败方案 / 不得恢复

1. `DDDES 20 -> 60`；
2. Legacy Timer 50ms -> 16.67ms；
3. 每秒调用 `0x44A970` 60次；
4. 完整 Draw Queue 60Hz 重放；
5. 只重复 Present 而没有世界中间位置，作为最终视觉方案；
6. 要求原始 Draw Queue 只能有 world；
7. 把 `world+0x280` 当稳定 scene identity；
8. 运动历史未准备时完全禁止额外 Present。

## 十八、当前阻塞项

只有 Windows 实机可确认的两层：

1. v1.3 普通探索 `ExtraPresent` 是否终于持续增长，外部 FPS 是否从20提高；
2. 在调度通过后，Camera/follower 当前字段是否正是 renderer 最终消费的视觉位置，能否获得足够平滑的中间状态。

## 十九、下一步决策树

### A. `ExtraPresent` 增长，外部 FPS 接近60，视觉也变顺

主路线成立，继续做场景覆盖回归和安全 gate 精简。

### B. `ExtraPresent` 增长，外部 FPS 接近60，但视觉仍20Hz

调度已完成。继续逆 `0x40B050 / 0x40ADE0` 内最终实体/Camera 绘制坐标，Render-only 插值移到最终消费点。

### C. `ExtraPresent` 仍为0

查看：

```text
无world跳过
Battle跳过
运行态保护跳过
```

v1.3 已经删除“运动历史阻止调度”，因此此时只排查 world capture / runtime gate / WaitMessage scheduler，不再回到历史判断。

### D. `ExtraPresent` 增长但外部软件仍20FPS

说明 extra render path 在运行，但最终 DirectDraw Flip/Blt 被 wrapper/宽屏/同步机制合并或丢弃。直接继续追 `0x405A10 -> 0x4064E0` 最终呈现链。
